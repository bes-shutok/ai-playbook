# Execute Plan Stack

Execute a stack plan one task at a time. The plan's Terms and Standing constraints define the stack contract; this skill owns branch ordering, evidence verification, draft PR creation, and run records.

## Workflow

1. Before remote work, read the plan, applicable facts, and `github-pr-workflow`; establish scope. Personal or pet runs stay local; unknown scope stops. For company scope, complete repository ownership and authorization checks before any remote operation. `github_review_team` does not authorize access.
2. Run execute-plan setup and claim rules; resolve the placement through execute-plan's Worktree-first policy by reference (the policy paragraph in `agents/skills/execute-plan/worktree-first.md`), adopting the established registered worktree, run context, and claim under the worktrees resolution and the recorded primary checkout, company task branch, and run context under the primary resolution. Keep one stable `run_session_id`, plan path, and placement identity (the registered worktree, or the recorded primary checkout and company task branch); re-bind the current task branch at each transition. Preserve predecessor order and omit descendants.
3. Read required `github_review_team` from `.ai-playbook/facts.md` per Configuration. If absent, stop before PR creation and ask the operator to configure it.
4. For each task in plan order, serially create or switch to a task branch based on the immediate predecessor branch (first task uses the configured base). Before invoking the task-only entry point, complete the retained-run branch transition in the resolved placement:
   - the continuity probe verifies the current placement and recorded branch, taking `--skip-worktree-checks` on a primary-placement run; run it, then switch only to the exact task branch selected from the predecessor;
   - refresh the run claim through `bash scripts/execution_claim.sh refresh <plan-path> --session <id> --runtime <canonical-runtime-id> --branch <task-branch>` and update the manifest identity's `run_branch` to the same branch, preserving `run_session_id`, plan path, and `run_worktree`; the claim refresh and manifest identity update stay as written, with the manifest's `run_worktree` carrying the no-worktree primary form under the primary resolution; record one `stack_branch_transition:` row naming the old branch, new branch, predecessor, and task;
   - re-read the claim and manifest and run the continuity probe with the new branch before launching the worker; the transition row, predecessor order, and pre-worker probe stay as written. If either identity write or the probe fails, stop before task execution with the claim and manifest retained for recovery. The stack-task caller then uses the already verified transition as its existing-run adoption evidence; it does not apply the ordinary resume refusal to the intentionally switched branch.
   Invoke `execute-plan --stack-task <plan-path> --task <N>` on that branch. It owns the task worker, intermediate review, the validation the target's suite policy assigns this boundary, commit, and returned evidence. Do not rerun that boundary's validation here.
5. Require fresh passing task-specific and scope-intersecting validation, plus any check the target's suite policy adds at this boundary, bound to the task commit, and confirm branch HEAD equals it. When the boundary is the run's final stack-task boundary under `full-before-final`, its complete-suite evidence is required before the draft PR. Missing, failing, unavailable, incomplete, or stale evidence blocks advancement; after repair or a changed HEAD, rerun the same task-only entry point and verify fresh evidence.
6. Before PR creation, measure the final changed-line delta (additions plus deletions) against the task's immediate predecessor branch, not trunk, through `github-pr-workflow`'s PR size policy. Resolve applicable guidance, facts, exclusions, boundary inclusivity, and exception prerequisites first; unresolved or contradictory inputs stop before creation. Above a defined hard maximum, record the disposition and stop for replanning before PR creation. At or below the resolved target, proceed; above it, if clean boundaries exist, record and return them for plan re-authoring, then stop before PR creation. If no clean split exists, record why in `Notes for reviewers` and proceed only when applicable policy conditions permit. Do not create a PR or branch outside the plan. Use the description sections `What`, `Why`, `How`, `Testing`, and `Notes for reviewers`, and complete other applicable pre-review requirements. Then create a draft PR with the immediate predecessor as base and the configured team as reviewer; verify all three before the next task.
7. Record each task's branch, immediate base and head identities, policy source and resolved target/maximum/exclusions, additions, deletions, production-line count and disposition, commit SHA, PR identity and state, requested team, and the boundary's policy-qualified validation sets and outcomes in the execute-plan session log. Report blocked tasks and evidence gaps without marking their boundary complete. Documentation-only endpoint slices keep honest descriptions, review, and applicable validation duties.
8. After each task has a verified draft PR and complete records, release the claim through execute-plan, after the stack-final fresh review gate below. Under `full-before-final`, verify before the release that the run's final stack-task boundary carried the policy's final-boundary obligation: the returned evidence names the complete-suite commands with fresh passing results. Complete-suite evidence that is absent, or a suite policy that is unresolvable at that boundary, blocks the release with the gap surfaced to the operator. Keep draft branches and records; never squash or merge. This stack ends at the verified draft-PR stack. Normal execute-plan closeout later archives the still-open plan and removes disposable artifacts after the human PR lifecycle. Stack-final fresh review: before the claim release, while every PR in the stack is still a draft, run one fresh review round (the doing-code-review or review-loop skill) over the full stack diff, from the stack base commit through the stack tip (the stack base commit: the first task branch's base; the stack tip: the final task branch's head). The review runs unconditionally: no threshold, size measure, or candidate-class gate fires it, so no reviewed-state baseline is recorded or compared and every deferred candidate and post-review pivot is inside the reviewed range. Machinery admission: witnessed incident, the 2026-11-09 five-task stack run whose deferred findings and post-review pivots surfaced only in external review (docs/history/backlog/2026-11-09-stack-run-publishes-without-full-diff-review.md); expected catch, every stack run runs the review once before its claim release; false-positive cost, one bounded review round on every stack run including runs with no deferred candidates or pivots; review date 2027-01-09. The review resolves or explicitly accepts every deferred candidate on the run's `inter_review` lines or in the pass records; new non-blocking findings follow the parent's backlog capture; the run parent applies accepted fixes and re-runs the stack's policy-qualified validation before the release; unresolved blocking findings, deferred or review-raised, block the claim release with the gap surfaced to the operator. Accepted fixes land on the owning task branch, descendants restack via the `update-stacked-branches` hand-off, and each affected task re-runs its step 5 validation with fresh evidence and refreshed step 7 records and PR descriptions. Before the release the run parent also lists every recorded `unverified-runtime:` claim from the run's `inter_review` lines and runs or explicitly accepts each.

### Post-publish review-fix round

After the claim release, one external review-fix round on the published stack runs with one owner per step; bash is the required shell for these snippets (no zsh-only expansions). Edit the lowest affected branch, capture its pre-edit tip as the old tip and its post-edit tip as the new tip, then in order:

1. Affected set and restack: `bash scripts/stack_review_round.sh affected` derives the lowest edited branch plus its chain descendants; `bash scripts/stack_review_round.sh restack` replays them in chain order. Method C stays the restack method of record, reused by reference from `agents/skills/update-stacked-branches/SKILL.md`; the helper wraps its mechanical shape and observes its hard rules.
2. Retest: `bash scripts/stack_review_round.sh retest-set` scopes the project test policy's command set to the affected branches; the project test policy owns what runs.
3. Push: `bash scripts/stack_review_round.sh push-leases` pushes each affected branch with a lease built from a fresh remote tip; `bash scripts/stack_review_round.sh verify-heads` confirms remote heads and bases.
4. Replies and thread resolution route to `receiving-review`; replies post only after the push verifies.
5. refresh-descriptions closes the round after every push: route the description refresh to `github-pr-workflow` so each pushed PR's description matches its new head.

Precedence: while an execute-plan-stack run is still active, workflow step 8's `update-stacked-branches` hand-off governs fixes on that run's own tasks; this section governs review-fix rounds on the published stack only after the claim release.

## Configuration (from facts document)

| Key | Purpose | Fallback |
| --- | --- | --- |
| `github_review_team` | Required team slug requested on each draft PR | None; ask the operator to configure it and stop before PR creation |

The key does not authorize remote operations. Apply the project-scope and authorization gate before any remote read or write.

If a completed parent PR changes the base of open descendants, hand off restacking to `update-stacked-branches`; do not implement a second restack procedure here. When the parent is already squash-merged and only child reparenting remains, follow `github-pr-workflow`'s `rebase --onto` routing, which is the explicit exception in the restack skill's routing boundary.

## Integration Points

- `execute-plan` provides the independently usable `--stack-task <plan> --task <N>` boundary, runs the policy-qualified validation set that boundary requires, and returns evidence bound to its commit. This skill verifies and consumes that evidence; it does not repeat task lifecycle or validation mechanics. Once the stack is complete, its run claim is released through execute-plan’s claim lifecycle.
- This skill consumes the doing-code-review or review-loop skill as the stack-final fresh review's executor, named by reference with no mechanics restated.
- `github-pr-workflow` owns project-scope and authorization routing plus GitHub PR creation and verification mechanics. This skill supplies the stack's predecessor base, draft requirement, and facts-configured team reviewer.
- `bootstrap-ai-playbook` documents the repo facts surface where the optional `github_review_team` project value is stored; the key has no shared default.
- `update-stacked-branches` owns restacking after a base moves.
