Every plan-authoring and plan-execution run works inside an ad-hoc worktree, never in the primary checkout by default; the standard governs fresh run work (the Recovery path's in-checkout exception over work already sitting in the primary checkout and an explicitly declared project's primary placement, the Project worktree policy paragraph's resolution for its declaring project, are the sanctioned in-checkout arms). This section owns the canonical lifecycle; consumer skills reference it, they do not restate it. The lifecycle, in imperative steps:

**Profile and placement:** project profile controls unattended maintenance eligibility; direct execute-plan invocation remains available under personal and company profiles. Resolve placement independently under this paragraph.

**Project worktree policy (consulted at dispatch):** a project's facts document may declare `worktree_policy = "worktrees"` (enabling ad-hoc worktrees, with `worktree_root` declaring the location rule); an absent key means the primary checkout for ordinary work and never disables the named lanes below: only an explicitly declared `worktree_policy` is a disabling declaration. The precedence ladder is fixed: an explicit user request for a worktree overrides the project policy and this standard's default; on a named worktree-requiring lane, an explicit user direction against the worktree reports the isolation conflict and stops for operator confirmation. The resolutions: an unconfigured project runs ordinary work in the primary checkout and the plan lanes below in their worktrees as today; a project whose facts explicitly declare `worktree_policy = "primary"` runs all its work, ordinary and named lanes including plan authoring and plan execution, in the primary checkout on its current branch: the placement consult resolves every lane of that project to the primary checkout and no run worktree is created for any of them; the primary placement is serialized by the existing execution-claim rules, so a fresh run in the primary checkout refuses to start while another live execution claim or recorded witness occupies the primary checkout (the same foreign-claim conjunct the provisioned-worktree adoption rule applies), and a resumed run adopts the recorded placement and never re-consults into the other mode mid-run; a primary-placement run works on the primary checkout's current branch and records that branch at start (in the execution claim and the manifest identity block, the primary placement recorded as no run worktree), standing down on a branch mismatch at resume instead of switching the shared checkout's branch; for personal and pet profiles, a primary-placement run is valid only when the primary checkout's current branch is the base branch at run start, and a run finding a non-base current branch stands down with the remedy named in its stand-down report (check out the base branch or take the worktree lane for this run) instead of switching the shared checkout's branch; its per-task commits therefore land on the base branch directly and the run records no landing, while the primary-checkout landing class (lifecycle step 4) stays the prohibition of record, never a hand-composed squash-and-commit sequence in the primary; a company-profile primary-placement run gains the per-run operator choice beside that base-branch-only rule: the choice comes from the operator's run directive, keep-current named explicitly or the task-branch name given, and the run keeps the current branch or creates a named task branch from the current HEAD (a task-branch name colliding with an existing branch carrying foreign work refuses and re-asks; naming the base branch itself is the valid keep-base form; an unattended run with no directive keeps the current branch by default and records that default, so a scheduled company lane never stalls on an ask); the chosen or created task branch records into the execution claim and the manifest identity block beside its start commit (the commit the task branch pointed at when the run started), the recorded task branch satisfies the placement check for the company run, a resume finding the shared checkout on any other branch stands down naming the recorded branch, and no clause switches the shared checkout's branch; the company task-branch arm's per-task commits land on the recorded task branch, the run records no landing (the primary-placement class's existing no-landing shape), and the run record names the PR pairing (the task branch as source, the confirmed base as target) so completion leaves the branch PR-ready; under the primary resolution the immediate-commit rule applies: every change is committed right after the change is made by a plain path-limited commit of the session's own paths (a primary-placement commit that writes a rolling prompt log, the Phase 0 freeze included, is the log's `Write boundary rule` write, a lock refusal standing the write down with the log unchanged), and a minutes-scale final closeout is acceptable, the done skill running once at the end of the session's work while the light boundary's learn capture runs at every boundary under both placements, and subagents return learnings and issues to the parent session, committing nothing themselves; transfer-out is a no-op by construction on a primary placement (there is no run worktree), and the worker-layer dirty-worktree gates are untouched; a project that opts into worktrees allows ad-hoc worktrees at the declared `worktree_root` location rule when a worktree is otherwise warranted by an explicit request or a named lane (opt-in is permission, not a mandate placing ordinary work); A worktree already provisioned for a named lane is adopted for that lane's resume and closeout even under a disabling declaration; the primary resolution's no-new-worktree refusal governs only new provisioning. The named worktree-requiring lanes are this standard's plan lanes; other workflows whose worktrees are created and removed inside one automated section of their own operation (the docs-branch docs checkout, the release rewrite worktree outside the repository tree; the worktree-complete landing critical section executes inside the run worktree and is not a placement decision) are mechanical fixtures that need no consult. The location rule, or its absent-key fallback resolution, resolves to a canonical path outside the primary checkout, every registered worktree, and every other git repository's work tree (a parent directory resolving as another repository's toplevel or git directory is rejected), with the run's branch name or plan slug substituting per run so the resolved path is unique; a `worktree_policy` value outside the two spelled forms, or an unresolvable root, is treated as unconfigured with a named report, never a silent fallback. The policy is consulted before any run-placement worktree decision, never after, and the resolved placement is reported with the worktree path and branch name this section already requires, or reported as a primary-checkout resolution in the same run-record line when no worktree is warranted. Closeout safeguards are unchanged: the transfer-out ordering and the migration-before-removal rule apply to every worktree this policy enables, and the primary checkout's own closeout discipline is untouched.

**Direct-commit class (ordinary ad-hoc work):** an eligible edit is tiny and self-contained, over at most four files, session-owned, carries no behavior, API, or schema change, needs no plan or review cycle, and has a quick verification path (this repository's public-hygiene and em-dash scans over the touched set); an edit inside an open plan's claimed scope is never eligible for the direct-commit class and rides that plan's own closeout, and work governed by another arm's placement or closeout contract (a live plan run holding its worktree or execution claim, a maintenance ad-hoc backlog arm child, a primary placement) is never eligible and rides that arm's own closeout or defers to session end. The placement consult resolves the direct-commit class before escalating ordinary ad-hoc work to a worktree or task branch; an ineligible edit falls through to the existing arms (the primary default, the named worktree lanes, or operator direction). Destinations: company projects commit on the current branch of the target checkout; pet projects and projects with no recorded project_type ask the operator before crossing out of the session's current checkout when it is not the target checkout, any worktree the session occupies included, and proceed unasked when the session already sits in the target checkout. Unattended and live-run arms: with no operator in the turn, the crossing ask resolves as ineligibility, the edit falls through to the existing arms, and the hold is recorded under a named reason; the class never knowingly commits in a target checkout whose consult reports a holder, and never authorizes push. Closeout compatibility precondition: the route is eligible only when the target checkout's index carries no unowned staged entries and, when the target checkout is not the primary checkout, the primary checkout's index carries none either (the primary is the index the landing gate inspects); the declared paths are disjoint from all foreign work and the checkout carries no dirty or untracked path the run classifies as a live peer's foreign claim - unowned staged residue keeps its refusing class, which is exactly what makes that shape ineligible. Closeout integration: the commit lands through the done closeout's path-limited commit in the target checkout with every landing sweep gate running unchanged; immediately before the commit stage the session runs `bash scripts/done-lock.sh merge-status` read-only and stands down while it reports any holder, the stand-down resolving as a named hold of the run per the done skill's blocked posture, never a placement fall-through and never an unbounded re-consult loop. Boundary notes: the class changes neither the maintenance ad-hoc backlog arm's worktree containment and panel contract, nor the plan authoring and execution lanes, nor the primary placement authorization, nor the per-execution worktree isolation protections; the session-shaped exclusion keeps each arm's work out of the class.

1. **Establish the resolved placement.** For worktree placement the take invocation is the plan-carrying run's single create path: `bash scripts/execution_claim.sh take <plan-path> --session <id> --branch <name> --worktree-parent <dir> [--base <ref>]` takes the execution claim create-or-refuse and creates the ad-hoc worktree in one atomic step, before any run work; the worktree it creates sits on its own branch off the per-project base branch (a sibling path, unique per run). A refusal (a fresh foreign claim, or the dead session's worktree still occupying the requested branch) creates no worktree and stands the run down writing nothing, and a create failure after this invocation created its claim deletes that claim again, so no half-created state survives. Restored-worktree resume: a restored worktree whose saved run state explains a surviving claim converts through the claim gateway's dead-run conversion arm per the recovery procedure in agents/skills/maintenance/template-execution.md (the sole recovery procedure; the gateway refuses unchanged when the evidence does not verify, and a converted run adopts the registered worktree instead of creating a second), and the gateway's claim-mutation sites stay last-instant compare-and-delete serialized per its arm-4 (never a second lock; a lost race refuses naming the racing holder). The resume restart (D-10, the wip-auto-checkpoint plan): a resume session restarts from the last checkpoint (the worktree branch's tip, the state the takeover adopts), composing with this arm's claim takeover rather than duplicating it; the unconsumed-successor-handoff disposition rides this arm's reconcile check (the takeover verifies the same run's recorded state, so the predecessor's last checkpoint is the adopted resume state). Survey arm: before creating a new ad-hoc worktree, survey the existing worktrees (`git worktree list --porcelain`) for one already bound to the same plan or run (by the Phase 0 identity block, a fresh foreign or execution claim naming it, or the branch-naming convention for the plan slug); adopt or resume that canonical checkout per the canonical section's provisioned-worktree adoption rule instead of creating a parallel branch, and create a second worktree only for a distinct run or a task with an explicit concurrency and integration contract. Report the worktree path and the branch name. For a project resolving the primary placement under the policy paragraph's primary resolution, create no worktree: verify the current branch is the base branch for personal and pet profiles, with a company-profile run's operator-chosen or created task branch (kept current or created from the current HEAD per the policy paragraph's company arm) satisfying the placement check, record the primary placement and branch, record the chosen or created task branch and its start commit with the claim invocation, take the run-level claim with `bash scripts/execution_claim.sh claim <plan-path> --session <id> --branch <task-branch> --start-commit <start-sha>` (the flags carry the recorded choice: the kept-current or created task branch and the start commit it pointed at, a keep-current run recording the current branch as the branch value), and pass the existing primary-checkout serialization check before any run work; any failed check stands the run down. Task-branch creation carries the working-tree state over as any checkout would, with the worker-layer dirty gates and the stale-checkout discriminator untouched.

**Pre-plan authoring arm (worktree placement; the plan file does not exist yet):** an authoring session holds its own fresh authoring claim (`docs/tmp/authoring-claims/<item>.md` naming this session) before any plan operand exists, so the take invocation above cannot run; the arm is the create path for that shape: derive the branch name `authoring/<claim-file-stem>` from the claim file's basename minus its `.md` extension, create the worktree with `git worktree add -b authoring/<claim-file-stem> <worktree-root>/<claim-file-stem> <base-ref>`, and verify it sits on that named branch, never a detached HEAD. Create nothing when the claim is missing or names a foreign session (the authoring claim paragraph's foreign-claim gate), or when a branch of that name already exists with no live authoring worktree bound to this claim: adopt the existing worktree per the survey and adoption arms or remove the stale branch deliberately, never reuse it blind. The authoring branch lands through lifecycle step 4 like any run branch; deleting its claim stays owned by the authoring claim paragraph's closeout duty.
2. **Transfer the inputs in for worktree placement.** Copy the run's gitignored input artifacts into the worktree before any work: the project facts file and any other gitignored inputs the run needs (for example, the reviews directory the readiness gate resolves). The **Transfer-in implementation** below owns how. For the primary placement, inputs already resolve in the primary checkout; do not copy them or create a worktree. An operator-provided input a plan declares (for example a review-evidence summary) is delivered by the operator or the review-evidence owner, never the run itself, to the run-scoped gitignored home `{tmp_dir}/execute-plan/<PLAN_SLUG>/` in the primary checkout before the consuming task, one entry per declared finding with the coverage fields the plan names; the run reads and verifies that coverage at that primary home, a named sanctioned crossing under the worktree placement, records fields it cannot verify as unavailable instead of inferring them, and an absent declared input keeps the plan's own stop response.
3. **Do the work in the resolved placement.** For worktree placement, perform all run work inside the worktree, on its own branch. No run work lands in the primary checkout while that worktree exists; the coordination witnesses and transfer steps the consuming duties name are the sanctioned exceptions, and the sanctioned direct-commit crossing per the Direct-commit class paragraph (ordinary ad-hoc work) is likewise sanctioned. For the primary placement, keep run work in the primary checkout under the recorded branch and serialized run claim, with task commits on the verified base branch for personal and pet profiles and on the recorded task branch for a company-profile run (the policy paragraph's company task-branch arm). Progress edits: under worktree placement, make checklist-only or other run-level edits on the canonical run branch/worktree; do not create a worktree solely for a progress edit (see PROJ-607). Under the primary placement, make progress edits on the recorded primary branch within the existing claim and serialization boundaries.

4. **Land under the lock.** Land the result as a squash merge to the base branch under the repository's merge-landing-lock discipline (acquire the lock before the landing critical section, release after it; on lock contention stand down keeping the worktree and branch and report). The worktree-complete landing's only sanctioned composition is the repository-local helper invocation `bash scripts/land_squash.sh land-worktree --branch <source-branch> --expected-tip <sha> --message <text>` run under the acquired merge lock, per the class-ownership paragraph below; the critical-section prose that follows documents failure paths and recovery handling and never authorizes a hand-composed equivalent. When the repository-local helper is absent from the resolved repository, the landing records a deployment gap naming the probed paths and defers; no alternate helper copy or hand-composed fallback is authorized. The landing `--message`'s subject line follows the landing-claim grammar with its prefix drawn from the guard constant `LANDING_CLAIM_PREFIXES` in `scripts/reverse_squash_guard.py`, the recognized prefixes' single source (added 2026-10-26; plan `docs/history/plans/2026-10-23-landing-subject-grammar-end-to-end.md`). The landing critical section is worktree-complete: where the landed result is a plan landing or a plan execution landing, the closeout riders (coverage flip bytes, PLAN-PROMPTS entry deletion (evaluated per the log's shared `Coverage and removal rule` label; one `PLAN-PROMPTS-PRUNE: <slug> -> <witness path>` receipt line per removed entry, gated by the pre-rider prune audit `python3 scripts/check_prompt_log_origins.py --prune-audit --base <merge-base>` per the plans skill's landing closeout, that receipt counting fully removed entries only), archive move, origin fold or deletion, ownership-registry row, the claim-fence scan, a pre-rider gate run rather than a landed rider itself (`check-claim-fence --base <merge-base> --head HEAD` over the landing range per the plans skill's landing closeout)) land as rider commits on the landing branch before the critical section, exactly like the existing archive commit, so the squash commit carries them and the tree-equality gate holds. Conflict-content discipline (added 2026-10-19; plan `docs/history/plans/2026-10-18-landing-conflict-intent-union.md`): every conflict block a merge or rebase inside this landing resolves by union of intents, never by taking one side: a branch-side removal stays removed, a base-side addition stays added, and overlapping edits merge line-by-line keeping foreign lines. The post-resolution re-verification duty follows: after any merge or rebase whose result feeds the landing's gates, whether composed before lock acquisition or inside the critical section, and always before the landing gates next run, each pruned heading or removed span is re-grepped absent and each base-side addition present on the merged tree, the landing's receipt audits are re-run against the post-merge bytes, and the landing record names the re-verification outcome whenever a conflict resolution composed with destructive intents in play (corpus home: project lesson 93 in `docs/maintenance/development_lessons.md`). Worktree-complete class ownership (added 2026-10-11; plan `docs/history/plans/2026-10-11-execute-plan-boundary-reliability.md`): the class's mechanical operation is the helper invocation `bash scripts/land_squash.sh land-worktree --branch <source-branch> --expected-tip <sha> --message <text>` (plus `--expected-base <sha>` whenever the run records a base pin), run under the acquired merge lock; the helper owns the class's gates (tree equality, base freshness, the parentage pre-swap and post-landing invocations, and the two-value compare-and-swap), and every lane of the class routes solely on the helper's outcome contract (the final `OUTCOME:` line per `scripts/OUTCOME_CONTRACT.md`; a run with no final line is a tool error), so the operative blueprints name this invocation instead of spelling the hand recipes; a fail whose output names the reconcile-gate leg is the post-ref-move keep-the-landing arm (the landing stands, the receipt and refusal are recorded, the named re-run command executes), and the class's closeout completes on the valid receipt, the deferred-landing restart path staying reserved for pre-ref-move refusals; a source branch with no merge-base to the base branch (the maintenance execution blueprint's severed-ancestry lane) is outside the helper's class and keeps that blueprint's diff-based-only prescription and its routing vocabulary; the rebase onto the current base tip and the squash merge both execute inside the run worktree, and the primary checkout receives only the final squash commit through one compare-and-swap ref update of the base branch ref; in the worktree-complete class the landing never writes the primary checkout's index or working tree, and staging (git add) in the primary checkout during a landing is a landing-gate violation for every lane (the helper's primary-checkout class below is the carve-out, whose protections are the helper's own pre-refusals and path-exclusive restore); every landing shell pipeline checks and propagates rebase and merge exit codes, and a masked rebase or merge failure aborts the landing before any staging or ref move; a residual lane that must stage paths in the primary checkout verifies each candidate path's disk bytes equal HEAD or are session-owned fresh writes first, through the pre-stage freshness gate (`scripts/prestage_freshness_gate.py`, the Task 1 script's `check` invocation with the session's fresh-write list), and the gate's outcome branches explicitly on the outcome contract: exit 1 (`OUTCOME: fail`) is a refusal naming the paths and defers the staging, never stages; exit 2 (`OUTCOME: indeterminate`) and exit 3 (`OUTCOME: tool_error`) defer the staging the same way and are never read as a pass; a run that ends without its final `OUTCOME:` line is treated as a tool error (stop, re-derive the candidates' state from disk). Tree equality at the squash step: the mode verifies tree equality between the squashed branch tip and the produced squash commit before the parentage gates and the ref move, and the gate outcomes route per the helper's outcome contract (a modeled fail refuses into the deferred-landing path; indeterminate and tool errors stop for re-derivation and are never read as a pass); the ref move never advances the base branch past a divergent tree: a non-empty diff between the squashed branch tip's tree and the landing commit's tree aborts the landing before the ref move, naming the divergent paths and taking the deferred-landing path keeping the branch and worktree; a deliberate non-pure squash says so explicitly at the call site, and silence fails closed. Base freshness at the same checkpoint, before the parentage gates and the ref move: run the reverse-squash guard's `check-landing --source-branch <run-branch> --target-ref <base-branch>` (probe the repo-local `scripts/reverse_squash_guard.py` first, then the deployed `$HOME/.ai-playbook/scripts/` copy; a guard copy absent from every resolved path is a rc 1 deployment gap, never a skip), and refuse the landing on exit 1: the refusal names the stale merge base and every path the landing would delete from the target tip (the witnessed stale-base squash clobber of 2026-10-02), and the landing takes the deferred-landing path (keep the branch and worktree, rebase onto the current base tip, restart the landing critical section); exit 2 is a tool failure: stop and report. Primary-checkout landing class (added 2026-10-03; plan `docs/history/plans/2026-10-03-squash-landing-failure-path-guard.md`): any landing whose squash executes in the base branch's primary checkout (archive riders, ad-hoc maintenance landings, manual recoveries) runs `scripts/land_squash.sh land --branch <source-branch> --expected-tip <sha> --message <text>` under the acquired merge lock, and is never a hand-composed multi-step squash-and-commit sequence; the same conflict-content discipline governs this class: every conflict block resolves by union of intents, never by taking one side (a branch-side removal stays removed, a base-side addition stays added, overlapping edits merge line-by-line keeping foreign lines), and the post-resolution re-verification duty runs before the landing gates next run; the helper owns that class's gates (lock-record verification, base-branch and tip verification, the porcelain snapshot, the staged and dirty-intersection pre-refusals, the path-exclusive failure restore, tree equality, the commit-tree compare-and-swap, and the parentage gate invocations), with `--expected-base <sha>` passed whenever the run records a base pin; before acquiring the lock the lane runs `scripts/land_squash.sh probe --branch <source-branch>` (the containment check plus the `git merge-tree --write-tree` conflict trial, run WITHOUT the lock, mutating nothing), and on a probe fail (a stale base or conflicts) composes the rebase or the conflict resolution in the execution worktree FIRST, so lock acquisition happens only when the probe passes (the short-critical-section discipline; the witnessed post-failure rebase becomes a pre-lock step); a sanctioned rebase ends by refreshing the recorded base pin (the manifest's `run_base` and the claim's `base:` line) to the post-rebase merge base before `land` runs, so the parentage gate's base-pin leg finds no mismatch; a probe indeterminate or tool error stops for re-derivation, never proceeds. Plans-egress archive gate at the same checkpoint, before the ref move: when the built landing commit's diff moves plan files from a plans root (`docs/history/plans/`, `docs/history/backlog/`, with sources at any depth under the root outside their `completed/`, `deferred/`, and `rejected/` subdirectories) into an archive state directory (`completed/` or `deferred/` of either root), sideways out of the source plans root entirely, or deletes them from a plans root at any depth outside the state subdirectories, the landing runs `python3 scripts/reverse_squash_guard.py check-archive --rev <built-commit> --repo <root>` before the ref move and refuses the landing on exit 1 with the same posture as a parentage-gate refusal: keep the branch and worktree, report the guard's named evidence and the sanctioned exits (verify the work and check the boxes, land the plans skill's marked backfill completion record, take the rejected path, or the operator-directed ack); exit 2 is a tool failure: stop and report. `--ack-egress` is passable only on the operator-directed-archive exception: the operator explicitly directed that specific archive in this turn, the direction recorded in the scheduler state file's turn record, and the acked egress path restated in the landing commit's message as an `Archive-egress-ack:` trailer. (The former amend-shape fence at this checkpoint is removed per the closeout-gate demotion program: the guard's ledger entry read zero live catches against the standing base-branch immutability rule - once a commit is reachable from the base branch it is never amended, corrections land as additive follow-up commits naming the amended sha - which stays binding on every lane without the machinery.) Base-branch ref-move integrity fences the landing's ref move: the fast-forward verification before the ref move (`git merge-base --is-ancestor <old-tip> <new-tip>` exit 0 required; a backward move is a deliberate, operator-visible operation recorded in the landing record with both tips and the reason, never a silent landing step; the maintenance execution blueprint's severed-ancestry lane inverse-compare-and-swap rollback is that recorded operation's sanctioned shape), the two-value CAS form (`git update-ref refs/heads/<base-branch> <new-tip> <old-tip>`, both values resolved via `git rev-parse` at move time; a failed old-value check aborts the landing keeping the branch), and the pre-swap empty-diff refusal as a stop-for-adjudication refusal: keep the branch and worktree, record the content-bearing commit already on the base branch as the receipt of record, and end the landing, because an automatic restart reproduces the same tree-identical commit and the deferred-landing path's restart clause does not apply to this refusal (the repair for a message-bearing empty tip already in history is a corrective commit naming the content-bearing sha, never an amend). Resolve-at-use digest rule (added 2026-10-03; origin `docs/history/backlog/2026-10-02-sha-resolution-at-use-fence.md`; witness: the 2026-10-02 fabricated-digest slip, a 40-character digest whose tail was fabricated by hand from a 7-character display prefix and refused by the CAS old-value existence check): every digest this landing passes to a helper invocation or writes into a durable record obeys **resolve-at-use**: a full digest used in a state-changing command or a durable record is produced by `git rev-parse`, `git log --format=%H`, or `git show -s --format=%H` at the moment of use; landing helper invocations pass refs (branch names, `HEAD`, relative forms) rather than literal digests wherever the tool accepts them. Landing-op uniqueness rule: choose exactly one landing operation per source branch (squash merge, merge, or cherry-pick) before applying it; before applying, check ancestry (`git merge-base --is-ancestor` of the source tip in the target, or the commits' patch-ids already present) and refuse the landing when the source commits are already reachable from the target through a previous landing operation, naming the integrating ref (the PROJ-607 witness: the same Task 5 commits applied by cherry-pick and then again by a true merge). Base-branch immutability rule (added 2026-10-03; origin `docs/history/backlog/2026-10-02-base-branch-commit-immutability.md`; witness: the 2026-10-02 18:09 amend of a peer's landed tip, a peer session amending the base-branch tip another session had landed four minutes earlier): once a commit is reachable from the base branch it is never amended; corrections land as additive follow-up commits; amend is legal only inside a session's own unlanded branch before the landing critical section. After releasing the lock, reconcile every live checkout of the base branch per the **Post-landing reconciliation implementation** below; the landing is not done until that reconciliation verifies completion, and an unverified refresh does not count as done.
5. **Transfer the artifacts out and verify.** Before any cleanup, move all run artifacts (review staging documents, stats sidecars, the certification seal file, telemetry, and the Phase 4 metrics archive copy under the resolved `{metrics_dir}`) from the worktree back to the primary checkout and verify them present there. Gitignored run artifacts never ride the branch commits, so the primary checkout is their only durable home. The **Transfer-out-and-deletion implementation** below owns how. A run parked before its closeout with its worktree still standing mirrors the gitignored artifacts its run created or modified from the worktree to the primary checkout's run homes, never a blanket sweep and never overwriting a newer primary-home file, byte-equal copies verified and a failed copy reported, never silently dropped, so the resume contract survives worktree loss.
6. **Delete only after verification.** Delete the worktree and its branch only after step 5's verification passed; the same implementation owns the deletion gating. Archival shape: on a host with managed worktree archival, archive through the managed workflow first so the recoverable snapshot is preserved; verify no live run names the checkout before archiving: no execution claim or fresh foreign claim or recorded witness may name the worktree; when the managed archive refuses over an active-session pin, use the host's supported unpin or move control and retry the archive, never substituting raw worktree-directory deletion for a refused managed archive; delete the local branch only after step 5's verification passed and ancestry confirms the branch's commits are reachable from the landing destination. Squash arm: after a squash landing, source commits are not ancestors by design, so the deletion proof is the squash proof instead - the tree equality between the run branch's tip and the landing commit, computed at the landed-commit verification moment when both refs exist, or re-derived later by scanning the landing destination's history for the commit whose tree equals the branch tip's tree (the branch still exists pre-deletion, so the comparison is live); the arm deletes only the exact run's source branch (the identity block's run_branch, or the recorded branch for runs predating the identity block) and only when no live task or process names it.

**Provisioned-worktree adoption (beside lifecycle step 1):** if the session already runs inside its dispatch-provisioned ad-hoc worktree, adopt it instead of creating a second: verify it is a linked worktree per the Linked-worktree detection sentence below; that it sits on a branch that is not detached and named per the run's Phase 0 convention (execution runs), or the branch the dispatching payload ordered the run to work on (authoring runs), verifiable by being inside that ordered worktree, or a branch otherwise recorded by the dispatching payload's witness; that it carries no tracked dirt (`git status --porcelain --untracked-files=no` empty); that no fresh foreign claim or recorded witness names the same worktree for another live run; that the worktree's pre-existing gitignored state (the facts file, the reviews directory, the review-certs seal directory) is absent or byte-identical to the primary checkout's sources, standing the run down on anything else (a stale or planted facts snapshot passes the transfer-in's noclobber copy untouched, and the unconditional reviews copy would clobber a newer prior run's staging docs); and that the run's gitignored inputs are resolvable from the primary checkout for transfer-in (the transfer-in step runs after adoption, so resolvability, not presence, is the precondition). A failed adoption check stands the run down under the same fail-closed creation stand-down. Linked-worktree detection: the adoption check, the transfer-out fence, and the tracked-dirt fence use the predicate that a session runs inside a linked worktree exactly when `git rev-parse --git-dir` and `git rev-parse --git-common-dir` resolve to different paths; the transfer-in fence uses its .git-is-a-file equivalent.

**Stale-checkout discriminator (before any dirt is classified):** a suspected-modified tracked file is a stale-checkout artifact, never an edit, exactly when its blob hash equals that path's blob at an ancestor commit while HEAD has advanced past that ancestor: compute the file's blob (`git hash-object <file>`) and compare it against the path's blob at ancestor commits (`git rev-parse <commit>:<path>` over `git log --format=%h -- <path>`, skipping commits where the path does not exist, a deletion or rename-source commit, rather than treating the failure as a match or a tool failure). An ancestor-blob match means restore-and-record: restore the file's worktree bytes from the base tip (the index is never written by this arm), record the restoration, and never commit the stale bytes; the file's mtime predating the commits it reverses is a supporting signal, not the gate. The index arm is wholesale: when a checkout's index sits byte-identical to a pre-landing tree (`git diff --cached <pre-landing-tip>` coming back empty while HEAD has advanced past the pre-landing tip), the staged state presents a reversal block of the whole landing. The remediation is gated per path, and this block is the rule's single home: restore a landing-changed path from the base tip (`git restore --source=<base-tip> --staged --worktree --` that one path) only when its index AND worktree bytes both equal the path's blob at an ancestor commit (the pre-landing tip's blob or any older ancestor), or when its worktree bytes equal the base tip while its index bytes equal an ancestor blob (a half-synced residue; the restore clears the index without changing the worktree bytes), or when its worktree bytes equal an ancestor blob while its index bytes equal the base tip (the wholesale residue a mixed reset leaves; the worktree-only restore clears it and the index is untouched), re-reading both byte states immediately before the restore in any arm; a path whose bytes match no ancestor blob in either state is a genuine modification and a named block, never restored; record the restoration or the block, and never commit, never blanket-reset.
