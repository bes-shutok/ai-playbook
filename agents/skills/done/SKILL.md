# Done

Run learn to capture lessons from this session, then commit all uncommitted changes across all repositories touched during the session. The closeout's mechanical spine is three runner invocations: `done_run.sh setup`, `done_run.sh commit`, `done_run.sh finalize`. The agent's inference lives in learn and in the staging decisions the commit runner surfaces; every mechanical decision inside those scripts is fail-loud with named errors, and each contract this text does not restate is owned by the composing script's usage text or one of its named stages.

For dated reports or any request containing relative dates such as "today", "tomorrow", or "next Monday", verify the current date from the system environment at the start of the task and derive the target date from that value. Do not infer the date from conversation timing or a previously drafted filename.

## Repository scope ledger

Before Step 0, inventory every repository touched by the task from tool activity, the user's explicit scope, and repository status. `done` applies to each applicable repository, not only the repository containing the latest artifact or the current working directory. Process each project repository independently through the runner sequence below with its own lock, then run the shared skills and docs/facts commit checks (the commit run's side-repo walk). Never report completion while a touched repository remains unverified or uncommitted.

## Invocation (read first)

`done`, `learn`, and `docs-branch` are **markdown skills**, not shell commands or binaries. There is no runner under `~/.ai-playbook/runtime` and no `/learn` executable.

- **Do not** run `done`, `learn`, `docs-branch`, `SKILL.md`, or `/learn` as shell commands.
- **Do not** delegate this workflow to a Task/subagent that tries to exec a skill path.
- **Do** read each skill file (`~/.agents/skills/<name>/SKILL.md`) and execute its steps in **this** agent session using normal tools (shell for scripts, Read/Write for skill logic).
- **Edit discipline:** read-before-edit is mandatory per file per session; Read a file in this session before this workflow's first edit to it, and re-Read it after any external-change signal, including a peer commit, a plan fold, a formatter run, docs-branch operations, a sweep-gate operation, or a `modified since read` failure; on such a failure, re-Read the file before retrying the edit.

**Workflow continuity:** this skill executes as one continuous sequence: `done_run.sh setup` (Step 0) → learn (Step 1) → `done_run.sh commit` (Steps 2 and 3, which own the one landing sweep, the docs-branch sync at its today position between sweep and landing commit, the single landing commit, and the Steps 4 and 5 side-repo walk) → `done_run.sh finalize` (Step 6) → the report (Step 7). The invoking boundary declares its class with `--boundary-class per-task|final-closeout` (default final-closeout): a per-task boundary runs the landing roster minus the primary-checkout inspection and skips the docs-branch sync, both final-closeout legs (the done runner's usage header is the canonical split); the review-artifact migration runs at every boundary. After each step or skill invocation completes, immediately proceed to the next step without stopping or waiting for user input. Only stop if a step fails, produces an error, or requires user clarification. **Exception:** Step 0 uses a short agent wait (`DONE_LOCK_AGENT_MAX_WAIT_SECS`, default 90s); on timeout return `blocked` with lock `status` instead of polling for hours. **An empty project working tree is not a stop condition:** still run setup, the commit run (it no-ops the landing commit when nothing is staged), and finalize, and finish with Step 7.

## Step 0: Acquire project done lock and set up the run (`done_run.sh setup`)

Parallel agent sessions on the **same git repository** must not run learn, docs-branch, or project commits at the same time; the done lock precedes learn and every commit step. **Review-candidate classification:** before acquiring the lock, classify the staging corpus whenever this run may face prior-session staging docs: which candidate review paths this run owns (to pass as `--owned-review` claims) and which stay foreign (to pass as `--foreign-review-from <file>` or per-path flags). The sweep-gates lib's classification emission (its writer's `--emit-foreign-candidates <file>` flag, run as its own bare command under `{tmp_dir}/done-session/`) enumerates the unclaimed candidates read-only; the emit-only invocation is reachable before the marker exists - in a fresh done-session directory holding no confirmable run-start marker it still enumerates and writes the file (the summary names the repo root the enumeration ran against), so this classification genuinely runs pre-lock, and the partial-setup receipt path (marker write, then one `--foreign-review-from` write after the lock) remains the fallback for any other refusal class; every manifest-writing invocation still requires the marker; a run that owns no staging doc of its own may bulk-mark the remainder foreign with `--claim-none` (it conflicts with `--owned-review`).

From the project git root, run setup with the classified claims:

```bash
done_run.sh setup --owned-plan <plan> --owned-review <staging-doc> --owned-path <start-dirt-path> --foreign-review <peer-candidate>
```

Setup composes, in order: the rearm-on-touch echo (the advisory posture above), the done-lock `wait-acquire` with the short agent wait, the runtime-helper drift advisory, the worktree residue sweep, the run-start marker write, and the run manifest write bound to that marker. Every refusal is the composed command's own named error, plus the relocated one-for-one setup refusals (the empty-echo abort and the partial-setup classification stop). The interrupted-run report's root match (`root_matches_current_repo=yes`) is a repository identity fact, not process or lock liveness; the report's lock column beside it and the done-lock `status` command carry liveness.

On success setup prints one status line plus eval-able exports (`DONE_LOCK_DIR`, `DONE_LOCK_TOKEN`, `DONE_RUN_MARKER`, `DONE_RUN_MANIFEST`, `DONE_RUN_ID`). Retain them in session context: finalize runs in a later shell whose env is fresh, and the release path never sources the session fence file. To keep the from-holder release arm producible, pin the acquire to a long-lived process you control (`DONE_LOCK_HOLDER_PID` plus `DONE_LOCK_HOLD_PIN`); pinning to a shared supervisor voids that arm's ancestry guard. On a blocked acquire, run `status`, report the holder evidence, return `blocked`, and do not commit; `stale-clean` is the explicit operator escape only. **Run placement:** done compute steps may run in any checkout (the done lock keys per checkout); the corpus surfaces (the reviews-corpus read, the ad-hoc-worktree migration destination, the docs-branch sync, the `{tmp_dir}/done-session/` artifacts) resolve the primary checkout regardless of where the run executes, and the primary checkout is the default dispatch placement; a done closeout consults the project worktree policy per the Worktree-first standard's policy paragraph (agents/skills/execute-plan/SKILL.md) before provisioning or adopting any worktree, and no policy ever skips the transfer-out ordering. On a project resolving the policy paragraph's primary resolution, the consult routes every session's work to the primary checkout and the immediate-commit rule applies: each change is committed right after the change is made by a plain path-limited commit of the session's own paths, and the done skill runs once at the end of the session's work (its learn and other closeout steps fire once rather than per change; a minutes-scale closeout is acceptable). A subagent or worker reaching its work boundary under the primary resolution returns its learnings and the issues it saw to the parent session in its result, editing no tracked corpus and committing nothing; the parent's single end-of-work run captures those learnings through the learn skill and commits the corpora, and routes issues needing follow-up work through the done boundary's candidate emission or an operator-directed investigate run; the full done closeout (docs-branch persistence, run manifest, done-lock release) belongs to that parent run alone. A plan-lane run under the primary resolution keeps its per-task done boundaries, their reviews, and their commits; only the learn capture and the full closeout run once at the run's end. **Baseline-dirt classification:** when the porcelain baseline shows dirty tracked paths, the commit run's stale-checkout adjudication classifies them mechanically; a hand-run of `scripts/revert_set_classifier.py classify --repo <repo-root>` answers in the same outcome contract, and the classifier's own usage text is the procedure of record.

**Direct-commit route:** when the direct-commit class is engaged, the done run executes in the target checkout, and the run manifest claims the session-owned declared paths as owned paths; the commit stage's existing explicit-pathspec staging applies unchanged. Every landing sweep gate runs unchanged, the consult-and-stand-down discipline runs as the standard's direct-commit class paragraph (agents/skills/execute-plan/SKILL.md, Direct-commit class (ordinary ad-hoc work)) prescribes, and eligibility and destination rules are owned there, referenced here, never restated; the consult is a read-only `scripts/done-lock.sh merge-status` read, not lock management, leaving the runner-owned acquire-and-release spans untouched.

## Step 1: Run Learn

Invoke the `learn` skill now to extract lessons and update the documentation corpus before committing. Learn may commit its own skills-repo artifacts during this step (its Step 1.8 backlog items and skill-placement edits); that is expected and does not double-commit, because the commit run's side-repo walk sees only non-learn leftovers. When execute-plan's parent-executed done boundary invokes learn directly with the implement log, learn's capture contract applies unchanged; the parent executing the boundary runs the same runner sequence without the sub-agent.

Learn-owned commits are recorded by receipt: immediately after learn, write the `committed: <sha> <subject>` receipt lines learn printed to `<tmp_dir>/done-session/learn-receipts-<run_id>.txt`, and pass that file to the commit run as `--learn-receipts-from <file>`; the commit subcommand resolves each reported sha in the run repository and appends only same-repository receipts to the run's owned-commits ledger, skipping an unresolvable cross-repo sha with a one-line note, so the landing sweep's doc-registry gate observes them.

**If `learn` reports a blocked state** (Step 6.6 user-corpus violation: a strict-tagged `UL#N` lesson is missing its `**Principle:** Family X` tag, or the gate script returned non-zero on the adopted corpus), release the lock via Step 6 and return `blocked` WITHOUT proceeding to the commit run. `learn` is invoked here as a SKILL (a sub-procedure), so the gate's block decision lives in `learn`'s Step 6.6 text and propagates here through `learn`'s returned state. The operator fixes the user corpus out-of-band before the next `done`, branching on the validator category each listed `UL#N` carries (`duplicate` | `untagged` | `multiple-tags` | `invalid-family`, classified in that precedence order by `lessons_index.py`); the recovery is operator-driven, never renumbering lessons or rewriting cross-references itself:
- `duplicate`: inspect the colliding headings, choose a unique identifier for the colliding lesson, update the same-corpus references to the renumbered id by hand, then re-run the validator (a duplicate is a heading collision, not a tagging case).
- `untagged` / `invalid-family`: classify the listed `UL#N` via learn/generalize, or run `lessons.py adopt --tag-unclassified <user_corpus>` manually.
- `multiple-tags`: classify the lesson first, then remove the competing family tags so exactly one `**Principle:** Family X` line remains outside fenced blocks, then re-run the validator.

**After learn completes, immediately continue to the commit run.** Do not stop or wait for user input; the workflow is continuous and all steps execute in sequence.

## Step 2: Preserve Gitignored Docs and Instructions (inside the commit run)

The commit run owns the docs-branch sync at its today position: the one landing sweep gates the staged set first, then `bash scripts/docs_branch_sync.sh` publishes the review docs, then the single landing commit carries work plus lessons. When the session runs in an ad-hoc worktree, the commit run first migrates the run's review staging docs and session logs to the main checkout (`worktree_closeout_migrate.py migrate`) and never removes the worktree before its gitignored review artifacts verify present in the main checkout; the gated removal check `python3 scripts/worktree_closeout_migrate.py gate-removal --plan <plan> --target <primary> --worktree <worktree>` passes (`OUTCOME: pass`) before any removal, and a refusal names what to resolve and re-run. The gate-removal claims set names each claimed review record's `.stats.json` sibling alongside the record path, and the gate refuses teardown while a worktree-side sibling would be destroyed by the removal (the sibling exists in the worktree staging home and is absent from the primary reviews home), so transfer the sidecar with its record before re-running the check. The migration destination is a corpus surface, not landing staging.

**Explicit sync deferral (availability-checked):** an explicit docs-branch sync deferral (an operator direction recorded for the run) does not by itself block the requested local commit when the owned-review availability check passes: the manifest's owned-review claims verified present under the primary reviews home, the same presence verification the migration and removal gates already perform. Record the deferral in the session notes, run the availability check, and when it passes proceed with the docs sync remaining its own later step; when the check fails (a claimed review missing from the primary reviews home), the sync, or the migration that fills the home, runs before the commit, because the deferral never overrides a missing deliverable.

The canonical `scripts/docs_branch_sync.sh` runner reads only the fixed review root and the facts-resolved review and metrics roots, validates them before traversal, prunes excluded or expired branch paths, and preserves prior docs commits; it uses one repository-level temporary-index and commit-tree backend with compare-and-swap regardless of `worktree_policy`, and preserves the active checkout and index. **Runner-owned merge-lock spans:** the worktree migration and the docs-branch sync are shared-checkout critical sections whose repository-keyed merge lock (the `merge-*` family of the same lock script; canonical semantics live in the `scripts/done-lock.sh` usage text) is held by the mutating runners themselves, never by this skill: each acquires inside its own process with a bounded wait, parses the lock exports in-process so no lock env var ever enters chat context, releases in an always-run finally, and prints one `merge-lock: held <N>s` line at release. Carry no lock management for these steps: never run the lock script's merge subcommands by hand here, and never copy lock exports between shells. **Runner-refusal posture:** when a runner refuses its merge-lock acquisition it fails loud with the holder evidence and leaves the docs ref and the checkout byte-identical; return `blocked` keeping every artifact of the run, release the done lock per Step 6 before reporting, and then apply the bounded responses (a bounded retry of the same runner, skip-with-report, or park-for-operator); never bypass a held lock and never hand-release another process's hold.

After the sync, verify gitignored files are still on disk (`git check-ignore -q` per candidate path) and that untracked WIP survived; restore any missing path from the docs orphan branch before committing.

## Step 3: Commit Uncommitted Changes (`done_run.sh commit`)

```bash
done_run.sh commit --stage <owned-path>... --subject "<why-first subject>" \
  [--learn-receipts-from <receipts-file>] [--revert-formatting <path>...] \
  [--side-commit <repo-path>...]
```

Declare every live edit this run intends to land via `--stage`, enumerated from a fresh git status rather than rebuilt from step reports, including the surfaces the learn step authored after setup (the lessons corpora, tightened backlog rows); the declared set reconciles into the landing sweep's ownership behind the primary-checkout shape guard. The shared record-only corpus is the exception: never declared, never claimed for staging, never committed - leave it unstaged; the allowlist keeps its unstaged dirt out of every refusal.

The subcommand owns the collapsed commit ladder in this order: stage by explicit pathspec from the declared `--stage` set (gitignored paths reported, never staged; never a directory-wide add), append staged plans-root paths to the deliverables file, the stale-checkout adjudication (ancestor-blob debris restored from HEAD and reported, never staged; a session-claimed path is reported for confirmation instead), the cached-diff guard (a declared staged path whose content equals an ancestor vintage is a leaked revert; the runner stops, nothing commits), the dirt regression gate, the staged-scope guard, the foreign-dirt disposition ladder (a manifest foreign claim attributable to a live peer aborts the landing; other unclaimed baseline dirt is reported and left unstaged for the next run), the formatting-only candidate list (no revert without `--revert-formatting`), the unused-import pass over touched lintable paths (skip-note when no linter resolves), the lesson-scope audit when the lessons corpus is touched, the learn-receipts ledger appends, the landing sweep (`done_sweep_gates.sh landing`, the closeout's one sweep run: the retained roster with plans-archive-twin deduped to one slot and instruction-size and description-length in warning posture), the docs-branch sync (Step 2), the registry digest arm, the reverse-squash check-staged, and exactly one landing commit with the owned-commits ledger append fused to it (`git commit ... && git rev-parse HEAD >> ledger`). In that sweep, the `plans-root-claim-fence` gate reports an unclaimed plans-root deletion as `claim-fence-warning:` lines that stay report-only on an exit-0 child, never refusal blocks, and the class's promotion to refusals is governed by the `unclaimed-plan-deletion-fence` machinery registry row.

**Dangling-change stop:** at the done boundary, dangling session-owned work product (modified, staged-but-uncommitted, or untracked files the session owns) is a named stop listing each path, distinct from the foreign-dirt disposition ladder above, whose predicate stays other sessions' paths and never the session's own work product; the session resolves it by committing the listed paths or explicitly standing down with the list recorded. (Motivating shape: the five-day worktree residue.)

**Direct-landing advisory (warning-only):** when the run's landing is a direct landing (this run's landing commit made in the primary checkout itself, not a worktree run's transfer-out squash landing) whose diff exceeds the direct-commit class bounds (a behavior, API, or schema change, or more than four files), the run prints a named advisory citing the direct-commit class and the worktree lane; it never blocks the landing and moves no exit code, and under the immediate-commit rule it measures the session's cumulative diff of its own committed changes when no single landing commit carries them. (Incident 9a046452e: an oversized behavior-bearing direct landing past the direct-commit class, witnessed 2026-10-16 in this repository.)

The agent's confirmation duties around the script: one line confirming the revert list when formatting-only candidates are named; one line confirming the lesson-scope audit findings (a duplicated full rule stops the commit for the user's classification; the placement receipts from the learn skill's capture step remain the placement evidence); one confirmed commit action per dirty side repo (Steps 4 and 5). **Reverse-squash arm:** the script runs the guard's `check-staged` immediately before the landing commit; exit 1 means the staged set carries a refusing reverse-squash signature (an archive-dir egress deletion or rename, or a reviews-home egress addition under the deny set .ai-playbook/reviews/): unstage the refused set and rebuild it from the intended edits, never committing the refused set; a diffstat-mirror finding of a landed commit is reported-not-failing, and the repeatable `--ack <sha>` suppresses a named mirrored commit's warning only when the deliberate-revert intent is recorded in the session notes; archive-egress and reviews-home findings still refuse and are never ackable.

**Commit message:** the script builds the why-first message from `--subject` (story key derived from the branch, plain descriptive subject without a ticket prefix when the branch has none; ask only when the repository convention is unclear). The subject leads with the why; when it cannot carry the reason, put the short why in `--subject` and let the body lines carry notes. Never add `Co-Authored-By:` trailers or use `git commit --trailer` for agent attribution. **Resolve-at-use digest rule:** any full digest this run writes into a commit message, receipt, or durable record is produced by `git rev-parse` at the moment of use; committed witness lines name repo-relative paths and dates, never a landing digest. **Base-branch immutability:** a commit reachable from the base branch is never amended; corrections land as additive follow-up commits; the script reports an amend attempt of a base-reachable commit as a warning line, never a refusal.

## Step 6: Release project done lock (`done_run.sh finalize`)

**Always run Step 6 before Step 7, on every exit path including failures** (a waiting parallel done resumes only after the release). Before finalize, apply the run's session-level conditional duties (the runner does not execute them):

- **Review-thread closure:** when a review-thread marker (a `docs/tmp/review-threads/<session-slug>.json` per `receiving-review`'s marker duty) whose recorded session identity matches the CURRENT session exists, run `python3 scripts/review_thread_gate.py --marker <path>` with an inventory source; exit 1 lists unclosed threads: report blocked, release the lock per this step, and do not report completion. A session with no marker, or a marker whose recorded identity does not match the current session, is unaffected; human-authored threads are never auto-resolved.
- **plans-root liveness (a session-level conditional gate the runner does not execute; apply it in-session per its bullet below before continuing):** run `python3 scripts/check_authoring_plans_liveness.py --repo <repo-root>` (repo-local copy first, then the deployed home copy); exit 1 names a stranded untracked plan file: report blocked and resolve it through the authoring-claims registry (a live peer's claim refreshes by its own heartbeat; a truly stranded file is adopted or removed by its owner, never deleted by this run).

Then run finalize:

```bash
done_run.sh finalize
```

Finalize composes the release ceremony: the resumable-closeout checkpoint refresh (a no-checkpoint refusal falls back to create-then-refresh; an already-finalized manifest skips the refresh arm), the run manifest finalize (a missing manifest is a one-line note and never blocks the release; any other non-zero exit aborts with the named error after the releases run, never stranded and never masked), the checkpoint remove, the done-lock release, the merge-lock release when a hold survives, and the status-free verification. **Exports lost (the `--from-holder` arm):** when `DONE_LOCK_DIR`/`DONE_LOCK_TOKEN` are lost mid-run and re-exporting from session context fails, `done_run.sh finalize --from-holder` releases through the lock script's metadata-sourced arm under its own recorded guards: the hold was pinned at acquire (`holder_pinned=1`), the recorded hostname still matches this host, the recorded holder is verifiably alive with exact identity (a dead holder routes to the orphaned arm), the holder is not pid 1, and the calling shell's process tree descends from it; every refusal names the failed gate. The env-token release stays the default path. When release fails, read it through the outcome contract, run `status`, and never source the session fence file to fix env; a verified-dead holder is reclaimed by the next acquire, and `stale-clean` stays the explicit operator escape.

Finalize also assembles the report inputs (the landing summary from the run's owned-commits ledger and the report-only missing-review-record scan over the archived plans: a referenced review record absent from the live reviews corpus is a reconstruction duty reported in Step 7 with a witness note naming the citing plan and the missing path; never fabricate record content, never block the run, never delete anything) and runs the advisory appends, never blocking: the guard-liveness ledger append (pass each firing as `--guard-firing <gate>:<kind>:<evidence>[:<note>]`, kind `catch` when the firing stopped real harm, `incident` when it blocked or misdirected valid work, `override` for a user-directed proceed over a tripped deferral-class refusal), and the landing-cost telemetry append (one JSON line to `{metrics_dir}landing-costs.jsonl` when this run landed work in the project repo; **The never-blocking posture: telemetry is analysis data, never correctness evidence - a failed append (read-only checkout, missing directory, any write error) is reported in this step's outcome and the closeout continues; no step, gate, or landing ever refuses or stalls on a missing, failed, or incomplete record.**)

## Step 7: Report outcome to the user

**Never end `/done` silently after diagnostics.** Always send a short summary:

- Project repo: commit hash(es) created, or **working tree clean** at `HEAD` (include `git log -1 --oneline`).
- Skills / shared docs repos: commits created or none.
- Lock: confirm `status` shows **free** after Step 6.
- If `blocked` at setup, learn, or the lesson-scope audit: state why and what the user should run (`stale-clean`, fix corpus, classify the duplicated lesson, retry).
- Turn-end reason: in the run's final report, when the session executed under a standing queue-drain directive (recorded in the orchestrator's handoff context or the session's standing directive to execute plans), the report states the turn-end reason as a guard fire (a quota pause or near-reset with the Budget gate's constants on the interactive lane, a landing-gate hold reported by `scripts/done-lock.sh` merge-status, a lane hold from the scheduler guards, provider rate pressure with its structured rate-limited end) or an empty queue (no digest-intact open plan remains); a user interrupt or explicit abort is always sanctioned as well, and a request for the user to confirm starting the next plan is never a sanctioned turn end under such a directive.
- Record-bearing claim re-derivation: before this report states a record-bearing claim (a fact statement about repository state written into a durable channel whose wrongness outlives the session), re-derive it with two independent commands (an existence claim via a filesystem probe plus a git probe; an absence claim via a working-tree grep plus `git grep` at the tip commit); a cross-check mismatch stops the record write until resolved.
- Base-branch immutability in reported commits: a commit sha this report cites is expected to stay reachable and immutable; an amend of a cited commit surfaces as a cross-check mismatch under the re-derivation bullet and stops the report write.

When the session used a passive review workflow, distinguish local finalization from review finalization: report the disposition of every tracked thread before reporting completion; a local commit does not replace a required reviewer reply, and a reply does not imply the branch was pushed. Keep push authorization separate from permission to reply to review feedback.

### With `release` skill

## Rules

- Always run setup (Step 0) before learn or any project commit step; always run finalize (Step 6) and this report (Step 7), even for "just commit" or empty working tree runs.
- Always run learn before committing; lessons must be captured first. Never skip learn even if the user says "just commit".
- Invoke `docs-branch` (through the commit run) for all docs/instructions preservation; do not inline the stash or branch logic here.
- Never remove an ad-hoc worktree before its run's gitignored review artifacts verify present in the main checkout; the docs-branch sync runs where the on-disk corpus is canonical (the main checkout after migration).
- Never stage or commit a file that is gitignored, even if it appears in `git diff` (it was previously force-tracked). Use `git rm --cached` to remove it from tracking; do not commit it on the feature branch.
- Stage by explicit path only; never a directory-wide add. Never commit a new or substantially edited project lesson whose scope audit has not passed; never skip a session-touched, non-gitignored project lessons corpus just because it is untracked or already synced to the orphan `docs` branch.
- **Visible blocking questions:** any question that blocks the work is visibly delivered before the workflow depends on an answer: printed in the run output and recorded in the session notes; a question the run can answer from records is answered from records instead of asked.
- Never add `Co-Authored-By:` or `Co-authored-by:` trailers or use `git commit --trailer` for agent attribution. Never use `--no-verify`. Never commit secrets, PII files (`.env`, credential files), or personal/org-specific information into public repositories.
- Never hardcode personal paths, org domains, or project-specific identifiers in skill files; externalize those to facts documents. Portable workflow policy and numeric thresholds stay in the skill (see `learn` Step 2, Facts vs skill configuration).
- If the branch has no story key, use a plain descriptive commit message on branches such as `main` or `master`; ask only when the repository convention is unclear.
- No silent gate-satisfying rewrites of human-authored prose: when a gate or validator fails on prose the user authored, do not rewrite the passage wholesale and do not silently substitute its wording, punctuation, or structure. Make only the narrowly-scoped edit the gate actually requires, only inside the lines this run's own change touches (the hunks this run edited, not merely the same file), and report the edit in the return or commit summary; when the failures reach untouched user prose, or no minimal edit exists, stop and surface the conflict for the user to adjudicate (returned-for-ask shape: name the gate, the failing lines, and the options). Whole-file rewording of user-authored text is out of scope for any worker, always. Restoring the user's original text outranks a green gate. Text you authored this run is yours to fix freely; this pin never applies to it and never excuses stopping for routine fixable failures.
