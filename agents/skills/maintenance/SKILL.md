# Maintenance

Unattended maintenance loop for this repository. One run of this skill is a **scheduler turn**: survey the work surface, apply the guards in fixed order, decide per lane, schedule at most one execution and one authoring child, and update the state file. The turn is designed to run from a recurring automation with standing pre-authorization: never block on questions, decide and proceed.

This skill stays runtime-agnostic. Runtime-specific scheduling primitives and recipes live in the runtime overlay `agents/skills/maintenance/zcode.md` (load it only when the runtime is ZCode). The two child blueprints the turn fills and schedules live in `agents/skills/maintenance/prompt-templates.md`.

## Cycle gate (durable pacing between cycles)

An authoring or execution session running under a standing user directive whose text gates the next cycle on a user-side action arms `authoring_cycle_gate` at every cycle closeout (the State file field paragraph owns the shape). The gate exists because a harness auto-compaction and a user-run compaction are indistinguishable from inside the resumed session: both arrive as a summary continuation, and the harness resume instruction points the resumed turn at the recorded next step. Resumed-turn rule: a continuation-summary resume (the session's latest context arrived as a machine summary rather than a user turn) that finds the gate armed performs due checks plus a readiness report only, re-running the survey-class reads, reporting queue and backlog readiness, and stopping without starting a new authoring cycle or executing the next plan; a real user message in the resumed context is the only thing that starts the next cycle, and the same explicit directive clears the gate (the field paragraph's clear trace). Conservative default: gate armed and no new user directive equals report readiness and stop. Sessions on repos with no scheduler state file are out of scope (the file's existence is the loop's own run-here predicate). The resumed-turn rule governs continuation-summary resumes (the session's latest context arrived as a machine summary), while an in-session interrupting task is a real user message governed by the Step 3 Interruption-resume rule, whose re-entry still passes through this gate when it is armed. The readiness report names the live loop - the session's bound mode, the gate field's recorded directive wording, the `cycles_completed` count, and the next step per the mandate's lane order (the alternation for `dual`) - instead of generic queue readiness; the conservative stop is unchanged. When reporting Cycle gate readiness, include the plan title, the five-line gist (Title, TLDR, Before, After, Edge cases), and the declared execution budget for the authored plan; follow the source mapping and budget rules in `agents/skills/plans/SKILL.md`. Include that same gist and budget in the final report. This content is advisory only and never blocks a lane or stops the loop (directive D-6 remains intact).

### Authoring plan gist reports

Before the first `review-plan` round, report the plan title, five-line gist (`Title`, `TLDR`, `Before`, `After`, `Edge cases`), and execution budget using `agents/skills/plans/SKILL.md`'s source and budget rules. Repeat the gist and budget in readiness, final, and in-session closeout reports. Advisory only: it never blocks a lane or stops the loop (directive D-6).

## Loop modes

Mode binding. The session classifies its own directive at launch; the bound mode lives only in the session's context, never persisted as a scheduler-state field, its only records being the per-turn mode token and the report line. The current run's mode vocabulary classifies auth, author, authoring wording as author mode; exec, execute, execution wording as exec mode; and both, dual, alternation wording as dual. A direct manual ruling also sets the current run's mode. When no keyword or manual ruling classifies the run, default to dual. Survey, survey-only, and stand-down wording routes the session through the Project-class guard paragraph's survey-only resolution with precedence over any competing mode wording (survey and stand-down wording outrank both-lanes wording), so a survey-worded session inherits the guard's resolution, the class-guard-survey-only token family, and the visibility format. Both-lanes wording outranks single-lane tokens in one payload (an exec+author mandate resolves dual). The queue-depth token and the corpus freshness rule read both rolling logs per Task 3's re-aims. The session records the binding in its decision channels, and each turn's `decision_reason` carries the token `mode:<author|exec|dual|survey>` beside the lane decisions.

Mode enforcement. The per-lane decision reads the session's bound mode first: author mode resolves D1 and D4 to D3 with the mode recorded in that lane's `decision_reason`, exec mode resolves D2 to D3, dual is inert; this paragraph is the Step 3 enforcement's source of record from Task 2 onward. The paragraph also reads the state file's incident `survey_only` flag as an operator-set all-lane stand-down input each lane decision consults, and an operator-directed turn receiving a lane-stop or lane-open directive writes the flag via one targeted field edit in that turn, before the turn ends, beside the decision record, the stop write recording the `decision_reason` token `survey-only-stop` beside it; a lane-stop directive whose wording scopes to one lane resolves explicitly: the turn either writes the flag with the over-broad all-lane consequence recorded in `decision_reason` and named in the turn report, or refuses the flag write and surfaces that only an all-lane stop persists across sessions. The flag's stop constrains successor chains beside the per-lane reads: a completing child's successor-dispatch duty reads the flag from the state file it already read and chains nothing while the flag stands, the successor target waiting for the next scheduler turn's reader path, which consults the same flag, so an operator lane stop told to one session still binds the sessions after it. The targeted edit rides the sanctioned-writer enumeration's existing scheduler-turn class (no ninth writer class), and the Step 6 carry-forward enumeration gains `survey_only` (the flag is written outside Step 6 by this operator-directed targeted edit, so the rewrite must carry it; Task 2's carry-forward edit lands the enumeration change). The flag remains an undocumented operator surface whose only contract is this reader text: no schema paragraph is added for it and the machinery registry stays untouched.

Starvation switch. The per-mode starvation predicates: author mode is starved when the authoring lane's inputs are empty per D2's selection rules, the rolling-log readiness, and the investigate leg's set; exec mode is starved when the execution lane's candidate set from Task 3 is empty. The switch lifts the bound mode's exclusion for the turned work and records `mode-starved-bypass:<lane>` in `decision_reason`; the effort pairing follows the switched work (where the runtime fixes effort at launch, the switched turn records the effort mismatch in `decision_reason` and the escalation rides the next payload rather than an impossible mid-run change). The switched turn runs the other lane's own machinery: for the execution lane, D1's plans-only selection (the ad-hoc arm and EXEC-PROMPTS entries stay gated to sessions bound exec); for the authoring lane, D2's selection rules, and the duties whose standing Mode-enforcement exclusion would otherwise hold the switched work (the Rolling prompt log duties' standing exclusion among them) read the recorded `mode-starved-bypass` as lifting that exclusion for this turn. Per the Mode binding paragraph, the bound mode stays session-local (never persisted, never read back).

Mode visibility. Every maintenance session's opening report and closing report names its bound mode in one line (`mode: <author|exec|dual|survey> (session)`), the closing report also naming the selected next target's path when one was selected; the Cycle gate readiness report names the session's mode beside the live-loop fields.

Project-class guard. The pet-project gate above the modes: the facts document's confirmed `project_type` decides, mapped pet to `personal`, company to `company`, and a missing, invalid, or unconfirmed type to `undeclared` (an unconfirmed type persists no `project_type` value), and the survey's Priority-profile resolution records the profile class, so the guard reads survey output, not a second read. A company-profile or undeclared project resolves both work lanes to survey-only in every mode, and the guard outranks the mode machinery; an interactive launch asks the confirmation question ("this project is company-class or undeclared; the loop runs survey-only here; confirm you want the loop session at all?") and records the answer in the turn record, and an unattended session reports the guard line and stands the lanes down; the guard never reads or writes any directives-home row. Fail-closed class resolution, unconditional for survey-worded sessions: a session whose binding classified survey wording resolves both lanes to survey-only regardless of the recorded profile class, recording the `class-guard-survey-only` token beside the recorded class and inheriting the same survey-only shape: the monitor's corpus-write duties (log appends, prune and freeze commits) hold with the standing reason recorded and its read and audit arms still run, and the registry consult's audit-kind and re-triage dispatches are held the same way (their due-read records the standing `class-guard-survey-only` reason and the task re-fires next turn). A missing facts file, a missing or unconfirmed `project_type` value, and a value outside the `pet`/`company` vocabulary all record class=undeclared and resolve survey-only; the persisted `project_type` key is the class source and no duplicate class marker is read or written; the default profile's ordering applies to survey grouping only and never classifies the project personal; a confirmed `project_type = "pet"` is the only lanes-live record for a non-survey binding. The state file's incident `survey_only` flag gains its standing reader in the Mode enforcement paragraph (by name); the guard never writes or clears the flag, and the flag never changes the recorded profile class, so an operator lane stop propagates across sessions through one machine-readable switch. A survey-only turn records the token `class-guard-survey-only` beside the recorded profile class in `decision_reason` as a sanctioned must-dispatch exemption (no dispatch-defect `turn_error`).

## Invariants

- The maintenance loop never pushes to origin.
- It never blocks on questions; unattended turns decide and proceed.
- It schedules at most one child per lane per scheduler turn (one execution and one authoring at most; an audit child occupies the authoring lane, so a turn whose dispatch is the audit child dispatches no authoring child that turn, and at most one audit child runs per cadence period; the authoring lane serves at most one re-triage child per cadence period, per its `next_due`).
- Fleet cap (added 2026-09-24, P54, superseding the single-lane in-flight caps and the strictly-sequential wording): the repo holds at most 4 concurrent children across mixed kinds (execution, authoring, audit, re-triage; the `G1e` / `G1a` fleet counting); the authoring and audit lanes fill the fleet slots; executions are fleet members, execution children run in per-execution ad-hoc worktrees per the Worktree-first standard (isolation landed 2026-09-24, P57); merge-lock landings stay serialized under the merge landing lock.
- Landing critical sections on the default branch are mutually exclusive under the merge landing lock, and both child kinds stand down or retry on contention.
- The fleet caps the post-review, pre-landed state at one recorded run: at most one run may sit in the post-review, pre-landed state at a time, and a new child dispatch of either lane requires zero outstanding unlanded runs with no surviving repo-matching `pending-landing-<plan-slug>` note (any outstanding record or queued note gates both lanes' dispatches); a race that strands a second run while one is recorded is captured by the per-run note and drained by the landing-completion work at one record per turn before further dispatch.
- It never touches peer-session state.
- `docs/history/plans/deferred/` plans are never auto-picked (human revival only).

Reader side (this skill): the Step 1 survey's Authoring-claim consult and D2's Fresh-foreign-claim consult read the claim surface the plans skill's Phase 0 Authoring claim step writes (the resolved tmp directory's `authoring-claims/` at the primary checkout); the D2 selection skips a target whose fresh foreign claim sits there, records the skip in `decision_reason`, and admits it as a sanctioned must-dispatch exemption reason; a stale claim does not block and stays the payload takeover path's input. Producer side (plans): the Phase 0 Authoring claim step runs the AUTHORING CLAIM duty by reference to `agents/skills/maintenance/template-authoring.md` (the procedure of record), deleting its claim at closeout and on an owned stand-down. Authorization handoff: this skill's authoring payload passes its standing authorization and the D2-selected item and scope to plans authoring, selecting the plans skill's Phase 1 maintenance-selected arm for exactly that invocation; other plans invocations keep the ordinary confirmation and grill paths.
- learn skill (`agents/skills/learn/SKILL.md`): bidirectional. The loop's Per-cycle harvest duty (Step 3) invokes learn once per completed cycle under a live standing directive over the cycle's session logs and outputs; learn's own placement and duplicate-refusal rules govern what lands, and learn's Integration Points entry attests the same contract from its side.
- investigate skill (`agents/skills/investigate/SKILL.md`): bidirectional. Maintenance's monitor step (the Step 3 Rolling prompt log duties) consumes investigate's log entries in the rolling prompt logs (`docs/history/backlog/PLAN-PROMPTS.md` and `docs/history/backlog/EXEC-PROMPTS.md`): it reads, prunes, and dispatches from both logs per duties (a) through (i), and it invokes the investigate skill per duty (e) (when neither log has a ready entry, one ungrouped backlog item per turn is investigated and its entry appended to the log the work-type verdict routes it to). Investigate's own `## Integration Points` entry names maintenance's scheduler turn as its consumer (its monitor step invokes investigate for ungrouped backlog items when neither log has a ready entry and reads the emitted entries in both logs), so the two sections attest the same contract from both sides. The Per-cycle harvest duty (Step 3) is the second invoke form beside the monitor step: one investigate pass per completed cycle under a live standing directive. Every anchored invocation carries investigate's Stage 0 survey sweep; the `Cluster:` annotation writes it performs are committed by the same turn under the log's write discipline.
