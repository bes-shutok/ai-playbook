# Maintenance

Unattended maintenance loop for this repository. One run of this skill is a **scheduler turn**: survey the work surface, apply the guards in fixed order, decide per lane, schedule at most one execution and one authoring child, and update the state file. The turn is designed to run from a recurring automation with standing pre-authorization: never block on questions, decide and proceed.

This skill stays runtime-agnostic. Runtime-specific scheduling primitives and recipes live in the runtime overlay `agents/skills/maintenance/zcode.md` (load it only when the runtime is ZCode). The two child blueprints the turn fills and schedules live in `agents/skills/maintenance/prompt-templates.md`.

### Trigger verbs (schedule vs execute vs resume)

These bindings govern interactive asks from a human-typed message; an unattended scheduler turn never blocks on questions regardless of wording and follows its blueprint duties instead.

- A scheduling verb ("schedule at HH:MM", "reschedule", "patch the automation") means create or patch the automation only; never execute the payload inline in the same turn. End the reply by echoing the automation id and its next fire time.
- An execution verb ("run now", "execute") means perform the work in-session.
- A loop verb ("resume", "re-arm the loop") means run the state-file re-arm recipe per the runtime overlay.

An ambiguous time ("12am 30 minutes this night") is resolved to a concrete timestamp before any create, never guessed.

### Step 1: survey

- Open backlog items: `find docs/history/backlog -maxdepth 1 -name '*.md'` (substitute the resolved `backlog_dir` when the facts document overrides it).
- Open plans: `find docs/plans -maxdepth 1 -name '*.md'` (substitute the resolved `plans_dir`); the `-maxdepth 1` scope keeps the survey at the top level and excludes the `completed/` and `deferred/` subdirectories. External-gate classification, per open plan: the plan's header block (the title line through the first `## ` heading, nothing beyond it) is scanned for a line matching `^External gate:`; a plan carrying the line is externally gated and its gate is evaluated per the Gate satisfaction rule, mechanically: the value's first whitespace-delimited token is either a `YYYY-MM-DD` date (date form; satisfied when the named date has passed at turn time) or a kebab-case slug (slug form; satisfied when some open top-level plan or open backlog item other than the declaring plan has the slug in its file basename as a hyphen-bounded segment: the basename carries the slug with a hyphen or a string edge on both sides; a match inside a longer word does not count); the slug-form match set is exactly the open surfaces: top-level plans under the resolved `plans_dir` (never the `completed/` or `deferred/` subdirectories) and open backlog items directly under the resolved `backlog_dir` top level (never its parked/completed subdirectories); basename matching only, no body-text matching, so the declaring plan's own body can never self-satisfy its gate; a plan without the line in that region is not gated (no declaration = not gated, preserving current behavior; body text never classifies). An empty gate value (the `External gate:` line with nothing after the colon) is neither form and reads as unsatisfied; a first token that is neither form (like the empty value) reads as unsatisfied too; when the plan carries no `## ` heading at all, the header block extends to the end of the file. The survey records a gated plan's classification with skip reason `externally-gated` in the survey output only when its gate is unsatisfied per the Gate satisfaction rule; a satisfied gate is not a skip (the plan dispatches under the normal rules).
- Certification: run `python3 scripts/plan_readiness.py <plan>` once per open plan. The exit status of scripts/plan_readiness.py is the certification oracle; exit 0 marks the plan digest-intact on current bytes.
- Plan coverage: for each open backlog item, grep the top-level plans for the item's filename. An item referenced by at least one top-level plan is plan-covered.
- Archived-coverage warn arm: an open top-level backlog item whose basename appears in any archived plan's origins block is reported as plan-uncovered-with-archived-coverage (warn and continue; this arm never changes skip semantics and never blocks the turn). Run `python3 scripts/check_plan_origins_closed.py` without `--plan` for the corpus-wide scan (it exits 0 with one warning per survivor; the archived plan's own origins block is the only gate the archive step enforces, and this survey arm owns the corpus-wide stragglers).
- Quota snapshot: run the harness detection then the probe exactly as Step 4 prescribes (`python3 scripts/harness_detection.py` first, repo-local copy then the deployed home copy; when it reports `harness: none` the snapshot's source is `skipped-unsupported-harness` and the probe does not run; otherwise run `python3 scripts/quota_window_probe.py` once), and carry the primary-window reading into Step 3 as decision input: percent used, minutes to reset, and the source, one of probe | pricing cache | unknown | skipped-unsupported-harness. This is the decision-time reading Step 3 records per lane as `quota_at_decision`; Step 4's landed wording and its own probe invocation stay verbatim: the runtime-fit rule is fire-time-relative and keeps computing its own minutes at the planned fire time, so this survey run is an additional reading taken for the decision layer only.
- Child-outcome check: run the failure-detection procedure from "Failure detection and the failure cap" at the end of this step, including its read-back of the persistent memory index (for alert notes left by turns whose state write failed), so its outputs are on file before Step 2 evaluates the guards in fixed order.
- Memory index: when the runtime provides a persistent memory index, read plan dependency-chain order and backlog priority groups from it; otherwise use the oldest-first defaults. Also read back `loop-parent-missing` notes: one whose `repo` key matches the resolved repository root means the last dispatched child may not have re-armed the parent; re-list first, and when an ENABLED automation matching the recognition rule (defined at Step 0) already exists, adopt its id into `parent_automation_id` with the Step 0 adoption guards, clear the note, and skip the re-arm; only when the listing shows no such parent, re-arm per the runtime overlay's recipe, clear the note, and record the recovery in the turn output, clearing any standing re-arm intent record in the same targeted edit that records the recovered `parent_automation_id` (the writer-class entry's named clear for this path; the field paragraph owns the intent's lifecycle). The read-back also surfaces repo-matching `successor-chain-failed` notes and records the re-chain decision for the note's target (the target re-enters the Step 3 selection). A repo-matching `pricing-verification-failed` note surfaces in the survey read-back like the other notes above, so a stale pricing pin is visible to the turn; the runtime overlay's Quota leg owns clearing it on a successful re-verification. The survey read-back also owns the park-proposal lifecycle: when a `park_proposals` state entry's plan is absent from the fresh top-level survey (a human parked it per `docs/plans/deferred/README.md`, or it executed), the turn clears that entry from the state file and deletes the repo-matching `park-proposal-<plan-basename>` note after its identity confirms the target (the note's `repo` key must match the resolved repository root, and the target is confirmed by the body's `plan` field for fixed-type bodies or by the name's own plan-basename suffix for legacy parameterized-type bodies: one note read, no listing; the deterministic name plus that confirmation makes the clear targeted, so a note naming a different plan is never deleted); a legacy note whose body carries the parameterized type literal (`park-proposal-<plan-basename>` as the type) matches the same clear by its name suffix alone and is deleted on sight, so notes written before the fixed body type self-migrate without a separate migration pass; a later revival starts a fresh first-proposed date. A repo-matching `park-proposal-*` note whose plan is surveyed but whose state entry is gone (cap eviction or state-file loss) is deleted too. The sweep is name-derivable only: a note whose plan is absent from the survey AND whose state entry is gone has no derivable name under the one-note-read no-listing convention, so that combination is the one case that can leave an orphaned note until the plan revives (its reappearance makes the basename derivable and the surveyed-but-entry-gone rule deletes it) or a human clears it; the no-orphan property is claimed only for the name-derivable combinations. When a proposed plan's gate now reads satisfied per the Gate satisfaction rule, the next turn clears that plan's `park_proposals` entry and memory note the same as a survey absence.
- Pending dispatch: when `pending_dispatch` is set, validate the target against the fresh survey (execution: plan top-level; authoring: item top-level and plan-uncovered); for an execution target the reader re-verifies the external-gate classification of the target plan with the survey's header-block scan, and a target that has become gated since the deciding turn and whose gate is unsatisfied per the Gate satisfaction rule is not dispatched: the pending entry is cleared with the skip reason `externally-gated` recorded in `decision_reason` (a target whose gate reads satisfied is not cleared; it dispatches under the normal rules); a valid target whose dispatch the standing `loop_mode` would suppress is retained instead of dispatched: an execution-kind target under a mode excluding the execution lane (`authoring-only`; the Step 3 enforcement resolves that lane to D3), or an authoring-kind target under a mode excluding the authoring lane (`execution-only`; likewise), is retained in `pending_dispatch` with reason `loop-mode-held` recorded in `decision_reason` and re-dispatched when the mode lifts (`dual` and `null` are inert, so the exclusion holds only while a non-dual mode names the target's lane), and the reader processes no further dispatch condition for that target this turn; when valid, the standing `loop_mode` does not exclude the target's lane, and, for an execution-kind target, the Step 3 rate-pressure deferral condition does not hold, dispatch it per its kind through the normal Step 5 path (quota leg applies) without re-running the Step 3 selection, then clear the field; when the target is invalid, clear it and record the invalidation in `decision_reason`; when the target is valid but the Step 5 lane precondition trips on the final slot (a tripping lane guard, or a fresh `G3b` merge-lock hold deferring the lane), retain `pending_dispatch` (retry next turn) and record the deferral in `decision_reason`; a retained target is re-dispatched only when the fixed-order guards pass (the `G2` failure cap, the `G3` joint state, and the duplicate-parent tripwire, not only the lane guard); when one of those guards trips, the target is retained in `pending_dispatch` with the tripping guard named in `decision_reason`; an execution-kind retained target is re-dispatched when valid, the standing `loop_mode` does not exclude its lane, and the Step 3 rate-pressure deferral condition does not hold; when the deferral condition holds (`rate_pressure` at or above 3), the target is instead retained in `pending_dispatch` with reason `rate_limited` recorded in `decision_reason`, so the decided work is never lost to a throttle window; this gate's re-dispatch preconditions apply to every execution-kind retention source (precheck park, merge-lock hold, loop-mode-held retention, rate-limited retention alike), while authoring-kind dispatches keep the existing validation only; label precedence: the short-circuit `loop-mode-held` reason wins when both holds coincide, and the `rate_limited` label is recorded only when rate pressure is the sole hold.
- Pending re-arm: when `pending_rearm` is set, decide state-first, mirroring the Step 0 rearm-on-touch discipline: consult the state file's recorded `parent_automation_id`, pending `children[]` entries, and `parent_absent_since` first, and run the automation listing only when the state file cannot decide; a set `pending_rearm` is itself a cannot-decide signal: when the field is set, the reader runs its armed-verification listing regardless of the state-first decision (the intent is the reason the state cannot decide); when the recipe re-arm conditions hold (the Step 0 darkness classification, unexplained by a live pending child), re-arm per the runtime overlay's recipe (the mode appendix included per `loop_mode`), update `parent_automation_id` to the re-armed parent's id, and clear `pending_rearm` in the same targeted state edit, consuming the intent's own keyed copy of the paired payload under the rearm kind's identity-bound payload filename (the field paragraph's identity-bound filename derivation, which the paragraph owns), the filename's `<date>` being the calendar date of the intent's `decided_at`; the paired copy is advisory, never a precondition: a missing copy never blocks the re-arm (re-arm per the recipe and note the missing copy in the turn output), consuming deletes the copy only after the re-arm's state edit has survived (deleting earlier would lose the payload inside the state write's crash window), and the mechanical re-arm supersedes the copy; on a refused re-arm create, record the structured-first-line `rearm_note` under the reader-side token (`refused-fallback-re-create`, or the token of the failed leg when the re-arm failed on a different leg), keep the intent, and let the attempt bound govern retries (the duty's escalation semantics mirrored reader-side; a later touch's re-arm attempt consults the live bound first, mirroring the Step 0 precedence wording: a `rearm_note` carrying a live bound matching the same defect token and parent within the last cadence period suppresses the re-arm attempt for that touch, recording nothing new, and the bound suppresses only the re-arm attempt, never the set `pending_rearm`'s mandated armed-verification listing, which still runs); a matching `rearm_note` clears per its field paragraph's clearer list; when a listing instead shows the parent verifiably armed (an ENABLED recognition match per the Step 0 recognition rule), clear the stale intent without re-arming; when neither holds, retain the intent for the next turn and record the reason in the turn output beside the retained intent (the fixed two-key `decision_reason` object carries lane decisions, not loop maintenance, so it is not the carrier here). Both clears join the scheduler-turn class's Step 1 reader-edits enumeration, with the successful re-arm's `parent_automation_id` update beside them.

### Step 2: guards (fixed order)

Evaluate in this order; each guard names its observable signal. The proposed slot for this turn's child is now plus 5 minutes, unless the quota leg (Step 4) later moves it.

- `G1e (execution lane)`: trips when an execution child (classified per the markers in `agents/skills/maintenance/zcode.md`) occupies the lane per any arm below, checked in this order:
  - State-file arm (release rules): a recorded child holds the lane while `fire_at` has not elapsed, or while its 6-hour horizon has not elapsed and (outcome is `pending`, or outcome is `progress` and the completion evidence is absent); completion evidence is, for an authoring child, the target plan passing the certification oracle, and for an execution child, the target plan archived; an execution child with `outcome: progress` whose manifest `updated:` is stale past one cadence period releases the lane as evidenced stopped (eligible for fast re-dispatch); an idle-time child (null `fire_at`) holds the lane until the runtime's idle-task listing (named in the overlay) no longer shows it queued or running, idle-time tasks being lane-occupying per the overlay's attribution rule (an entry whose session identifier matches the current session, or one a pending `children[]` entry records whose target carries the `(idle)` marker, `created_at` matched where the idle listing exposes it), or six hours pass after `created_at`, with the same outcome and completion-evidence conditions. An `(in-session)` children[] entry (Step 5's in-session dispatch mode) holds the lane while it is pending within the same horizon, joins no listing (no automation exists for it to appear in), and is released by the entry's own outcome write; a deciding turn that dies mid-in-session-authoring leaves it pending like any dead child. This arm is the primary in-flight detector for children this repository dispatched itself.
  - Armed arm: an execution-child automation armed to fire within `CHILD_LANE_SPACING_HOURS` (default 5, sized to outlast a typical child run; observed runs span one to four hours) of the proposed slot.
  - Fired arm: a fired execution child fewer than six hours past its `fire_at` (the post-fire outcome-horizon floor; the spacing constant governs pre-fire arming), computed from the automation listing when the child still appears there; a listing record counts only while it is ENABLED.
  - Widened arm: catch-all for children not covered by the arms above. Evaluate in order: (1) exclude the recorded parent by id; (2) when the recorded id is null, exclude a sole ENABLED automation whose prompt begins with the scheduler template's opening line and contains the resolved repository root; (3) for each remaining automation whose fire or last-run time falls inside the spacing window, classify its prompt only when the prompt contains the resolved repository root (the same containment the recognition matchers and the duplicate-parent tripwire require); a prompt without that containment occupies nothing, because a foreign repository's plan work is not this repository's lane occupant; a prompt not visible in full is not classifiable and counts as a potential child per the not-visible fail-safe (the lane is treated as busy). Among contained prompts: a match for this lane's markers occupies this lane, an authoring marker occupies only `G1a`, an execution marker occupies only `G1e`, a prompt affirmatively unrelated to plan/backlog work occupies nothing, and anything else occupies both lanes. The classification ignores records whose `lifecycleStatus` is completed or `enabled` is false (a lingered completed child record occupies nothing; the state-file arms are the in-flight detectors), so the fast re-dispatch, successor chaining, and early release paths are not re-blocked by a corpse record. When the lane of an in-flight child is uncertain, treat both lanes as busy.
  - Discovery arm: a live execution session otherwise discoverable (an execute-plan claim check via the execute-plan live-session discovery ladder, the `## Live-session discovery ladder` section of `agents/skills/execute-plan/SKILL.md` with its mechanism pin under the same heading in `agents/skills/execute-plan/runtime-contract.md`, or active child session traces on the checkout).
  When uncertain whether an execution child is in flight, treat the lane as busy.
- `G1a (authoring lane)`: the same arms as `G1e`, evaluated only against authoring children (markers per the overlay; the widened arm's lane-classification rule applies symmetrically), except that the discovery arm is its own below, replacing the execution-side arm inherited by reference (authoring claim files are authoring-only artifacts). The two lanes are independent by policy: an authoring child never trips `G1e` and an execution child never trips `G1a`. Executions are strictly sequential (never two in flight); an authoring child may run alongside an execution child, and it lands via its own merge-lock-serialized self-landing onto the default branch from its ad-hoc worktree, carrying the plan-document commits. One authoring child still never runs alongside another.
  - Discovery arm (authoring-side): an authoring claim file under the resolved tmp directory's `authoring-claims/` (facts key `tmp_dir`, `docs/tmp/` default) whose `updated:` is fresher than one cadence period occupies the authoring lane, UNLESS the state file's pending `children[]` entries explain it: a claim whose item basename matches the target's item basename in a pending authoring child entry is that child's own witness (not foreign), a claim whose item matches no pending entry is foreign and occupies the lane (listing records carry no session ids and `children[]` entries carry automation ids, so target-keyed matching against the state file is the only data source the guard has); a stale claim (its `updated:` one cadence period old or older) occupies nothing. Path caveat: the authoring payload writes the literal `docs/tmp/authoring-claims/` (it cannot resolve facts keys) while this guard reads the resolved tmp directory's `authoring-claims/`, so a facts `tmp_dir` override must revisit both sides. The execution-side live-session mechanism, named for the mirror, is the execute-plan live-session discovery ladder (`G1e` discovery arm); the authoring payload writes and refreshes its claim file per `agents/skills/maintenance/prompt-templates.md` and deletes it at closeout, so an explained hold ends with its own child.
- Duplicate-parent tripwire: when the automation listing shows an ENABLED automation whose visible prompt begins with the scheduler prompt template's opening line and contains the resolved repository root (the tripwire's span shape: the two title-less conjuncts it shares with the recognition rule defined at Step 0, deliberately without that rule's title conjunct, so a hand re-created duplicate with a drifted title still trips; the span literal, the scheduler prompt template's opening line, is pinned in the runtime overlay's child-classification markers), and whose id differs from the recorded `parent_automation_id`, or more than one such ENABLED span match while the recorded id is null, treat the extra as lane-occupying (both lane guards trip) and record a `turn_error` with reason `duplicate-parent-candidate` in the state file (Step 6) so a human collapses the duplicates. Self-heal arm: when the recorded `parent_automation_id` is absent from the listing and exactly one ENABLED span match exists under the same title-less span shape as the tripwire above (not the full recognition rule), the turn adopts that id into the recorded value, clears a `duplicate-parent-candidate` turn error, and schedules normally; the human deletion remedy applies only when the recorded id is still present in the listing.
- `G2 (failure cap)`: trips when an alert is present in the state file or recovered from the memory index read-back, from either the child cap (three consecutive no-progress child outcomes) or the turn tripwire (three consecutive `turn_error` records, or an N >= 3 write-failure streak note).
- `G3 (joint state)`: trips when a merge or rebase is in progress on the checkout or the done-lock (`scripts/done-lock.sh`) is held, standing down the whole turn; a tripped G3 records the stand-down as a D3 no-op in the state file (Step 6) before stopping.
- `G3b (landing in flight)`: evaluated immediately after `G3 (joint state)`; trips when the merge landing lock is held (observable: `bash scripts/done-lock.sh merge-status` reporting a holder). Unlike `G3` it never stands the turn down: the survey, the guards, the decisions, and the state write all still run, and its effect is confined to Step 5's final-slot precondition and the Step 3 lane resolutions. When the hold is fresh (younger than `MERGE_LOCK_STALE_SECS`, default 600 seconds), the affected lane's dispatch creation defers with `pending_dispatch` retained per the existing Step 1 reader semantics and the reason `merge-lock-held` recorded in `decision_reason` (the lane per the Step 3 label mapping). When the hold is at or past the stale threshold it is crash evidence: record `turn_error: merge-lock-stale`, name `merge-stale-clean` as the operator escape, and proceed with scheduling (a stale lock blocks no scheduler decision; a stale holder whose process is still alive keeps landing children in the bounded wait until an operator runs `merge-stale-clean`, while a verified-dead stale holder is auto-reclaimed by the lock's own recovery rules -- dead-holder grace -- without operator action, so such a hold does not keep children waiting). The escape's reach is scoped: `merge-stale-clean` removes a hold whose meta parses once it is at the stale threshold and an aged meta-less hold (crash leftover past the incomplete threshold), while a corrupted-meta hold refuses `merge-stale-clean` by design (fail-closed) and needs manual removal after inspecting the `merge-status` dump. A hold whose age cannot be resolved at all (metadata missing or unparseable, `merge-status` printing `metadata missing` or `age_secs: unknown`) classifies as the same stale crash evidence under the same rule (same `turn_error` reason, same operator escape; the `G2` interaction below is unchanged), so an unresolvable holder can never defer the lane alertlessly forever. Failure-cap interaction, stated explicitly: a persistently stale lock records `turn_error: merge-lock-stale` every turn, so three consecutive stale turns trip `G2` and stand the loop down with an alert until a human runs `merge-stale-clean` (per the escape scoping above: a corrupted-meta hold refuses it and needs manual removal after inspecting the `merge-status` dump) and clears the alert; that is intended crash-evidence behavior, not indefinite loop continuity.

### Step 3: decision

Apply the rules in this order; the two lanes decide independently, so one turn may dispatch an execution child AND an authoring child (at most one of each).

Loop-mode enforcement runs before D1, D4, and D2: the per-lane decision reads `loop_mode` from the state file first, and a non-dual mode resolves the excluded lanes to D3 with the mode recorded in that lane's `decision_reason`: authoring-only resolves D1 and D4 to D3, execution-only resolves D2 to D3; `dual` and `null` are inert (today's behavior).

- `D1 (execute)`: when all guards pass except at most `G1a`, the execution lane (`G1e`) is free, and an open plan exists, schedule an execution child for the best open plan, skipping plans the memory index marks dependency-blocked when selecting: memory dependency-chain order when available, otherwise the oldest basename among digest-intact plans, otherwise the oldest open plan whose re-certification the child's PRE-STEP performs. Treat a plan skipped as dependency-blocked whose marked blocker is no longer an open plan anywhere under the resolved plans_dir (completed or absent) as not blocked (self-healing), so a stale memory mark cannot starve the queue; a blocker still present under the deferred/ subdirectory keeps the plan blocked. D1 also skips externally gated plans (the Step 1 classification) exactly like dependency-blocked ones; when nothing remains after the two skips (every open plan is dependency-blocked, externally gated with an unsatisfied gate, or both), fall through to D2. The gated skip carries the mirrored self-heal: a gated plan whose gate satisfies the Gate satisfaction rule is no longer skipped and becomes dispatchable again without human action, so a satisfied gate cannot starve the queue. The execution lane must not idle by choice: when the lane is free and a dispatchable open plan exists, D1 dispatches; a turn that ends with the lane free and no dispatch while a dispatchable plan exists, without a guard, quota, dependency, external-gate, rate-pressure, or loop-mode reason, records a `turn_error` (dispatch defect) so the idle lane is visible to the next turn. Rate-pressure deferral: when `rate_pressure` (the state file's derived count of `rate_limited_events` entries within the last 24 hours) is at or above 3, the turn defers execution dispatch: it writes the decided dispatch to `pending_dispatch` only when `pending_dispatch` is not already set (a retained entry the Step 1 reader kept stands, so a retained target is never silently overwritten by a different fresh selection) (`kind`, `target`, `payload_slug`, `decided_at` per the existing field paragraph in State file, mirroring the decided-but-could-not-schedule writer semantics) and records the deferral with reason `rate_limited` in `decision_reason`; the deferral is a sanctioned reason in the must-dispatch exemption list (no dispatch-defect `turn_error`), alongside the guard, quota, dependency, external-gate, and loop-mode reasons. The threshold is exact: a state with 3 events within the last 24 hours defers; with 2 it dispatches.
- `D4 (propose park)`: evaluated immediately after D1 and before D2; it refines D1's per-plan skip outcomes, per plan, all conjuncts required: for EACH open plan D1 skipped this turn at its selection time with reason `externally-gated` (the Step 3 skip itself, not the Step 1 survey's classification record; D1 dispatches at most one plan, so every gated plan it skipped is a D4 candidate even in a turn where another plan was dispatched), whose gate is unsatisfied per the Gate satisfaction rule (Step 1), and whose plan-file bytes have been unchanged for 7+ days (git log/diff evidence against the plan path), D4 records a park proposal naming the plan, the gate text, and the unsatisfiability evidence, in all three surfaces: an upserted `park_proposals` entry in the state file (keyed by plan path, bounded at 10 entries, oldest evicted), a per-plan repo-keyed memory note named `park-proposal-<plan-basename>` (repo-keyed like `loop-parent-missing`; the deterministic per-plan name is what keeps concurrent proposals from overwriting each other) whose body carries the fixed type literal `park-proposal` with `plan` and `repo` fields (the `plan` field naming the proposed plan's path, mirroring the state entry), plus the gate text and the latest evidence, and the turn output (the turn's `decision_reason.execution` summary string names the plans proposed and points at the state entry; the schema's fixed two-key `decision_reason` object gains no new key). Lifecycle: when a proposed plan leaves the top-level survey (a human parks it per `docs/plans/deferred/README.md`, or it executes), the next turn clears that plan's `park_proposals` entry and its memory note; a later revival starts a fresh first-proposed date. D4 never moves plan bytes: the proposed plan keeps being skipped, there is no autonomous `git mv` of certified work, and the deferred never-auto-picked invariant is unchanged.
- `D2 (author)`: when all guards pass except at most `G1e`, the authoring lane (`G1a`) is free, and an open backlog item is plan-uncovered, schedule an authoring child for the highest-priority plan-uncovered open backlog item. When the plan-uncovered set is empty, D2 falls through to D3. Primitive selection is quota-aware (added 2026-09-20): before choosing the authoring dispatch primitive, consult the quota leg's probe report as a required decision input; when the report is usable, used_percent is below the max-percent threshold, the probe decision is continue, and this session is alive and able to carry the full authoring loop, author in-session (the deciding turn runs the plans-skill authoring loop itself, no child automation is created; Step 5's in-session dispatch mode), recording the dispatch's quota_signal; when quota is scarce (used_percent at or above the threshold or the decision is not continue) or a pricing deferral is active, or the session cannot carry the work, dispatch out through the existing clocked or idle-time rules.
- `D3 (no-op)`: otherwise, for a lane, record the reason and schedule nothing for that lane.
- Quota-aware lane decisions (per lane; consumes the Step 1 quota snapshot): every lane decision this step resolves records `quota_at_decision` (per lane: status, percent_used, minutes_to_reset, the Step 1 snapshot's reading) alongside `decision_reason` in the Step 6 state write. Near-reset branch, reusing the landed Step 4 upper bounds as decision input: when minutes to reset at the realistic start of work is below the lane's expected runtime upper bound (execution 240 minutes, authoring 120 minutes, the Step 4 constants), D1 defers the execution dispatch past the reset and D2 defers the authoring dispatch, each recording the quota reason. In the band where the execution bound does not fit but the authoring bound does (120-240 minutes left), D1 defers while D2 may still dispatch, which is the rule's per-lane bias; above both bounds the lane dispatches and the recorded comparison makes the call auditable. A quota deferral is a sanctioned must-dispatch exemption (the same sanctioned-reason list the D1 dispatch-defect rule reads); the deferred lane re-decides on a later turn from the fresh post-reset snapshot. Fresh-window rule: when the window is fresh (under 25 percent used with well over an hour left) and a lane lands on D3 with dispatchable work available, the `decision_reason` must cite an explicit non-quota reason.
- A tripped `G1e` resolves D1 and D4 to D3 for the execution lane; a tripped `G1a` resolves D2 to D3 for the authoring lane. A fresh `G3b` hold defers per lane by the holder label `merge-status` reports (the label-to-lane mapping): the label `execution-final-merge` defers the execution lane (D1 and D4 to D3), the label `authoring-self-landing` defers the authoring lane (D2 to D3), and any other resolvable label defers both lanes; a stale or unresolvable-age hold is not a defer at all: it is crash evidence that records `turn_error: merge-lock-stale` per the `G3b` stale rule while scheduling proceeds. `G2`, `G3`, or the duplicate-parent tripwire tripping stands the whole turn down to D3 for both lanes and suppresses D4 entirely for the turn (no park proposal is recorded and none is emitted; the next unstood-down turn re-evaluates). There is no checkout-branch precondition for D2: the authoring child runs in its own ad-hoc worktree on its own branch, and its plan-document commits reach the default branch only through the merge-lock-serialized self-landing, so no commit of its ever depends on which branch the shared checkout holds.

### Step 4: quota leg

This leg binds every clocked child dispatch, from any session type: a scheduler turn, a pending_dispatch re-dispatch, a successor-chain dispatch, an operator-requested dispatch, and a resume continuation all apply it before creating the child; a dispatch path that cannot run the leg (no probe access) proceeds on the fallback without a state write; a sanctioned-writer decider records the fallback evidence on the child entry at its next Step 6 rewrite, and any other decider surfaces it in its own turn output. The leg's probe report is also the D2 primitive-choice input for the authoring lane (Step 3): its decision and used_percent decide whether the authoring work authors in-session or dispatches out, alongside this leg's existing fire-time role; the probe runs once per turn and the single report is shared between the D2 primitive-choice input and the fire-time role, never a second probe run.

- Run `python3 scripts/quota_window_probe.py`.
- Unsupported-harness budget skip: before running the probe, run the detection helper first (`python3 scripts/harness_detection.py`, repo-local copy first, then the deployed home copy); when it reports `harness: none` (this surface defines no override knob, so no override clause applies here), record `quota_status: "skipped-unsupported-harness"` on the child entry and proceed with the per-lane child cap plus the failure cap (the unknown-mode operative fallback) without calling the probe; a missing or erroring helper counts as unsupported (record the evidence; the family must not run against an unknown harness).
- When its window data is usable, use it to time the child; never fire the child inside a window the probe's decision defers (a report-only pause never defers; the runtime overlay's Quota leg names which pauses defer).
- Runtime-fit rule: when minutes_remaining at the planned fire time on the primary window is less than the lane's expected runtime upper bound (execution 240 minutes; authoring 120 minutes), fire at reset_at_epoch instead, regardless of pricing preference, and record the comparison (expected versus remaining minutes) in the lane's decision_reason.
- When the probe output is not usable, apply the fallback pinned in `agents/skills/maintenance/zcode.md` ("Quota leg"). Dead probe output downgrades timing precision; it never blocks scheduling.
- When the final fire time lands inside the provider's published peak-pricing window, apply the overlay's usage-pricing rule: defer to the window's end so the child's run bills at off-peak rates, unless the starvation exception applies; before deferring for pricing, verify the deferred slot passes the runtime-fit rule, and when it does not, defer to reset_at_epoch instead. Starvation is named by observation: no child record with kind `execute` and `created_at` within the last 24 hours in the state file (fall back to the runtime listings when state writes have been failing), and the exception releases only the starved lane; starvation beats pricing, never the runtime-fit rule. The pricing cache lives in the state file's `pricing_cache` field and wins when fresher than the overlay's tracked seed; the turn updates only that state cache (plus a memory note when the values changed) and never edits tracked skill files to re-pin pricing.
- Record the deferral on the child entry when the writer is one of the State file's sanctioned children[] writers (scheduler turns and successor dispatches); a dispatch path outside the sanctioned writer classes records nothing itself in the state file: a resume continuation's deferral is recorded per the Budget gates' resume-fit and resume-pricing record-sink clause (the budget_pause record on a pause boundary; the turn output on a continue boundary), with the state-file audit owned by the next scheduler turn that reads that record, and an operator-requested dispatch by a non-sanctioned session surfaces the deferral in its own turn output: quota_status: "deferred-peak" when a pricing deferral moved the fire time, and requested_at carrying the original requested fire time whenever any deferral moved it.

### Step 5: scheduling

- Assemble the child prompt from the matching blueprint in `agents/skills/maintenance/prompt-templates.md`, filling that blueprint's placeholders. Dispatch slice: for an execution child the scheduled automation prompt is ONLY the content of the `<prompt for the scheduled session>` block of the execution blueprint, with `{REPO_ROOT}` and `{some_plan}` filled. The wrapper sentences around that block (the SCHEDULER voice, "Schedule at {execution_time}") describe the deciding turn's own job and are never part of the scheduled payload; `{execution_time}` is filled into the scheduling call (the delay or cron fields), not into the payload. Authoring slice: for an authoring child the scheduled prompt is the authoring blueprint's fenced body with `{REPO_ROOT}` (in the re-arm duty paragraph), `{schedule_time}`, and `{backlog_item}` filled; the two field lines after the block are fill-in spec and are never part of the payload.
- Schedule at most one child per lane per scheduler turn (one execution AND one authoring at most), never into a lane whose child is in flight (`G1e` / `G1a`). A clocked child is a one-shot firing at least 5 minutes out: the final fire time is never earlier than now plus 5 minutes, even when the quota leg defers past a reset that lands sooner (floor lowered from 30 minutes by user request; see the Revisions ledger's 2026-09-15 floor-revision entry: the deciding turn's state write precedes the fire by construction, so a tight floor is safe). A runtime dispatch primitive without a clock (idle-time dispatch) schedules no fire time and is exempt from the 5-minute floor. When both lanes dispatch in one turn, the execution child takes the clocked create and the authoring lane takes the idle-time primitive or defers to the next turn; the execution lane is never dispatched through a primitive without a clock, because the failure-cap machinery and this step's fire-time bookkeeping require its fire time. For an idle-time dispatch `{schedule_time}` is filled with the literal `an idle-time run (no scheduled fire time)`.
- In-session dispatch mode: when D2's quota-aware primitive selection resolves the authoring lane to in-session, no automation is created and no fire time is scheduled: the deciding turn runs the authoring blueprint's task paragraph itself, with every gate still applied (done lock, fire-time checks, and the blueprint's remaining pre-work checks), and the run's outcome is the turn's authoring record. The in-session mode precedes the idle-time primitive whenever its quota conditions hold; when they do not, the lane follows the existing clocked or idle-time rules above.
- Precondition: after the quota leg fixes the final fire time, re-evaluate the lane guard (`G1e` or `G1a`) and the `G3b` final-slot effect (a fresh merge-lock hold defers the lane) against that final slot before creating the automation; if either trips, resolve to D3 and record the reason (schedule nothing). Ladder precheck: after the quota leg fixes the final fire time and before any ladder step, run the runtime overlay's ladder precheck; a tripped precheck resolves the lane to D3 with the overlay's `turn_error` reason and schedules nothing; the parked `pending_dispatch` entry the precheck write creates persists until the next turn's Step 1 reader dispatches it (the precheck imports only the trap rule's park-or-retain write, never its clear-on-idle-success clause).
- Record the child's automation id, kind, target, and fire time in the state file (Step 6); an idle-time dispatch records a null id and fire time with an `idle` marker on the target; an in-session dispatch records a null id and fire time with an `(in-session)` marker on the target, mirroring the `(idle)` marker convention. An execution dispatch also records `dispatch_plan_sha` (the target plan file's sha256 at dispatch time) so the failure cap's stand-down carve-out can compare the plan file against its dispatch-time state.

### Step 6: state update

- Rewrite the whole state document from the fresh survey, using the schema in "State file" below, through a temp file plus atomic replace.
- This step is best-effort and runs in a guard of its own: a failed state write is reported in the turn output but never blocks the already-made decision. Even a turn that fails before scheduling records `last_run_at` and a `turn_error` reason.

## Failure detection and the failure cap

- The child-outcome check runs at the end of Step 1 (survey) and writes its `outcome`, `outcome_checked_at`, `progress_mark`, `consecutive_failures`, and `alert` updates to the state file before Step 2 evaluates the guards in fixed order; Step 6's whole-document rewrite carries them forward, so `G2 (failure cap)` arms on the tripping turn, not one turn late.
- Each turn checks the oldest `pending` child whose `fire_at` plus 6 hours has passed.
- Early authoring outcome check: every pending authoring child whose `fire_at` has passed (idle-time: once the idle-task listing no longer shows it queued or running) gets the progress predicate evaluated each turn, and `outcome: progress` plus `outcome_checked_at` are recorded on observe; the 6-hour horizon stays the failure threshold for children that never show progress.
- Idle-time children are covered too: a `pending` child recorded with a null `fire_at` (idle-time dispatch) gets its progress check once the runtime's idle-task listing (named in the overlay) no longer shows it queued or running. Six hours after `created_at` is the lane-hold horizon only: a child still shown queued or running at that mark is not failed and accrues no failure credit; one that vanished from the listing without progress is failed like any other child. Exception for evidenced provider-side stops: a child whose session demonstrably ended on a retryable provider error (for example a surfaced 429 `rate_limited` stop) is requeued by the deciding turn or the next scheduler turn without holding the six-hour horizon, whether or not the stop preceded progress; an execution child is not re-armed while the Step 3 rate-pressure deferral condition holds, and the requeue's operative scheduler-side rule while the deferral condition holds is the next scheduler cadence boundary (re-evaluated each turn; bounded unless new rate-limited events keep landing), falling back to the quota leg's reset-anchored slot (fire after `reset_at_epoch`) when a pause window was active; the child's named resume condition (backoff elapsed or the next defined boundary) is advisory only, describing the child's own in-run resume behavior rather than binding the scheduler-side requeue fire time, and the evidenced provider-side stop accrues no failure credit: the cap counts child-behavior failures, not provider incidents. Requeue evidence is the surfaced error record, a budget-guard pause decision covering the child's run window, the timestamped rate-limited stop lines in the child's execute-plan session manifest (the machine surface for the rate-limited case), or a structured rate-limited end-of-run report (operator-facing only: no report-retrieval primitive exists and none is assumed); the manifest-stop-line and structured-report evidence qualify only with an end corroborator: no live claim or launch is observable for the child (the discovery arm's claim check comes back empty), or the session manifest is stale past one cadence period; a graceful rate-limited end under this exception (the run ending with the plan unarchived and the machine manifest left active) accrues no failure credit and requeues per the exception's rules like any other evidenced provider-side stop.
- In-session entries are covered too: an `(in-session)` child entry (Step 5's in-session dispatch mode) that never records an outcome is marked `failed` when the arm's horizon passes (the same six-hour horizon), so the failure cap sees repeated dead deciding turns.
- Rate-limited event ingestion: when the child-outcome check observes a surfaced 429 `rate_limited` stop on a child (the same stop evidence the evidenced provider-side stop exception above reads), it appends a `rate_limited_events` entry of kind `turn` (target: the child's `target`; the entry's `ts` is the surfaced stop record's own timestamp) to the state file. Independently, on every read-back while the child is pending, it appends kind `launch` entries for rate-limited stop lines found in the pending child's execute-plan session manifest free-text lines (the manifest at `execute-plan/<plan-slug>/manifest.md` under the resolved tmp directory; the `budget_skip` precedent for session-manifest free-text lines as event evidence; each `launch` entry's `ts` is the stop line's own timestamp and its `target` is the child target), so every scheduler turn while the child is pending ingests the child's own launch-side rate-limit stops whether or not the surfaced stop fired. Ingestion is deduplicated: entries are ingested only for stop evidence not yet recorded (each entry is keyed on the `{ts, kind, target}` triple -- timestamp, kind, and target -- and an append is skipped when an entry with the same triple already exists), so a pending child's repeated read-backs cannot re-append the same event and inflate `rate_pressure`; the dedup applies to both `turn` and `launch` kinds, and one underlying stop is ingested once across kinds: cross-kind suppression matches on the child target plus a bounded time window, not exact-timestamp equality (a `launch` stop line whose timestamp falls within 15 minutes of an existing same-target `turn` entry's `ts` is suppressed, and vice versa). The append follows the entry schema and the 20-entry oldest-evicted cap defined in "State file"; the derived `rate_pressure` count (entries within the last 24 hours) is what Step 3's deferral reads.
- Progress for an authoring child means a top-level plan now references the target item or the item left the backlog top level.
- Progress for an execution child means the target plan left the top-level plans directory (archived), or the target plan's checked-checkbox count increased beyond the recorded `progress_mark`. The checkbox count is stored in `progress_mark` at every survey turn while the child is pending (one grep per turn) and at each outcome check, counting with `grep -cE '^[[:space:]]*-[[:space:]]\[[xX]\]' <plan>` (the escaped literal brackets are load-bearing: an unbracketed `[xX]` class matches the bare letter after the dash-space and never matches a `- [x]` line; measured at authoring: 0 matches on pure checked-checkbox lines vs 2 for the corrected pattern).
- Fast re-dispatch of a stalled execution child, with a single sound trigger aligned with the release arms: a pending execution child is fast-re-dispatched when both progress evidence and stop evidence hold, plus a negative live-session check. Progress evidence: its checkbox count exceeds the `progress_mark` stored at the previous turn, or its outcome is already `progress`. Stop evidence: the execute-plan session manifest under the resolved tmp directory (facts key `tmp_dir`, `docs/tmp/` default) at `execute-plan/<plan-slug>/manifest.md` carries an `updated:` timestamp older than one cadence period, or it carries a timestamped rate-limited stop line (the same lines the evidenced provider-side stop exception above names as requeue evidence), so a graceful mid-run rate-limited end (which may occur after progress) is caught without waiting a cadence period; a live child refreshes the manifest on every orchestrator update, so the staleness conjunct is what prevents re-dispatching a live child that is merely between manifest writes. Live-session check: the re-dispatch goes through the Step 5 lane-guard re-evaluation with the discovery arm (the execute-plan claim check) mandatory before the replacement dispatch, so a live child whose manifest gap exceeded one cadence period is caught by the claim check, not replaced. The re-dispatch replaces the old child record with the new entry (same target, new `created_at`, `resume_count` incremented on the new entry) so two records for one plan never coexist, and accrues no failure credit when the progress evidence held; the fresh child enters via the existing PRE-STEP re-cert and the payload's resume rule. Two bounds gate the replacement: it is deferred while the Step 3 rate-pressure deferral condition holds (`rate_pressure` at or above 3), the same pressure gate the requeue path applies; and precedence between the two re-arm paths: a child requeued under the evidenced provider-side stop exception is not fast-re-dispatchable until its pushed requeue fire time has elapsed, and when a replacement does fire it supersedes (not leaves behind) any armed requeue automation for the same child.
- Otherwise, and only when no armed child targets the same work, the child is `failed`.
- Stand-down carve-out (beside the evidenced provider-side stop exception above, the same spirit: an evidence-backed outcome accrues no failure credit): when an execution child's zero checkbox progress is explained by its own recorded stand-down (the target plan's own first task prescribed an edit-nothing stand-down because the plan's external gate is unsatisfied), the outcome stays the documented enum value `failed`, `outcome_reason` is set to `stand-down`, and `consecutive_failures` is not incremented. Machine test, three conjuncts, all required and named: (1) `.ai-playbook/last-stand-down.json` is present and its `plan` key names the target plan path, the file's literal key schema being `{"plan": "<plan path>", "reason": "<gate-unsatisfied-reason>", "date": "<iso date>"}` (an ad-hoc-worktree child writes the json into the primary checkout, the only checkout the checking turn reads); the json file is the machine-readable retrieval surface; no report-retrieval primitive exists and none is assumed; (2) the target plan file is unchanged since dispatch: a git comparison of the plan path's current sha against the children entry's `dispatch_plan_sha`.; (3) the checking turn re-runs the Gate satisfaction rule (Step 1) on the target plan's own current bytes and the gate reads unsatisfied: a child claiming stand-down on a plan whose gate now reads satisfied (a stale dispatch, the gate having satisfied between dispatch and check) or on a plan whose header block carries no External gate line accrues credit normally, the one conjunct the checking turn evaluates itself rather than trusting child-asserted evidence The child's final report opening with the literal `STAND-DOWN:` marker line (`STAND-DOWN: <plan-path> <gate-unsatisfied-reason>`, the reporting duty the execution-child payload blueprint in `agents/skills/maintenance/prompt-templates.md` carries) is the human-visible witness quoted in the turn output, produced by that payload duty; it is not part of the machine test: report text alone never qualifies, the exclusion coming from the json conjunct rather than from marker matching (the marker stays a literal line prefix matched exactly, so a broken child whose report merely contains the word stand-down anywhere is not the witness). The cap's count includes only children entries whose `outcome_reason` is not `stand-down`, so a stand-down-explained zero-progress outcome can never alone trip the alert. An authoring child never qualifies (its `dispatch_plan_sha` is null). The checking turn consumes the json file it checked (deletes or clears it) only after the stand-down outcome record write has survived (consuming earlier would lose the evidence inside the state write's crash window), so a stale file cannot qualify a later child. The turn output echoes the consumed json's contents (its plan, reason, and date values) for triage alongside the quoted marker witness. A genuinely broken child that wrote no json file does not qualify, so real stall loops keep accruing credit.
- Carve-out witness: a stand-down outcome accrues nothing, so a stand-down followed by two real failures holds `consecutive_failures` at 2, below the three-strike cap; three stand-down outcomes alone never trip the alert; a child whose report opens with the marker while its plan file changed since `dispatch_plan_sha` does NOT qualify and accrues credit normally; a child whose json satisfies conjuncts 1 and 2 while the plan's gate re-reads satisfied under conjunct 3 does not qualify and accrues credit normally; a child whose report contains the word stand-down anywhere but wrote no json file does not qualify: via the json conjunct, not marker matching (a conforming child that omits the marker also omits the json, the payload duty coupling the two).
- Children-entry schema additions (both additive under schema 4, no version bump): `outcome_reason` is an optional string, `null` by default, carrying the value `stand-down` per the stand-down carve-out above; `dispatch_plan_sha` is the target plan file's sha256 recorded at dispatch time (Step 5), `null` for authoring children.
- Progress resets `consecutive_failures` exactly as archival does, so a multi-session plan never false-trips the cap; failure increments it.
- At three or more consecutive no-progress child outcomes the turn writes `alert` (with `tripped_at` and the reason) and stops scheduling children until a human clears the alert. The turn also notes the alert in the agent's persistent memory index when one exists.
- Turn-level tripwire for the broken-parent case: Step 6 runs in a best-effort guard of its own, so even a turn that fails before scheduling records `last_run_at` and a `turn_error` reason. The schema counter `consecutive_turn_errors` keeps the streak alive across whole-document rewrites: a turn ending with a `turn_error` record writes the previous value plus one, a fully successful turn resets it to 0, and three consecutive `turn_error` records (or, when the state writes themselves fail, three consecutive turns with no successful state update detected via the memory-note streak in the Signal split below) write the same `alert` and trigger the same stop as the child cap. When the trip comes through the `turn_error` records, the alert's reason records the most recent `turn_error` reason (for example `duplicate-parent-candidate`), so the clear procedure's duplicate-removal clause always binds when that reason tripped the alert; the write-failure-streak trip keeps the write-failure reason described in the Signal split below.
- Signal split: the file counter covers turns that ran but failed (`turn_error` records); when the state write itself fails, the file cannot count the turn. For that case the turn writes or updates a memory note `{"type": "turn_tripwire", "consecutive_write_failures": N, "repo": "<resolved repository root>"}` in the agent's persistent memory index on every failed state write (N is the running count of consecutive failed writes; below the threshold a successful state write resets the streak and clears the note), and the Step 1 read-back of the memory index arms the same stop as the child cap only when a note whose `repo` key equals the resolved repository root records N >= 3, resolving the turn to D3 with nothing scheduled; the `repo` key is the cross-repo discriminator, so a streak note written by another repository's scheduler never arms this repository's tripwire. When the read-back finds N >= 3, a successful Step 6 state write converts the streak into the persisted `alert` (reason: write-failure streak) instead of silently clearing the note; the stop then holds until the documented human-clear procedure runs. The `last_run_at` staleness check in the State file section remains a further rail for a dead or silent parent.
- Silent-turn classification may consult the store-level darkness-triage witness where the runtime overlay provides one (it reads the app logs for session-store integrity events around the child's run window, separating a child that outlived its parent record from a parent that actually died); this skill stays runtime-agnostic, so the concrete log event names and the read procedure live in the overlay, not here.
