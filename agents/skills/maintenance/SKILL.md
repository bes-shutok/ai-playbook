# Maintenance

Unattended maintenance loop for this repository. One run of this skill is a **scheduler turn**: survey the work surface, apply the guards in fixed order, decide per lane, schedule at most one execution and one authoring child, and update the state file. The turn is designed to run from a recurring automation with standing pre-authorization: never block on questions, decide and proceed.

This skill stays runtime-agnostic. Runtime-specific scheduling primitives and recipes live in the runtime overlay `agents/skills/maintenance/zcode.md` (load it only when the runtime is ZCode). The two child blueprints the turn fills and schedules live in `agents/skills/maintenance/prompt-templates.md`.

### Trigger verbs (schedule vs execute vs resume)

These bindings govern interactive asks from a human-typed message; an unattended scheduler turn never blocks on questions regardless of wording and follows its blueprint duties instead.

- A scheduling verb ("schedule at HH:MM", "reschedule", "patch the automation") means create or patch the automation only; never execute the payload inline in the same turn. End the reply by echoing the automation id and its next fire time.
- An execution verb ("run now", "execute") means perform the work in-session.
- A loop verb ("resume", "re-arm the loop") means run the state-file re-arm recipe per the runtime overlay.

An ambiguous time ("12am 30 minutes this night") is resolved to a concrete timestamp before any create, never guessed.

## Cycle gate (durable pacing between cycles)

An authoring or execution session running under a standing user directive whose text gates the next cycle on a user-side action arms `authoring_cycle_gate` at every cycle closeout (the State file field paragraph owns the shape). The gate exists because a harness auto-compaction and a user-run compaction are indistinguishable from inside the resumed session: both arrive as a summary continuation, and the harness resume instruction points the resumed turn at the recorded next step. Resumed-turn rule: a continuation-summary resume (the session's latest context arrived as a machine summary rather than a user turn) that finds the gate armed performs due checks plus a readiness report only, re-running the survey-class reads, reporting queue and backlog readiness, and stopping without starting a new authoring cycle or executing the next plan; a real user message in the resumed context is the only thing that starts the next cycle, and the same explicit directive clears the gate (the field paragraph's clear trace). Conservative default: gate armed and no new user directive equals report readiness and stop. Sessions on repos with no scheduler state file are out of scope (the file's existence is the loop's own run-here predicate, the serialization-boundary precedent).

## The scheduler turn

Run Steps 0 through 7 in this order, in one pass. Never reorder the steps and never reorder the guards inside Step 2.

### Step 0: context load

- Resolve the repository root; anchor every path below to it.
- Load the Configuration keys from the facts document.
- Re-check git state (current branch, `git status --porcelain`, in-progress merge or rebase) immediately before acting, because parallel sessions share the checkout and its state may have changed since the turn started.
- turn-start carrier re-arm: run the runtime overlay's Turn-start carrier re-arm duty before the survey. In a session whose own spawner record lingers completed, the duty's first primitive emission is the recorded delete of that record, before any listing that is not itself duty-mandated; already-gone is success; a recorded recurring form or form-unknown keeps the delete at the cap-refused create. A turn arriving to classified darkness arms per the same cadence rule, superseding the rearm-on-touch check's re-arm leg for the turn itself (the check's listing-derived bookkeeping edits and its child-duty exemption are unchanged).
- rearm-on-touch check: consult the scheduler state file first (its recorded `parent_automation_id`, the pending `children[]` entries, and `parent_absent_since`), and run the automation listing only when the state file cannot decide (no recorded id, no live pending child explaining an absence whose `parent_absent_since` is younger than one cadence period (not yet darkness per the State file semantics), a file whose own last write is older than one cadence period (the staleness escape: nothing in the file then attests a listing verification of the recorded parent's presence within one cadence period, so presence counts as not listing-verified and only the listing decides), or a darkness classification that needs listing confirmation, or a fresh `loop_mode` write or replace (a cannot-decide event for the next touch: the first Step 0 touch after a directive change or withdrawal runs its listing, so the self-heal arm can fire on the divergence or withdrawal; the write is fresh to a touch when the field's `set_at` is within one cadence period of that touch (non-null), and a withdrawal is fresh when its `cleared_at` (see the field paragraph) is within one cadence period), or a `rearm_note` carrying a self-heal bound whose structured first line's recording timestamp falls within the last two cadence periods (a cannot-decide event for the touch: the bound is live for the first cadence period and recently expired for the second, so the touch's listing re-observes while the bound's witness is fresh and the arm can fire once the bound has expired or the defect shape changed; the live bound itself still suppresses only the mutating repair per the attempt-bound clause below)); the consultation also reads `rearm_note` for the self-heal's attempt bound: a `rearm_note` carrying a live bound (its structured first line naming the same defect token and parent automation id as the repair this touch would attempt, its recording timestamp within the last cadence period) decides the self-heal for this touch from the state file alone, suppressing the repair for that touch (the bound the self-heal arm below applies; a live bound suppresses only the mutating repair, never the touch's listing, so a cannot-decide event's mandated listing still runs, and the bound itself is one per the enumeration above); when the listing shows no ENABLED parent for this repository (the recognition rule: an ENABLED automation whose title matches the recipe title, whose prompt begins with the scheduler prompt template's opening line, and whose prompt contains the resolved repository root; the literals live in the runtime overlay's recipe, pinned by the suite), consult the State file semantics and re-arm per the runtime overlay's recipe only when they classify darkness, and a re-arm that succeeds there records the new `parent_automation_id` and clears a standing `pending_rearm` in that same targeted edit (the field paragraph's actor-clears-its-re-arm rule). The check runs on every touch whenever the runtime exposes an automation listing and this repository already runs the loop (its scheduler state file exists at the path the State file section defines): the darkness condition above gates only the re-arm decision; the bookkeeping is listing-gated: whenever the listing ran, the check performs its three bookkeeping edits per the State file semantics: the `parent_automation_id` adopt under the Step 0 adoption guards, the `parent_absent_since` set-or-clear (first observation, keeping the earliest value; an ENABLED recognition match clears it), and the `rearm_note` clear on an armed-again listing (scoped per the `rearm_note` field paragraph's clearer list, whose lead clause governs every listing-derived armed-observation clear); all three edits are listing-derived, so when the state file decided and no listing ran, none of them applies and the fresh state-file decision is the bookkeeping of record for that touch (the staleness escape above bounds how long the touch surface goes between listings). Self-heal arm (added 2026-09-21, scheduler/maintenance state durability plan Task 2; widened to divergence, withdrawal, precheck, and refusal-leg routing by review r1): when a listing-derived observation shows an ENABLED recognition match whose prompt does not carry the mode appendix in the form the current `loop_mode` requires (the detection predicate: the prompt must carry the appendix built from the pinned recipe template per `loop_mode`, the shape the recipe clause owns; the predicate fails when the appendix is absent under a non-dual mode or carries a previous directive's form), the check repairs the parent with one update-primitive call that changes nothing else (the prompt's appendix is rebuilt from the current `loop_mode`; cadence, title, and schedule are untouched), and the repair counts as landed only on a verifiable echo (recurring true, enabled true, a future nextRunAt confirmed by a listing, and the prompt carrying the appendix); when the `loop_mode` mode value is `dual` or null (the withdrawn field's cleared trace, whose mode is null, included) and the listing-derived ENABLED match carries a mode appendix, the same repair removes it with one update-primitive call under the same verifiable-echo discipline with the removal's intended form (recurring true, enabled true, a future nextRunAt confirmed by a listing, and the prompt carrying no mode appendix); before either mutating leg the arm prechecks the session actually owns the primitives that leg needs (the update primitive for the repair; the delete and create primitives for the delete-plus-create fallback), and a precheck absence records and skips for this touch (a targeted state edit recording the absence in `rearm_note`, the self-heal writer the `rearm_note` field paragraph's enumeration names; the Step 3 loop-mode enforcement and the existing detectors carry the directive meanwhile), mirroring the child duties' precheck discipline; on a garbled or non-verifiable echo, delete the record and create the parent per the runtime overlay's recipe (appendix included per the current `loop_mode`), then update `parent_automation_id`; a refused delete leg records the refusal via the same `rearm_note` targeted state edit and leaves the standing record untouched; a refused fallback re-create records the refusal via a targeted state edit (`rearm_note`; the writer the `rearm_note` field paragraph's enumeration already names), paired in the same targeted state edit with a `parent_absent_since` set (the delete has already succeeded, so the state file must not attest a healthy parent) and with the repo-keyed `loop-parent-missing` memory note written beside it, and lets the existing `parent_absent_since` and staleness detectors carry recovery, mirroring the dispatch ladder's fallback refusal handling in the runtime overlay; each of the arm's three self-heal refusal records (a refused delete leg, a refused fallback re-create, and a precheck-absent mutating leg) opens its `rearm_note` value with the bound's structured first line, carrying the defect token (`refused-delete-leg` for the refused delete leg, `refused-fallback-re-create` for the refused fallback re-create, `precheck-absent-leg` for the precheck-absent mutating leg; the repair this touch would attempt carries the token of the leg it is about to run, the token the bound's same-defect-token test matches), the parent automation id, and the recording timestamp, so the bound's same-shape and cadence-period tests read structured fields rather than free prose; the Step 1 reader's refusal record is the registry's second emitter, opening with the same structured first line under its reader-side token (the Pending re-arm bullet's refusal branch names the reader-side tokens), so both structured writers share the one token registry the bound matches against; the arm is attempt-bounded: the consultation's live-bound condition above (a `rearm_note` for the same repair shape: the same defect token and parent, recorded within the last cadence period) suppresses the repair for that touch and records nothing new, spending no additional primitive call, and no listing beyond the touch's already-mandated one, on the suppressed shape. The Step 0 adoption guards (shared: the Step 1 memory-note reader adopts with the Step 0 adoption guards): a recognition match whose prompt contains the resolved repository root and whose id differs from the recorded one, adopted only when the recorded id is not itself live in the listing (present with enabled true; a lingered completed or disabled recorded id is treated as absent); the adopting edit clears `parent_automation_form` to null per the field paragraph; more than one differing-id match defers to the Step 2 duplicate-parent tripwire. On a runtime without an automation listing this bullet is inert. A session already carrying a maintenance child duty (the execution or authoring blueprint's re-arm-first paragraph) is governed by that duty and its guards instead of this check. The mechanical consumer script for rearm-on-touch sessions is `scripts/rearm_on_touch.py` (deployed runtime copy `~/.ai-playbook/scripts/rearm_on_touch.py`): it mirrors this bullet's state-first classification (cadence period 2 hours, live-child horizon 6 hours, adoption guards, earliest-value retention, and the three listing-gated bookkeeping edits through a temp file plus atomic replace) and prints a JSON verdict plus a one-line human summary; it classifies, books, and decides but never calls automation primitives, so the session performs any listing or re-arm the verdict calls for and may feed a fetched listing back through `--listing-json` as decision input; its verdict or failure is advisory for the touching session and is echoed into that session's run record.


### Step 1: survey

- Open backlog items: `find docs/history/backlog -maxdepth 1 -name '*.md'` (substitute the resolved `backlog_dir` when the facts document overrides it).
- Priority profile resolution: read the facts document's `## Priority profile` block per guidelines rule 68; when absent, use the default profile (the section 64 ordering with formal-hardening defer-by-default). For each open backlog item, record in the survey output the item's priority group per the profile's `priority_order` and the item's class, judged real or formal per the receiving-review `## Triage class (real vs formal)` section, in the token form `<backlog-item-basename>:class=<real|formal>` carried by the turn's decision_reason summary strings (the survey output's persistent record home; no state-schema change); the survey records the class of every item it groups, so a plan's origin list is auditable against the profile. An item whose class is in the profile's `deferred_classes` is recorded with skip reason `profile-deferred` and is not re-triaged on later turns, the same shape as the survey's other recorded skip reasons. **Exception (shared-skill consumer urgency):** an open item that carries a `Consumer urgency:` header line (or Priority critical/high with Scope naming shared skills under `agents/skills/`) is class=`real` and is never skipped as `profile-deferred` under formal-hardening; it stays eligible for authoring/execution dispatch. Those items exist for consumer projects that run the skills, not as optional hygiene for the skills repo alone (receiving-review Triage class shared-skill consumer defects).
- Bulk disposition sweep gate (P51 origin 1; origin docs/history/backlog/2026-09-22-deferral-sweeps-must-cross-check-claimed-origins.md): before a bulk deferral/disposition sweep moves open backlog items (a git mv into the backlog directory's deferred/ or rejected/ archive, or a bulk Status flip over many items), the sweep runs the claimed-origin checker (python3 scripts/check_backlog_claimed.py, one invocation carrying every candidate slug) and treats a claimed report as skip-and-annotate: the claimed item is never moved (ownership beats triage verdict; a top-level plan's origin list or validation-gate literal naming the item is the claim), and the sweep's output records the skip with the claiming plan path. Manual sweep prompts order the same run; the checker's exit 1 is the gate's stop signal: it stops the claimed item's move (the skip-and-annotate above) and aborts the sweep's remaining moves pending reconciliation of the claim with the claiming plan, and every other checker exit or outcome (exit 2, a usage or path error meaning the gate did not run, or a missing checker report) also means no move proceeds; only a clean exit 0 clears the sweep to move.
- Open plans: `find docs/history/plans -maxdepth 1 -name '*.md'` (substitute the resolved `plans_dir`); the `-maxdepth 1` scope keeps the survey at the top level and excludes the `completed/` and `deferred/` subdirectories. External-gate classification, per open plan: the plan's header block (the title line through the first `## ` heading, nothing beyond it) is scanned for a line matching `^External gate:`; a plan carrying the line is externally gated and its gate is evaluated per the Gate satisfaction rule, mechanically: the value's first whitespace-delimited token is either a `YYYY-MM-DD` date (date form; satisfied when the named date has passed at turn time) or a kebab-case slug (slug form; satisfied when some open top-level plan or open backlog item other than the declaring plan has the slug in its file basename as a hyphen-bounded segment: the basename carries the slug with a hyphen or a string edge on both sides; a match inside a longer word does not count); the slug-form match set is exactly the open surfaces: top-level plans under the resolved `plans_dir` (never the `completed/` or `deferred/` subdirectories) and open backlog items directly under the resolved `backlog_dir` top level (never its parked/completed subdirectories); basename matching only, no body-text matching, so the declaring plan's own body can never self-satisfy its gate; a plan without the line in that region is not gated (no declaration = not gated, preserving current behavior; body text never classifies). An empty gate value (the `External gate:` line with nothing after the colon) is neither form and reads as unsatisfied; a first token that is neither form (like the empty value) reads as unsatisfied too; when the plan carries no `## ` heading at all, the header block extends to the end of the file. The survey records a gated plan's classification with skip reason `externally-gated` in the survey output only when its gate is unsatisfied per the Gate satisfaction rule; a satisfied gate is not a skip (the plan dispatches under the normal rules).
- Certification: run `python3 scripts/plan_readiness.py <plan>` once per open plan. The exit status of scripts/plan_readiness.py is the certification oracle; exit 0 marks the plan digest-intact on current bytes. A drifted result records the needs-recert mark instead of a silent skip, so the survey output shows why a drifted plan remains eligible (added 2026-09-24, P54; the D1 needs-recert rule owns the dispatchability semantics).
- Plan coverage: for each open backlog item, grep the top-level plans for the item's filename. An item referenced by at least one top-level plan is plan-covered.
- Parked-dependency liveness arm: for each `parked_dependencies` entry (the State file field), classify mechanically. First run the clear arms BEFORE any classification, so a resolved entry is removed from the array and only a surviving entry is classified: the plan-absent clear (the entry's plan absent from the top-level plans survey as parked, completed, or archived), the resolution clear (the branch probes showing the wait resolved: zero commits ahead on the resolving ref, or the recorded `landed_as` squash commit now an ancestor of the default branch, or the name unresolvable in both ref namespaces with the plan otherwise dispatchable — the unresolvable-ref clear requires the name to be unresolvable in BOTH namespaces with the plan otherwise dispatchable, so an origin-ref wait can never be erased by a local-namespace probe failure), each performed as a targeted state edit with the reason recorded in `decision_reason`. The branch probes: `git rev-parse --verify refs/heads/<blocked_on>` first and `git rev-parse --verify refs/remotes/<blocked_on>` when the local probe fails (the bare `blocked_on` name is prefixed into each namespace; remote-qualified names like `origin/foo` resolve in the remote namespace), then `git rev-list --count <default-branch>..<resolving-ref>` (ahead count) and `git log -1 --format=%ct <resolving-ref>` (last touch) against the ref that resolved, plus the live-work check (an execute-plan session manifest for the plan under the resolved tmp_dir fresher than one cadence period, or a fresh execution claim for the plan). The arm also owns the refusal-cycle reset mechanically: when an entry carries `refused_tip` and the resolving-ref tip differs from it, the arm resets `refusal_count` to 0 in the same targeted-edit pass (the branch has moved since the last refusal, so the refused gate is re-testable). A surviving entry is classified: the actionable conjuncts are evaluated FIRST and win over the aging states — a ref resolving in either namespace with a positive ahead count and a negative live-work check is actionable regardless of age; only a non-actionable entry is classified by age as stale (its `since` at or past the stale threshold of two cadence periods) or waiting (younger), with the entry's `deferred_until` honored throughout (a future `deferred_until` suppresses the actionable proposal and D1's unblock selection until it passes). Each classification rides the survey output as a `parked-dep:<plan-slug>:<state>` token in `decision_reason` (the class-token precedent); a stale classification proposes resume-or-close in the survey output, an actionable one proposes the unblock dispatch. An entry older than six cadence periods with a negative live-work check and no future `deferred_until` records `turn_error: parked-dependency-entry-stale` naming the entry (joining the human clear procedure's escalation list), so a lost clear write degrades to a visible alert instead of a silent livelock. Refusal-cycle bound: when an entry's `refusal_count` reaches 3, the survey arm classifies the entry as needing human disposition instead of actionable (no further auto re-selection) and the turn records `turn_error: parked-dependency-unblock-stuck` naming the entry (joining the human clear procedure's escalation list), so a doomed dependency branch cannot re-dispatch a child every cadence forever.
- Archived-coverage warn arm: an open top-level backlog item whose basename appears in any archived plan's origins block is reported as plan-uncovered-with-archived-coverage (warn and continue; this arm never changes skip semantics and never blocks the turn). Run `python3 scripts/check_plan_origins_closed.py` without `--plan` for the corpus-wide scan (it exits 0 with one warning per survivor; the archived plan's own origins block is the only gate the archive step enforces, and this survey arm owns the corpus-wide stragglers).
- Quota snapshot: run the harness detection then the probe exactly as Step 4 prescribes (`python3 scripts/harness_detection.py` first, repo-local copy then the deployed home copy; when it reports `harness: none` the snapshot's source is `skipped-unsupported-harness` and the probe does not run; otherwise run `python3 scripts/quota_window_probe.py` once), and carry the primary-window reading into Step 3 as decision input: percent used, minutes to reset, and the source, one of probe | unknown | skipped-unsupported-harness. This is the decision-time reading Step 3 records per lane as `quota_at_decision`; Step 4's landed wording and its own probe invocation stay verbatim: the runtime-fit rule is fire-time-relative and keeps computing its own minutes at the planned fire time, so this survey run is an additional reading taken for the decision layer only. The probe report's used_percent key and its minutes_remaining key are the reading this decision layer consumes; the state shape's percent_used and minutes_to_reset are this snapshot's transcription of those two keys.
- Quota display caveat: a runtime or desktop quota display may render a cached server snapshot rather than a live counter (multi-minute cache lifetimes and integer rounding are common), so a display value that stays unchanged across a busy interval is never by itself evidence that consumption stopped; it can reflect display staleness or a legitimately small deduction. The probe's reading is the decision source, and when only a display is available, prefer its freshest manually refreshed value, never one older than the refresh cadence (display age is operator-attested, never measured: absent a refresh observed during the conversation, record the reading as unknown regardless of the claimed freshness; a display value older than about 5 minutes is recorded as unknown rather than used), and record the display staleness as an annotation on the snapshot's recorded source value (probe | unknown | skipped-unsupported-harness), never as a competing source kind.

- Friction-audit consult: read the audit state's `next_due` (the state file under the resolved `friction_audit_dir`; a missing audit state file is a cold start and reads due) during the survey; when due and lanes allow, dispatch at most one audit child with the authoring dispatch discipline (claim check, `children[]` entry, park/retain on quota pressure), idle/off-peak preferred; hard caps: at most 2 sub-agents and a total token budget recorded in the audit state; dedupe-and-fold: evidence on existing items becomes a dated evidence line, new items only after checking open plus completed plus deferred. The audit child occupies the authoring lane (`G1a`); its kind, completion evidence, and progress witness are the state-file and failure-cap arms below. Park arbitration: the audit park writes only when the `pending_dispatch` slot is null; when a retained execute or author dispatch already occupies it, the audit dispatch is skipped this turn with reason `pending-dispatch-occupied` recorded in `decision_reason` (the retained entry is never silently overwritten), and the consult re-fires next turn because its `next_due` still reads due. The concrete data map (db path, table shapes, log location and event schema, noise filter, provider code meanings) lives in the runtime overlay's audit recipe; this skill stays runtime-agnostic.
- Child-outcome check: run the failure-detection procedure from "Failure detection and the failure cap" at the end of this step, including its read-back of the persistent memory index (for alert notes left by turns whose state write failed), so its outputs are on file before Step 2 evaluates the guards in fixed order.
- Memory index: when the runtime provides a persistent memory index, read plan dependency-chain order and backlog priority groups from it; otherwise use the oldest-first defaults. Also read back `loop-parent-missing` notes: one whose `repo` key matches the resolved repository root means the last dispatched child may not have re-armed the parent; re-list first, and when an ENABLED automation matching the recognition rule (defined at Step 0) already exists, adopt its id into `parent_automation_id` with the Step 0 adoption guards, clear the note, and skip the re-arm; only when the listing shows no such parent, re-arm per the runtime overlay's recipe, clear the note, and record the recovery in the turn output, clearing any standing re-arm intent record in the same targeted edit that records the recovered `parent_automation_id` (the writer-class entry's named clear for this path; the field paragraph owns the intent's lifecycle). The read-back also surfaces repo-matching `successor-chain-failed` notes and records the re-chain decision for the note's target (the target re-enters the Step 3 selection). A repo-matching `pricing-verification-failed` note surfaces in the survey read-back like the other notes above, so a stale pricing pin is visible to the turn; the runtime overlay's Quota leg owns clearing it on a successful re-verification. The survey read-back also owns the park-proposal lifecycle: when a `park_proposals` state entry's plan is absent from the fresh top-level survey (a human parked it per `docs/history/plans/deferred/README.md`, or it executed), the turn clears that entry from the state file and deletes the repo-matching `park-proposal-<plan-basename>` note after its identity confirms the target (the note's `repo` key must match the resolved repository root, and the target is confirmed by the body's `plan` field for fixed-type bodies or by the name's own plan-basename suffix for legacy parameterized-type bodies: one note read, no listing; the deterministic name plus that confirmation makes the clear targeted, so a note naming a different plan is never deleted); a legacy note whose body carries the parameterized type literal (`park-proposal-<plan-basename>` as the type) matches the same clear by its name suffix alone and is deleted on sight, so notes written before the fixed body type self-migrate without a separate migration pass; a later revival starts a fresh first-proposed date. A repo-matching `park-proposal-*` note whose plan is surveyed but whose state entry is gone (cap eviction or state-file loss) is deleted too. The sweep is name-derivable only: a note whose plan is absent from the survey AND whose state entry is gone has no derivable name under the one-note-read no-listing convention, so that combination is the one case that can leave an orphaned note until the plan revives (its reappearance makes the basename derivable and the surveyed-but-entry-gone rule deletes it) or a human clears it; the no-orphan property is claimed only for the name-derivable combinations. When a proposed plan's gate now reads satisfied per the Gate satisfaction rule, the next turn clears that plan's `park_proposals` entry and memory note the same as a survey absence.

Evaluate in this order; each guard names its observable signal. The proposed slot for this turn's child is now plus 5 minutes, unless the quota leg (Step 4) later moves it.

### Step 3: decision

Apply the rules in this order; the two lanes decide independently, so one turn may dispatch an execution child AND an authoring child (at most one of each).

Loop-mode enforcement runs before D1, D4, and D2: the per-lane decision reads `loop_mode` from the state file first, and a non-dual mode resolves the excluded lanes to D3 with the mode recorded in that lane's `decision_reason`: authoring-only resolves D1 and D4 to D3, execution-only resolves D2 to D3; `dual` and `null` are inert (today's behavior). Cycle-gate enforcement runs beside the loop-mode enforcement: when `authoring_cycle_gate` is armed (a non-null gate value), both lanes resolve to D3 with the reason `cycle-gate-armed` recorded in `decision_reason` (the field paragraph owns the semantics).

- `D1 (execute)`: when all guards pass except at most `G1a`, the execution lane (`G1e`) is free, and an open plan exists, schedule an execution child for the best open plan, skipping plans the memory index marks dependency-blocked when selecting: memory dependency-chain order when available, otherwise the oldest basename among digest-intact plans, otherwise the oldest open plan whose re-certification the child's PRE-STEP performs. Queue and priority ordering (added 2026-09-24, P54): when `execution_queue` is non-empty, its head is the selection candidate, still through the guards, the certification oracle, and the skip rules; an invalid head pops and the next head is evaluated, each pop recorded in `decision_reason`; when `execution_priority` is set, this ordering reads it before the memory dependency-chain order; a dispatching turn or child pops the dispatched head and records the pop. Needs-recert dispatchability (added 2026-09-24, P54): a plan failing the certification oracle on a stale `source_digest` is not dropped from selection: mark it needs-recert on the selection record (or its `execution_queue` entry) and keep it dispatchable, the child's PRE-STEP re-certification being the designed drift handler; record the drift reason in `decision_reason`; keep the hard skip only for a plan that fails re-certification after the pre-step (the existing execute-plan behavior). Treat a plan skipped as dependency-blocked whose marked blocker is no longer an open plan anywhere under the resolved plans_dir (completed or absent) as not blocked (self-healing), so a stale memory mark cannot starve the queue; a blocker still present under the deferred/ subdirectory keeps the plan blocked. D1 also skips externally gated plans (the Step 1 classification) exactly like dependency-blocked ones; when nothing remains after the two skips (every open plan is dependency-blocked, externally gated with an unsatisfied gate, or both), fall through to D2. Parked-dependency integration (added 2026-09-25): a plan named by a live parked_dependencies entry joins the dependency-blocked skip class with the same self-heal (live means any entry not yet cleared by the field paragraph's clear arms; the survey arm's resolution clear releases the plan without human action); when the survey arm marked an entry actionable, the execution lane selects the parked-dependency unblock dispatch for that entry before ordinary D1 selection, still through the guards, the quota leg, the landing gate, and the rate-pressure condition; waiting and stale entries are sanctioned dependency reasons in the must-dispatch exemption list, so no dispatch-defect `turn_error` fires for a lane held by a live entry; when two entries are actionable in one survey, the oldest-`since`-first order selects the unblock target. The gated skip carries the mirrored self-heal: a gated plan whose gate satisfies the Gate satisfaction rule is no longer skipped and becomes dispatchable again without human action, so a satisfied gate cannot starve the queue. The execution lane must not idle by choice: when the lane is free and a dispatchable open plan exists, D1 dispatches; a turn that ends with the lane free and no dispatch while a dispatchable plan exists, without a guard, quota, dependency, external-gate, rate-pressure, loop-mode, or cycle-gate reason (the cycle-gate reason per the authoring_cycle_gate field paragraph, Step 3 cycle-gate enforcement, added 2026-09-26 P64 r4), records a `turn_error` (dispatch defect) so the idle lane is visible to the next turn. Rate-pressure deferral: when `rate_pressure` (the derived count defined in State file) is at or above 3, the turn defers execution dispatch: it writes the decided dispatch to `pending_dispatch` only when `pending_dispatch` is not already set (a retained entry the Step 1 reader kept stands, so a retained target is never silently overwritten by a different fresh selection) (`kind`, `target`, `payload_slug`, `decided_at` per the existing field paragraph in State file, mirroring the decided-but-could-not-schedule writer semantics) and records the deferral with reason `rate_limited` in `decision_reason`; the deferral is a sanctioned reason in the must-dispatch exemption list (no dispatch-defect `turn_error`), alongside the guard, quota, dependency, external-gate, and loop-mode reasons. The threshold is exact: a state with 3 events within the last 24 hours defers; with 2 it dispatches. Landing gate (sequential landing discipline): the execution lane dispatches only when zero outstanding unlanded runs survive the Step 1 resolution and no surviving repo-matching `pending-landing-<plan-slug>` note remains (the gate is global: a record or note of either lane blocks it); D1's selection and its skip outcomes are computed before the landing-gate resolution, so D4 still evaluates D1's skip outcomes when the gate defers the dispatch. When one is outstanding, D1 resolves to the landing-completion work first, at most once per turn (when both lanes resolve to it, the first lane's exit decides: the second lane's gate re-reads the resolution and defers with the same reason literal when the record or any note survives); a fresh `G3b` hold defers the affected lane or lanes per its own rule and the completion work waits for a turn whose `G3b` is clear. ## Failure detection and the failure cap

- The child-outcome check runs at the end of Step 1 (survey) and writes its `outcome`, `outcome_checked_at`, `progress_mark`, `consecutive_failures`, and `alert` updates to the state file before Step 2 evaluates the guards in fixed order; Step 6's whole-document rewrite carries them forward, so `G2 (failure cap)` arms on the tripping turn, not one turn late.
- Each turn checks the oldest `pending` child whose `fire_at` plus 6 hours has passed.
- Early authoring outcome check: every pending authoring child whose `fire_at` has passed (idle-time: once the idle-task listing no longer shows it queued or running) gets the progress predicate evaluated each turn, and `outcome: progress` plus `outcome_checked_at` are recorded on observe; the 6-hour horizon stays the failure threshold for children that never show progress.
- Idle-time children are covered too: a `pending` child recorded with a null `fire_at` (idle-time dispatch) gets its progress check once the runtime's idle-task listing (named in the overlay) no longer shows it queued or running. Six hours after `created_at` is the lane-hold horizon only: a child still shown queued or running at that mark is not failed and accrues no failure credit; one that vanished from the listing without progress is failed like any other child. Exception for evidenced provider-side stops: a child whose session demonstrably ended on a retryable provider error (for example a surfaced 429 `rate_limited` stop) is requeued by the deciding turn or the next scheduler turn without holding the six-hour horizon, whether or not the stop preceded progress; an execution child is not re-armed while the Step 3 rate-pressure deferral condition holds, and the requeue's operative scheduler-side rule while the deferral condition holds is the next scheduler cadence boundary (re-evaluated each turn; bounded unless new rate-limited events keep landing), falling back to the quota leg's reset-anchored slot (fire after `reset_at_epoch`) when a pause window was active; the child's named resume condition (backoff elapsed or the next defined boundary) is advisory only, describing the child's own in-run resume behavior rather than binding the scheduler-side requeue fire time, and the evidenced provider-side stop accrues no failure credit: the cap counts child-behavior failures, not provider incidents. Requeue evidence is the surfaced error record, a budget-guard pause decision covering the child's run window, the timestamped rate-limited stop lines in the child's execute-plan session manifest (the machine surface for the rate-limited case), or a structured rate-limited end-of-run report (operator-facing only: no report-retrieval primitive exists and none is assumed); the manifest-stop-line and structured-report evidence qualify only with an end corroborator: no live claim or launch is observable for the child (the discovery arm's claim check comes back empty), or the session manifest is stale past one cadence period; a graceful rate-limited end under this exception (the run ending with the plan unarchived and the machine manifest left active) accrues no failure credit and requeues per the exception's rules like any other evidenced provider-side stop.
- In-session entries are covered too: an `(in-session)` child entry (Step 5's in-session dispatch mode) that never records an outcome is marked `failed` when the arm's horizon passes (the same six-hour horizon), so the failure cap sees repeated dead deciding turns.
- Rate-limited event ingestion: when the child-outcome check observes a surfaced 429 `rate_limited` stop on a child (the same stop evidence the evidenced provider-side stop exception above reads), it appends a `rate_limited_events` entry of kind `turn` (target: the child's `target`; the entry's `ts` is the surfaced stop record's own timestamp) to the state file. Independently, on every read-back while the child is pending, it appends kind `launch` entries for rate-limited stop lines found in the pending child's execute-plan session manifest free-text lines (the manifest at `execute-plan/<plan-slug>/manifest.md` under the resolved tmp directory; the same repository-relative manifest path inside the recorded worktree when the entry's `worktree` field is set, the primary checkout's resolved tmp directory staying the fallback when the field is null or the per-run file is absent; the `budget_skip` precedent for session-manifest free-text lines as event evidence; each `launch` entry's `ts` is the stop line's own timestamp and its `target` is the child target; a rate-limited stop line is a line-initial rate_limited: token followed by an ISO timestamp, the pinned writer-side format, so the execute-plan writers and this ingester cannot drift), so every scheduler turn while the child is pending ingests the child's own launch-side rate-limit stops whether or not the surfaced stop fired. Ingestion is deduplicated: entries are ingested only for stop evidence not yet recorded (each entry is keyed on the `{ts, kind, target}` triple -- timestamp, kind, and target -- and an append is skipped when the rolling dedup ledger already carries the same triple (the ledger, not the capped array, is the dedup basis)), so a pending child's repeated read-backs cannot re-append the same event and inflate `rate_pressure`; the dedup applies to both `turn` and `launch` kinds, and one underlying stop is ingested once across kinds: cross-kind suppression matches on the child target plus a bounded time window, not exact-timestamp equality (a `launch` stop line whose timestamp falls within 15 minutes of an existing same-target `turn` entry's `ts` is suppressed, and vice versa). The append follows the entry schema and the 20-entry oldest-evicted cap defined in "State file"; the derived rate_pressure count is what Step 3's deferral reads (defined once in State file).
- Progress for an authoring child means a top-level plan now references the target item or the item left the backlog top level.
- Progress for an execution child means the target plan left the top-level plans directory (archived), or the target plan's checked-checkbox count increased beyond the recorded `progress_mark`. The checkbox-grep consumer is scoped to plan-execution children (added 2026-09-25): an unblock child's progress is its manifest-refresh witness, never a checkbox count against the serialized plan — manifest refreshes count as progress for unblock children, and the evidenced-completion pair (ledger entry cleared plus the serialized plan present in `execution_queue`) is the unblock child's terminal witness. The checkbox count is stored in `progress_mark` at every survey turn while the child is pending (one grep per turn) and at each outcome check, counting with `grep -cE '^[[:space:]]*-[[:space:]]\[[xX]\]' <plan>` (the escaped literal brackets are load-bearing: an unbracketed `[xX]` class matches the bare letter after the dash-space and never matches a `- [x]` line; measured at authoring: 0 matches on pure checked-checkbox lines vs 2 for the corrected pattern) (added 2026-09-24, P57): the checkbox count is resolved inside the entry's recorded `worktree` when that additive field is set, else the primary checkout's file; when the entry's `worktree` field is set but the recorded path no longer exists, the read falls back to the primary checkout's file. Per-run archival visibility: the archival arm is read ref-based, using the landed-commit-test form `git cat-file -e refs/heads/<default>:<archived-plan-path>`, so a compare-and-swap landing is visible from any checkout, a worktree-isolated child checking boxes in its own tree and a CAS landing never updating the checking turn's working tree.
- Progress for an audit child means the audit state file's digest and `next_due` updated after the recorded `created_at` (the same witness as its completion evidence, the state-file arm), so an audit child neither accrues credit while running nor holds the lane after finishing.
- Fast re-dispatch of a stalled execution child, with a single sound trigger aligned with the release arms: a pending execution child is fast-re-dispatched when both progress evidence and stop evidence hold, plus a negative live-session check. Progress evidence: its checkbox count exceeds the `progress_mark` stored at the previous turn, or its outcome is already `progress`. Stop evidence: the execute-plan session manifest under the resolved tmp directory (facts key `tmp_dir`, `docs/tmp/` default) at `execute-plan/<plan-slug>/manifest.md` (the same per-run resolution the rate-limited ingestion bullet applies) carries an `updated:` timestamp older than one cadence period, or it carries a timestamped rate-limited stop line (the same lines the evidenced provider-side stop exception above names as requeue evidence), so a graceful mid-run rate-limited end (which may occur after progress) is caught without waiting a cadence period; a live child refreshes the manifest on every orchestrator update, so the staleness conjunct is what prevents re-dispatching a live child that is merely between manifest writes. Live-session check: the re-dispatch goes through the Step 5 lane-guard re-evaluation with the discovery arm (the execute-plan claim check) mandatory before the replacement dispatch, so a live child whose manifest gap exceeded one cadence period is caught by the claim check, not replaced. The re-dispatch replaces the old child record with the new entry (same target, new `created_at`, `resume_count` incremented on the new entry) so two records for one plan never coexist, and accrues no failure credit when the progress evidence held; the fresh child enters via the existing PRE-STEP re-cert and the payload's resume rule. Two bounds gate the replacement: it is deferred while the Step 3 rate-pressure deferral condition holds (`rate_pressure` at or above 3), the same pressure gate the requeue path applies; and precedence between the two re-arm paths: a child requeued under the evidenced provider-side stop exception is not fast-re-dispatchable until its pushed requeue fire time has elapsed, and when a replacement does fire it supersedes (not leaves behind) any armed requeue automation for the same child.
- Otherwise, and only when no armed child targets the same work, the child is `failed`.
- Stand-down carve-out (beside the evidenced provider-side stop exception above, the same spirit: an evidence-backed outcome accrues no failure credit): when an execution child's zero checkbox progress is explained by its own recorded stand-down (the target plan's own first task prescribed an edit-nothing stand-down because the plan's external gate is unsatisfied), the outcome stays the documented enum value `failed`, `outcome_reason` is set to `stand-down`, and `consecutive_failures` is not incremented. Machine test, three conjuncts, all required and named: (1) `.ai-playbook/last-stand-down.json` is present and its `plan` key names the target plan path, the file's literal key schema being `{"plan": "<plan path>", "reason": "<gate-unsatisfied-reason>", "date": "<iso date>"}` (an ad-hoc-worktree child writes the json into the primary checkout, the only checkout the checking turn reads); the json file is the machine-readable retrieval surface; no report-retrieval primitive exists and none is assumed; (2) the target plan file is unchanged since dispatch: a git comparison of the plan path's current sha against the children entry's `dispatch_plan_sha`.; (3) the checking turn re-runs the Gate satisfaction rule (Step 1) on the target plan's own current bytes and the gate reads unsatisfied: a child claiming stand-down on a plan whose gate now reads satisfied (a stale dispatch, the gate having satisfied between dispatch and check) or on a plan whose header block carries no External gate line accrues credit normally, the one conjunct the checking turn evaluates itself rather than trusting child-asserted evidence The child's final report opening with the literal `STAND-DOWN:` marker line (`STAND-DOWN: <plan-path> <gate-unsatisfied-reason>`, the reporting duty the execution-child payload blueprint in `agents/skills/maintenance/prompt-templates.md` carries) is the human-visible witness quoted in the turn output, produced by that payload duty; it is not part of the machine test: report text alone never qualifies, the exclusion coming from the json conjunct rather than from marker matching (the marker stays a literal line prefix matched exactly, so a broken child whose report merely contains the word stand-down anywhere is not the witness). The cap's count includes only children entries whose `outcome_reason` is not `stand-down`, so a stand-down-explained zero-progress outcome can never alone trip the alert. An authoring child never qualifies (its `dispatch_plan_sha` is null). The checking turn consumes the json file it checked (deletes or clears it) only after the stand-down outcome record write has survived (consuming earlier would lose the evidence inside the state write's crash window), so a stale file cannot qualify a later child. The turn output echoes the consumed json's contents (its plan, reason, and date values) for triage alongside the quoted marker witness. A genuinely broken child that wrote no json file does not qualify, so real stall loops keep accruing credit.
- Carve-out witness: a stand-down outcome accrues nothing, so a stand-down followed by two real failures holds `consecutive_failures` at 2, below the three-strike cap; three stand-down outcomes alone never trip the alert; a child whose report opens with the marker while its plan file changed since `dispatch_plan_sha` does NOT qualify and accrues credit normally; a child whose json satisfies conjuncts 1 and 2 while the plan's gate re-reads satisfied under conjunct 3 does not qualify and accrues credit normally; a child whose report contains the word stand-down anywhere but wrote no json file does not qualify: via the json conjunct, not marker matching (a conforming child that omits the marker also omits the json, the payload duty coupling the two).
- Children-entry schema additions (both additive under schema 4, no version bump): `outcome_reason` is an optional string, `null` by default, carrying the value `stand-down` per the stand-down carve-out above, the value `covered-stand-down` per the authoring covered-stand-down carve-out (State file), and the value `deferred` per the parked-dependency unblock deferral (the deferral write names the refused gate in the same field, and `deferred` is excluded from failure credit only while the value names the refused gate, so persistent refusals park with the bounded re-selection of the refusal-cycle rule instead of accruing credit); `dispatch_plan_sha` is the target plan file's sha256 recorded at dispatch time (Step 5), `null` for authoring children.
- Progress resets `consecutive_failures` exactly as archival does, so a multi-session plan never false-trips the cap; failure increments it.
- At three or more consecutive no-progress child outcomes the turn writes `alert` (with `tripped_at` and the reason) and stops scheduling children until a human clears the alert. The turn also notes the alert in the agent's persistent memory index when one exists.
- Turn-level tripwire for the broken-parent case: Step 6 runs in a best-effort guard of its own, so even a turn that fails before scheduling records `last_run_at` and a `turn_error` reason. The schema counter `consecutive_turn_errors` keeps the streak alive across whole-document rewrites: a turn ending with a `turn_error` record writes the previous value plus one, a fully successful turn resets it to 0, and three consecutive `turn_error` records (or, when the state writes themselves fail, three consecutive turns with no successful state update detected via the memory-note streak in the Signal split below) write the same `alert` and trigger the same stop as the child cap. When the trip comes through the `turn_error` records, the alert's reason records the most recent `turn_error` reason (for example `duplicate-parent-candidate`), so the clear procedure's duplicate-removal clause always binds when that reason tripped the alert; the write-failure-streak trip keeps the write-failure reason described in the Signal split below. A turn whose turn_error is recovered in-turn (the parked intent discharged and the carrier re-armed by a create verified per the ENABLED recognition rule and ENABLED verification) resets `consecutive_turn_errors` to 0 in the same targeted edit that records the recovery, quotes the verification in the recovery note, and the turn's Step 6 write carries the reset forward; absent the verified re-arm, the streak stands.
- Signal split: the file counter covers turns that ran but failed (`turn_error` records); when the state write itself fails, the file cannot count the turn. For that case the turn writes or updates a memory note `{"type": "turn_tripwire", "consecutive_write_failures": N, "repo": "<resolved repository root>"}` in the agent's persistent memory index on every failed state write (N is the running count of consecutive failed writes; below the threshold a successful state write resets the streak and clears the note), and the Step 1 read-back of the memory index arms the same stop as the child cap only when a note whose `repo` key equals the resolved repository root records N >= 3, resolving the turn to D3 with nothing scheduled; the `repo` key is the cross-repo discriminator, so a streak note written by another repository's scheduler never arms this repository's tripwire. When the read-back finds N >= 3, a successful Step 6 state write converts the streak into the persisted `alert` (reason: write-failure streak) instead of silently clearing the note; the stop then holds until the documented human-clear procedure runs. The `last_run_at` staleness check in the State file section remains a further rail for a dead or silent parent.
- Silent-turn classification may consult the store-level darkness-triage witness where the runtime overlay provides one (it reads the app logs for session-store integrity events around the child's run window, separating a child that outlived its parent record from a parent that actually died); this skill stays runtime-agnostic, so the concrete log event names and the read procedure live in the overlay, not here.

## Invariants

- The maintenance loop never pushes to origin.
- It never blocks on questions; unattended turns decide and proceed.
- It schedules at most one child per lane per scheduler turn (one execution and one authoring at most; an audit child occupies the authoring lane, so a turn whose dispatch is the audit child dispatches no authoring child that turn, and at most one audit child runs per cadence period).
- Fleet cap (added 2026-09-24, P54, superseding the single-lane in-flight caps and the strictly-sequential wording): the repo holds at most 4 concurrent children across mixed kinds (execution, authoring, audit; the `G1e` / `G1a` fleet counting); the authoring and audit lanes fill the fleet slots; executions are fleet members, execution children run in per-execution ad-hoc worktrees off the default-branch snapshot (isolation landed 2026-09-24, P57); merge-lock landings stay serialized under the merge landing lock.
