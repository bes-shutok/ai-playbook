## Failure detection and the failure cap

- The child-outcome check runs at the end of Step 1 (survey) and writes its `outcome`, `outcome_checked_at`, `progress_mark`, `consecutive_failures`, and `alert` updates to the state file before Step 2 evaluates the guards in fixed order; Step 6's whole-document rewrite carries them forward, so `G2 (failure cap)` arms on the tripping turn, not one turn late.
- Each turn checks the oldest `pending` child whose `fire_at` plus 6 hours has passed.
- Early authoring outcome check: every pending authoring child whose `fire_at` has passed (idle-time: once the idle-task listing no longer shows it queued or running) gets the progress predicate evaluated each turn, and `outcome: progress` plus `outcome_checked_at` are recorded on observe; the 6-hour horizon stays the failure threshold for children that never show progress.
- Idle-time children are covered too: a `pending` child recorded with a null `fire_at` (idle-time dispatch) gets its progress check once the runtime's idle-task listing (named in the overlay) no longer shows it queued or running. Six hours after `created_at` is the lane-hold horizon only: a child still shown queued or running at that mark is not failed and accrues no failure credit; one that vanished from the listing without progress is failed like any other child. Exception for evidenced provider-side stops: a child whose session demonstrably ended on a retryable provider error (for example a surfaced 429 `rate_limited` stop) is requeued by the deciding turn or the next scheduler turn without holding the six-hour horizon, whether or not the stop preceded progress; an execution child is not re-armed while the Step 3 rate-pressure deferral condition holds, and the requeue's operative scheduler-side rule while the deferral condition holds is the next scheduler cadence boundary (re-evaluated each turn; bounded unless new rate-limited events keep landing), falling back to the quota leg's reset-anchored slot (fire after `reset_at_epoch`) when a pause window was active; the child's named resume condition (backoff elapsed or the next defined boundary) is advisory only, describing the child's own in-run resume behavior rather than binding the scheduler-side requeue fire time, and the evidenced provider-side stop accrues no failure credit: the cap counts child-behavior failures, not provider incidents. Requeue evidence is the surfaced error record, a budget-guard pause decision covering the child's run window, the timestamped rate-limited stop lines in the child's execute-plan session manifest (the machine surface for the rate-limited case), or a structured rate-limited end-of-run report (operator-facing only: no report-retrieval primitive exists and none is assumed); the manifest-stop-line and structured-report evidence qualify only with an end corroborator: no live claim or launch is observable for the child (the discovery arm's claim check comes back empty), or the session manifest is stale past one cadence period; a graceful rate-limited end under this exception (the run ending with the plan unarchived and the machine manifest left active) accrues no failure credit and requeues per the exception's rules like any other evidenced provider-side stop.
- In-session entries are covered too: an `(in-session)` child entry (Step 5's in-session dispatch mode) that never records an outcome is marked `failed` when the arm's horizon passes (the same six-hour horizon), so the failure cap sees repeated dead deciding turns.
- Rate-limited event ingestion: when the child-outcome check observes a surfaced 429 `rate_limited` stop on a child (the same stop evidence the evidenced provider-side stop exception above reads), it appends a `rate_limited_events` entry of kind `turn` (target: the child's `target`; the entry's `ts` is the surfaced stop record's own timestamp) to the state file. Independently, on every read-back while the child is pending, it appends kind `launch` entries for rate-limited stop lines found in the pending child's execute-plan session manifest free-text lines (the manifest at `execute-plan/<plan-slug>/manifest.md` under the resolved tmp directory; the same repository-relative manifest path inside the recorded worktree when the entry's `worktree` field is set, the primary checkout's resolved tmp directory staying the fallback when the field is null or the per-run file is absent; the `budget_skip` precedent for session-manifest free-text lines as event evidence; each `launch` entry's `ts` is the stop line's own timestamp and its `target` is the child target; a rate-limited stop line is a line-initial rate_limited: token followed by an ISO timestamp, the pinned writer-side format, so the execute-plan writers and this ingester cannot drift), so every scheduler turn while the child is pending ingests the child's own launch-side rate-limit stops whether or not the surfaced stop fired. Ingestion is deduplicated: entries are ingested only for stop evidence not yet recorded (each entry is keyed on the `{ts, kind, target}` triple -- timestamp, kind, and target -- and an append is skipped when the rolling dedup ledger already carries the same triple (the ledger, not the capped array, is the dedup basis)), so a pending child's repeated read-backs cannot re-append the same event and inflate `rate_pressure`; the dedup applies to both `turn` and `launch` kinds, and one underlying stop is ingested once across kinds: cross-kind suppression matches on the child target plus a bounded time window, not exact-timestamp equality (a `launch` stop line whose timestamp falls within 15 minutes of an existing same-target `turn` entry's `ts` is suppressed, and vice versa). The append follows the entry schema and the 20-entry oldest-evicted cap defined in "State file"; the derived rate_pressure count is what Step 3's deferral reads (defined once in State file).
- Progress for an authoring child means a top-level plan now references the target item or the item left the backlog top level.
- Progress for an execution child means the target plan left the top-level plans directory (archived), or the target plan's checked-checkbox count increased beyond the recorded `progress_mark`. The checkbox-grep consumer is scoped to plan-execution children (added 2026-09-25): an unblock child's progress is its manifest-refresh witness, never a checkbox count against the serialized plan: manifest refreshes count as progress for unblock children, and the evidenced-completion pair (ledger entry cleared plus the serialized plan present in `execution_queue`) is the unblock child's terminal witness. The checkbox count is stored in `progress_mark` at every survey turn while the child is pending (one grep per turn) and at each outcome check, counting with `grep -cE '^[[:space:]]*-[[:space:]]\[[xX]\]' <plan>` (the escaped literal brackets are load-bearing: an unbracketed `[xX]` class matches the bare letter after the dash-space and never matches a `- [x]` line; measured at authoring: 0 matches on pure checked-checkbox lines vs 2 for the corrected pattern) (added 2026-09-24, P57): the checkbox count is resolved inside the entry's recorded `worktree` when that additive field is set, else the primary checkout's file; when the entry's `worktree` field is set but the recorded path no longer exists, the read falls back to the primary checkout's file. Per-run archival visibility: the archival arm is read ref-based, using the landed-commit-test form `git cat-file -e refs/heads/<default>:<archived-plan-path>`, so a compare-and-swap landing is visible from any checkout, a worktree-isolated child checking boxes in its own tree and a CAS landing never updating the checking turn's working tree.
- Progress for an audit child means the audit state file's digest and `next_due` updated after the recorded `created_at` (the same witness as its completion evidence, the state-file arm), so an audit child neither accrues credit while running nor holds the lane after finishing.
- Progress for a re-triage child means the re-triage record's corpus digest and `next_due` updated after the recorded `created_at` (the same witness as its completion evidence, the state-file arm), so a re-triage child neither accrues credit while running nor holds the lane after finishing.
- progress for a registry-task child means its state record next_due or last_run_at updated after the entry's created_at (the same witness as its completion evidence, the state-file arm), so a registry-task child neither accrues credit while running nor holds the lane after finishing.
- Progress for an ad-hoc child (added 2026-10-06, the two-mode loop policy plan Task 3) means the run's recorded worktree branch tip advanced or the target item left the backlog top level: the deciding turn records the ad-hoc run's worktree path and branch tip on its own `adhoc` `children[]` entry through the in-session write pair's scheduler-turn class, `progress_mark` carrying the tip like the checkbox precedent, and the predicate compares the recorded tip across turns; the landing receipt is the terminal witness per the completion-evidence clause (the state-file arm's ad-hoc evidence).
- Fast re-dispatch of a stalled execution child, with a single sound trigger aligned with the release arms: a pending execution child is fast-re-dispatched when both progress evidence and stop evidence hold, plus a negative live-session check. Progress evidence: its checkbox count exceeds the `progress_mark` stored at the previous turn, or its outcome is already `progress`. Stop evidence: the execute-plan session manifest under the resolved tmp directory (facts key `tmp_dir`, `docs/tmp/` default) at `execute-plan/<plan-slug>/manifest.md` (the same per-run resolution the rate-limited ingestion bullet applies) carries an `updated:` timestamp older than one cadence period, or it carries a timestamped rate-limited stop line (the same lines the evidenced provider-side stop exception above names as requeue evidence), so a graceful mid-run rate-limited end (which may occur after progress) is caught without waiting a cadence period; a live child refreshes the manifest on every orchestrator update, so the staleness conjunct is what prevents re-dispatching a live child that is merely between manifest writes. Live-session check: the re-dispatch goes through the Step 5 lane-guard re-evaluation with the discovery arm (the execute-plan claim check) mandatory before the replacement dispatch, so a live child whose manifest gap exceeded one cadence period is caught by the claim check, not replaced. The re-dispatch replaces the old child record with the new entry (same target, new `created_at`, `resume_count` incremented on the new entry) so two records for one plan never coexist, and accrues no failure credit when the progress evidence held; the fresh child enters via the existing PRE-STEP re-cert and the payload's resume rule. Two bounds gate the replacement: it is deferred while the Step 3 rate-pressure deferral condition holds (`rate_pressure` at or above 3), the same pressure gate the requeue path applies; and precedence between the two re-arm paths: a child requeued under the evidenced provider-side stop exception is not fast-re-dispatchable until its pushed requeue fire time has elapsed, and when a replacement does fire it supersedes (not leaves behind) any armed requeue automation for the same child.
- Otherwise, and only when no armed child targets the same work, the child is `failed`.
- Stand-down carve-out (beside the evidenced provider-side stop exception above, the same spirit: an evidence-backed outcome accrues no failure credit): when an execution child's zero checkbox progress is explained by its own recorded stand-down (the target plan's own first task prescribed an edit-nothing stand-down because the plan's external gate is unsatisfied), the outcome stays the documented enum value `failed`, `outcome_reason` is set to `stand-down`, and `consecutive_failures` is not incremented. Machine test, three conjuncts, all required and named: (1) `.ai-playbook/last-stand-down.json` is present and its `plan` key names the target plan path, the file's literal key schema being `{"plan": "<plan path>", "reason": "<gate-unsatisfied-reason>", "date": "<iso date>"}` (an ad-hoc-worktree child writes the json into the primary checkout, the only checkout the checking turn reads); the json file is the machine-readable retrieval surface; no report-retrieval primitive exists and none is assumed; (2) the target plan file is unchanged since dispatch: a git comparison of the plan path's current sha against the children entry's `dispatch_plan_sha`.; (3) the checking turn re-runs the Gate satisfaction rule (Step 1) on the target plan's own current bytes and the gate reads unsatisfied: a child claiming stand-down on a plan whose gate now reads satisfied (a stale dispatch, the gate having satisfied between dispatch and check) or on a plan whose header block carries no External gate line accrues credit normally, the one conjunct the checking turn evaluates itself rather than trusting child-asserted evidence The child's final report opening with the literal `STAND-DOWN:` marker line (`STAND-DOWN: <plan-path> <gate-unsatisfied-reason>`, the reporting duty the execution-child payload blueprint in `agents/skills/maintenance/prompt-templates.md` carries) is the human-visible witness quoted in the turn output, produced by that payload duty; it is not part of the machine test: report text alone never qualifies, the exclusion coming from the json conjunct rather than from marker matching (the marker stays a literal line prefix matched exactly, so a broken child whose report merely contains the word stand-down anywhere is not the witness). The cap's count includes only children entries whose `outcome_reason` is not `stand-down`, so a stand-down-explained zero-progress outcome can never alone trip the alert. An authoring child never qualifies (its `dispatch_plan_sha` is null). The checking turn consumes the json file it checked (deletes or clears it) only after the stand-down outcome record write has survived (consuming earlier would lose the evidence inside the state write's crash window), so a stale file cannot qualify a later child. The turn output echoes the consumed json's contents (its plan, reason, and date values) for triage alongside the quoted marker witness. A genuinely broken child that wrote no json file does not qualify, so real stall loops keep accruing credit.
- Carve-out witness: a stand-down outcome accrues nothing, so a stand-down followed by two real failures holds `consecutive_failures` at 2, below the three-strike cap; three stand-down outcomes alone never trip the alert; a child whose report opens with the marker while its plan file changed since `dispatch_plan_sha` does NOT qualify and accrues credit normally; a child whose json satisfies conjuncts 1 and 2 while the plan's gate re-reads satisfied under conjunct 3 does not qualify and accrues credit normally; a child whose report contains the word stand-down anywhere but wrote no json file does not qualify: via the json conjunct, not marker matching (a conforming child that omits the marker also omits the json, the payload duty coupling the two).
- Children-entry schema additions (both additive under schema 4, no version bump): `outcome_reason` is an optional string, `null` by default, carrying the value `stand-down` per the stand-down carve-out above, the value `covered-stand-down` per the authoring covered-stand-down carve-out and per its second qualified surface the in-session log-entry covered-stand-down (both State file; the in-session log-entry variant records the standard `covered-stand-down` value with no marker file, its justification living in `decision_reason`), and the value `deferred` per the parked-dependency unblock deferral (the deferral write names the refused gate in the same field, and `deferred` is excluded from failure credit only while the value names the refused gate, so persistent refusals park with the bounded re-selection of the refusal-cycle rule instead of accruing credit); `dispatch_plan_sha` is the target plan file's sha256 recorded at dispatch time (Step 5), `null` for authoring children.
- Progress resets `consecutive_failures` exactly as archival does, so a multi-session plan never false-trips the cap; failure increments it.
- At three or more consecutive no-progress child outcomes the turn writes `alert` (with `tripped_at` and the reason) and stops scheduling children until a human clears the alert. The turn also notes the alert in the agent's persistent memory index when one exists.
- Turn-level tripwire for the broken-parent case: Step 6 runs in a best-effort guard of its own, so even a turn that fails before scheduling records `last_run_at` and a `turn_error` reason. The schema counter `consecutive_turn_errors` keeps the streak alive across whole-document rewrites: a turn ending with a `turn_error` record writes the previous value plus one, a fully successful turn resets it to 0, and three consecutive `turn_error` records (or, when the state writes themselves fail, three consecutive turns with no successful state update detected via the memory-note streak in the Signal split below) write the same `alert` and trigger the same stop as the child cap. When the trip comes through the `turn_error` records, the alert's reason records the most recent `turn_error` reason (for example `duplicate-parent-candidate`), so the clear procedure's duplicate-removal clause always binds when that reason tripped the alert; the write-failure-streak trip keeps the write-failure reason described in the Signal split below. A turn whose turn_error is recovered in-turn (the parked intent discharged and the carrier re-armed by a create verified per the ENABLED recognition rule and ENABLED verification) resets `consecutive_turn_errors` to 0 in the same targeted edit that records the recovery, quotes the verification in the recovery note, and the turn's Step 6 write carries the reset forward; absent the verified re-arm, the streak stands.
- Signal split: the file counter covers turns that ran but failed (`turn_error` records); when the state write itself fails, the file cannot count the turn. For that case the turn writes or updates a memory note `{"type": "turn_tripwire", "consecutive_write_failures": N, "repo": "<resolved repository root>"}` in the agent's persistent memory index on every failed state write (N is the running count of consecutive failed writes; below the threshold a successful state write resets the streak and clears the note), and the Step 1 read-back of the memory index arms the same stop as the child cap only when a note whose `repo` key equals the resolved repository root records N >= 3, resolving the turn to D3 with nothing scheduled; the `repo` key is the cross-repo discriminator, so a streak note written by another repository's scheduler never arms this repository's tripwire. When the read-back finds N >= 3, a successful Step 6 state write converts the streak into the persisted `alert` (reason: write-failure streak) instead of silently clearing the note; the stop then holds until the documented human-clear procedure runs. The `last_run_at` staleness check in the State file section remains a further rail for a dead or silent parent.
- Silent-turn classification may consult the store-level darkness-triage witness where the runtime overlay provides one (it reads the app logs for session-store integrity events around the child's run window, separating a child that outlived its parent record from a parent that actually died); this skill stays runtime-agnostic, so the concrete log event names and the read procedure live in the overlay, not here.
