## Scheduling primitives

- Loop carrier: the armed automation that fires scheduler turns. Two legal forms per the cadence rule in "Recurring automation recipe": the chain record (a one-shot carrying the scheduler prompt template, armed for the next window's start) and the recurring fallback (the fixed-cadence recurring parent created when the probe is unusable). There is one carrier per repository; it fires scheduler turns on the cadence the rule selects, and its automation id is the state file's recorded `parent_automation_id`.
- Child sessions: create each clocked child as a one-shot delayMinutes automation (the backlog's verified child shape: relative delayMinutes, no cron expression, `recurring: false`). delayMinutes is preferred for children because a self-computed absolute time that has just passed silently rolls a full year forward under a cron-pinned one-shot, though cron-pinned one-shots with `recurring: false` are also observed working in this repo's automation fleet (2026-09-13). An idle-time child uses the idle-time task primitive instead (see "Child dispatch ladder"). The two schedule shapes do not combine: `CronCreate` refuses a payload carrying both `delayMinutes` and a cron expression (witnessed live 2026-10-31), so a one-shot pinned to an absolute wall-clock time passes the cron expression alone with `recurring: false` and verifies the returned `nextRunAt` before treating the arm as landed.
- In-session authoring primitive (added 2026-09-20): beside the idle-time primitive, the authoring lane can dispatch in-session: no child automation is created and the deciding turn runs the authoring blueprint's task paragraph itself (SKILL.md Step 5's in-session dispatch mode). The quota-signal input decides: when the quota leg's probe report is usable, used_percent is below the max-percent threshold, its decision is continue, and this session can carry the full authoring loop, the D2 rule authors in-session; when quota is scarce (used_percent at or above the threshold, or the decision is not continue) or a pricing deferral is active, or the session cannot carry the work, dispatch out through the clocked one-shot or the idle-time primitive instead. The child entry records the `(in-session)` target marker with a null automation id and the dispatch's quota_signal (SKILL.md Step 6). The primitive is not a stop boundary: after an in-session authoring run lands, the turn re-runs the execution-lane decision on the freshly landed plan under the continue-loop condition (directive D-17; D-6's quota clauses remain active, decisions.md), never ending at the authoring boundary while dispatchable work remains and the primary 5h limit is not low.
- Execution-lane fallback legs (added 2026-09-26, P64): the concrete primitives behind the SKILL.md Step 3 ordering: the idle leg (when the Ladder precheck retires the clocked leg and the session owns `OffPeakCreate`, dispatch the execution child through the idle-time queue, dispatch-slice payload unchanged, no fire time, the children[] entry carrying the `(idle)` marker and `dispatch_plan_sha`; the idle-child lane-hold, idle-listing attribution, and failure-cap coverage apply unchanged); the in-session leg (when both dispatch primitives are absent after the precheck, or the idle queue refuses the idle leg, and the quota signal is abundant per the D2 thresholds, and the session can carry the work, the deciding turn runs the execution blueprint's payload itself, recording the `(in-session)` entry with `dispatch_plan_sha` and `quota_signal`); the park-with-carrier leg (a precheck park that leaves the loop with no armed carrier pairs the park with the launchd resume carrier per the Launchd resume carrier bullet below, the pairing part of the park's own targeted-edit step). The SKILL.md cap's directive-bound second execution leg is capacity-parallel beside the primary dispatch and not one of these fallback legs; the ordering's trigger stays absent-or-retired primitives for the one primary dispatch.
- Rescheduling a live child (verified 2026-09-15): `CronUpdate` has no delay field, so pulling in a `delayMinutes` one-shot means converting it to a cron-pinned one-shot via `CronUpdate` (observed working). The cron fields are the user's LOCAL timezone: pinning a UTC hour lands in the past and silently rolls `nextRunAt` a full year forward (the same year-roll trap as a just-passed self-computed one-shot). Compute the local wall-clock hour, add margin, and verify the returned `nextRunAt` before treating the update as landed.
- Listing: list armed automations with `CronList`. The lane guards `G1e` / `G1a` (SKILL.md Step 2) read this listing: armed fire times, last-run timestamps, and the prompts of armed or recently fired automations. Observed listing fields (orchestrator first-hand evidence, 2026-09-14): every automation carries `automationId`, `title`, `cronExpr`, `prompt`, `enabled`, `lifecycleStatus`, `nextRunAt`, `runCount`, `recurring`; `lastRunAt` appears only after the first run and `maxRuns` only when set (both conditional). A one-shot child lingers listed after completion (enabled false, lifecycleStatus completed; linger model, corrected 2026-09-16: supersedes the 2026-09-15 disappears-at-completion claim) and still binds its spawner session before it ages out, so a child still running after firing is tracked by the lane guards' state-file arm, not by this listing. Fail-safe: an automation whose prompt is not visible in the listing counts as a potential child; treat the lane as busy.
- Merge landing lock (added 2026-09-20): landing critical sections on the default branch serialize under a second lock family in `scripts/done-lock.sh` beside the done lock (a holder may hold both at once): `merge-acquire [--label TEXT]` tries once, `merge-wait-acquire [--label TEXT] [--max-wait SECS]` polls with a bounded wait (the child blueprints cap the wait at 300 seconds), `merge-release` and `merge-release-repo` release token-fenced from the environment (`merge-release-repo` requires the env and never session-loads), `merge-status` prints the holder or `free`, and `merge-stale-clean` is the operator escape for a stale hold. Acquisition prints the `MERGE_LOCK_DIR` and `MERGE_LOCK_TOKEN` exports; the holder keeps both across the whole landing critical section. Stale threshold: `MERGE_LOCK_STALE_SECS`, default 600 seconds. A hold at or past that threshold, or one whose age cannot be resolved at all (metadata missing or unparseable), is the scheduler's `G3b` stale crash evidence (`turn_error: merge-lock-stale`, operator escape `merge-stale-clean`): it blocks no scheduler decision; a stale holder whose process is still alive keeps landing children in the bounded wait until an operator runs `merge-stale-clean`, while a verified-dead stale holder is auto-reclaimed by the lock's own recovery rules (dead-holder grace) without operator action. The escape's reach is scoped: `merge-stale-clean` removes a hold whose meta parses at the stale threshold and an aged meta-less hold (crash leftover), while a corrupted-meta hold refuses it by design and needs manual removal after inspecting the `merge-status` dump. Contention behavior for a child: bounded wait, then stand down keeping the branch and worktree and report. The critical section the lock serializes is worktree-complete (added 2026-10-02, plan `docs/history/plans/2026-10-02-worktree-complete-landing-lifecycle.md`): the rebase and the squash merge execute inside the landing session's worktree, the default branch receives only the compare-and-swap ref update, so staging (git add) in the primary checkout during a landing is a landing-gate violation for every lane, and a masked rebase or merge failure aborts the landing before any staging. The landing also verifies tree equality between the squashed branch tip and the produced squash commit before the parentage gates and the ref move (added 2026-10-02, plan `docs/history/plans/2026-10-02-squash-landing-tree-equality-gate.md`; a non-empty diff aborts before the ref move and a deliberate non-pure squash says so at the call site). The landing commit itself is built from the staged index inside that worktree (added 2026-10-08, the plan-directory-shape execution landing): the staged set is derived mechanically from the branch delta (`git diff --name-only <old-base>...<branch>`), never a hand-curated list, and the commit is a bare index commit of the staged squash (the staged index proven equal to the branch delta, the peer-byte guard's `check-staged` verifying containment), because a pathspec commit silently skips worktree-absent (deleted) paths and a zsh invocation shell never word-splits an unquoted path variable (move the list through xargs or a quoted array); the tree-equality gate above is the check that catches every commit-form drift. A prescribed release term never sits at the tail of an `&&` chain (always-run position, so a mid-chain failure cannot skip the release), and release stderr is never suppressed (a hidden refusal is the stranded-hold shape). Monitor prompt-log commits (the rolling prompt logs' prune, freeze, and investigate writes) run under the log preamble's Standing rules block's `Write boundary rule` label in `docs/history/backlog/PLAN-PROMPTS.md`; the concrete primitives: the primary done lock through `bash scripts/done-lock.sh acquire` or `wait-acquire`, run from primary-checkout context so the done key resolves to the primary worktree (a worktree session addresses the primary checkout through an explicit-rooted form, never its own worktree's key), ; the write verifies the selected symbolic ref and starting OID against primary `HEAD` under the done lock before the final log read or edit and routes the commit through the runner's ref-bound captured-tree transaction in `scripts/done_run.sh`, release token-fenced as `release-repo`; primary log writes never take the merge lock (the then-merge-lock acquisition and the `merge-release-repo`-then-`release-repo` release order are retired 2026-10-28, plan `docs/history/plans/2026-10-25-primary-log-branch-drift-at-commit.md`; a worktree log commit keeps the merge lock through `merge-acquire` or `merge-wait-acquire`, released token-fenced as `merge-release-repo`); an acquisition refusal defers the write per the monitor duty (the monitor never rewrites a log to recover a refused write).
