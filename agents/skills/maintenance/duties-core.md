# Duties core (maintenance child prompts)

The byte-identical shared duty set the pins suite holds identical across the child blueprints (plan docs/history/plans/2026-10-10-maintenance-skill-size-refactor.md Task 4): the re-arm FIRST ACTION paragraph, carried here once as the canonical copy; template-authoring.md and template-execution.md name this span by reference, and a dispatched child loads this file beside its blueprint.

FIRST ACTION, before any gate or phase: re-arm the maintenance loop state-first, without listing first. Read .ai-playbook/scheduler-state.json (Bash) and take your own record to be the last children[] entry whose kind and target match this payload (an idle-time dispatch records a null automation id and takes no record: a matching entry is not taken as its record either, and the session proceeds exactly as if "parent_automation_id" were null); when no entry matches, you have no record: proceed exactly as if "parent_automation_id" were null. Then, first applicable step wins: (1) when "parent_automation_id" equals your own record's automation id and that entry still has outcome "pending" in the state file, the dispatch ladder left the parent record in child form under this session (date-tagged 2026-09-22, P36 scheduler durability and audit plan Task 4: migration-compat under the fresh-id delete-plus-create model, live only while a pre-2026-09-21 recycled-id record lingers, so a future simplifier does not delete this live migration-period behavior): precheck before the call (the child-side twin of the overlay's ladder precheck): assert the session actually owns the update primitive the reshape leg needs, and when it does not, route to this step's delete-plus-create path (or, when the delete and create primitives are absent too, to the escalation in (4)) without burning listings on statically absent primitives; update that one record into the parent form with one update-primitive call per the recipe in agents/skills/maintenance/zcode.md "Recurring automation recipe" (its title and prompt template, in the form the recipe's cadence rule selects: the chained one-shot at the next window's start when the probe is usable, otherwise the recurring fallback; enabled true, its prompt template with {REPO_ROOT} filled); HOST CAVEAT: any recycling update whose echoed record is not verifiably the intended form (enabled true, the intended recurring value, a future nextRunAt confirmed by a listing) is treated as a refusal and takes the delete-plus-create path (deleting your own spawner record and creating the parent exactly per the recipe, recording the refusal in the "rearm_note" field); a landed update then updates "parent_automation_id" as a targeted field edit (atomic replace; change no other field) and stops; when that entry is no longer pending, the recorded id is untrusted: do not flip on it, and route through steps (2) and (3) instead (listing to confirm before any mutation). (2) when "parent_automation_id" names a different non-null id, the parent is believed armed: list at most once to confirm; when an ENABLED automation with the recognition title and prompt opening (the literals defined in agents/skills/maintenance/zcode.md "Recurring automation recipe": its Title line and its prompt template opening) whose prompt also contains the resolved repository root is present, stop; when absent, set "parent_automation_id" to null (targeted field edit) and enter step 3 with that listing already in hand (do not list again). (3) when "parent_automation_id" is null: decide from the listing you already performed in step 2 when you entered from there, otherwise list at most once; when an ENABLED recognition match is present (an ENABLED automation with that recognition title and prompt opening whose prompt contains the resolved repository root), adopt its id into "parent_automation_id" (targeted field edit) and stop; when the listing shows an armed child payload for this repository other than your own spawner record (a non-recurring ENABLED automation whose prompt contains the resolved repository root and a plan-execution payload), do not create or recycle: the lane is held by that child; stop; when neither is present, precheck before leg selection (the child-side twin of the overlay's ladder precheck): assert the session actually owns the primitives the chosen leg needs (the update primitive for the recycle leg; the delete plus create primitives for the create leg, its delete also serving the lingered-record deletion), and on absence route to the escalation in (4), whose park path carries the decided re-arm, without burning listings on statically absent primitives; after any delete this duty performs, one read-only listing probe precedes the create (the overlay's post-delete probe rule; never read absence from a truncated listing), and a repeated identical create failure parks per step (4) with the mechanism switch to the launchd clocked-order chain rather than a third identical emission; recycle your own spawner record into the parent form with the same update as step 1 when you have one (under the same HOST CAVEAT: an echo not verifiably the intended form is a refusal routed to this step's delete-plus-create path), otherwise create the parent exactly per the recipe, deleting your own lingered completed spawner record first when the create is refused for the automation-born cap, and the record deleted first must be an id this session's own state file records as its spawner, never any other lingered record in the listing (the overlay's ownership allowlist applies to this duty unchanged: a foreign lingered record is untouchable, and a cap that no own-record delete can lift parks per step (4)); a create refusal indicating the parent already exists counts as success only after one more listing confirms an ENABLED automation with that title and prompt opening whose prompt contains the resolved repository root is present, and a failed confirmation routes to the escalation below; then update "parent_automation_id" and record the armed carrier's fire time into "next_turn_at" as one targeted field edit. When this step succeeds after an earlier refusal recorded in "rearm_note", clear "rearm_note" in the same targeted edit. A recycling update refusal of any kind in this step, an unverifiable echo under the HOST CAVEAT included, falls back to this step's create path and is recorded in the "rearm_note" field naming the refusal. Decision-first recording: when this duty has decided to re-arm (step 3 entered with a null "parent_automation_id") and a listing still remains to be done there, record the re-arm intent in the state file before or with that listing: set "pending_rearm" (targeted field edit) paired with the assembled parent payload copy under the rearm kind's identity-bound payload filename (derived per the pending_rearm field paragraph; the park-path pairing rule), so a session lost mid-decision leaves a mechanically executable record; when the re-arm then succeeds in this same session, clear "pending_rearm" in the same targeted state edit that records the new "parent_automation_id"; an intent left standing because the armed-child lane hold stopped this session stays set for the next scheduler turn's reader (its armed verification clears the stale intent without re-arming). Loop guard: if you have listed twice without a mutating step between listings, write the "rearm_note" field via a Bash state edit naming the loop and, when the re-arm this duty had decided is left unexecuted (a suppressed re-arm), write "pending_rearm" plus the assembled parent payload copy under the rearm kind's identity-bound payload filename (derived per the pending_rearm field paragraph) in that same targeted state edit (the park-path pairing rule); either way, then stop touching automation primitives. Carve-out: when the decided mutation was recorded state-first before the first listing and this session owns that record (its own decision-first write, or the pending record it takes as its own under this duty's record-taking rule), the overlay's one-recorded-mutation carve-out (agents/skills/maintenance/zcode.md, "Dispatch discipline and loop stand-down") permits exactly ONE mutating call implementing that recorded decision before this guard's stop applies regardless of the call's outcome. (4) Any other refusal after two retries: record it in the state file "rearm_note" field (targeted field edit), then write "pending_rearm" plus the assembled parent payload copy under the rearm kind's identity-bound payload filename (derived per the pending_rearm field paragraph) in the same targeted state edit (the park-path pairing rule: intent record and payload copy are one paired write, always before the memory note), so the next scheduler turn's Step 1 reader can dispatch the parked intent mechanically from the paired payload copy; then write a memory note {"type": "loop-parent-missing", "repo": "<repository root>"} in the agent's persistent memory index, and continue; a later session reading that note re-arms per the recipe. When the park stands because this session lacks the create primitive (the reduced-toolset carrier case), the pending "pending_rearm" record and its paired payload copy are kept in place, not cleared by this session, so the next capable session can restore; that later capable interactive session, reading the pending recovery input, restores the parent (the recurring carrier) per the recipe before any competing one-shot scheduling ask, which is reported unscheduled (the carrier re-arm precedence over a schedule ask; the AGENTS.md "Scheduling asks" section's standing pending re-arm clause and the same-named bullet in agents/skills/maintenance/zcode.md are the contract side).
