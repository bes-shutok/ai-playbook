## Recurring automation recipe

- Cadence (the cadence rule, rewritten 2026-09-21 by the quota-aligned cadence plan, which supersedes the fixed every-2-hours cadence): the turn decides its own successor at arming time, state-first, instead of firing on a fixed clock. When the quota leg's probe report is usable, the carrier is a one-shot carrying this recipe's title and prompt template, armed for the next window's start, which is the probe's reported reset_at_epoch plus 10 minutes (the arming margin). When the probe is unusable, the recurring fallback is created per this recipe with the fallback cadence `15 */2 * * *` (every 2 hours at :15; raised from every 4 hours to hourly on 2026-09-15 and to every 2 hours the same day by user request; token-frugal: the turn itself is a few greps plus one primitive call). One rule binds every arming path: no arming path may end with the loop dark.
- Title: `Maintenance scheduler turn` (the recognition title the child payloads' re-arm duties match by reference to this recipe; form-independent since the quota-aligned cadence plan, whose superseding origin deletes the cadence parenthetical so the title no longer pins a cadence; the payloads and sibling files never carry the literal, so there is nothing to keep in sync with them; pinned by `scripts/check_maintenance_pins.sh`).
- Prompt: the scheduler prompt template below, with `{REPO_ROOT}` replaced by this repository's absolute path at automation-creation time. Never commit the resolved absolute path into the repo; this template keeps the placeholder literal.
- Directive lift (added 2026-10-03, the stray-close incident dossier plan Task 3): the carrier prompt construction lifts lane directive text from `docs/maintenance/operator-directives.md` (the directives home) at dispatch instead of baking aging clauses, and the assembled payload defers to the home's active records on conflict; the 2026-10-02 carrier clause that outlived two in-chat lifts across 87 armed runs is the anti-shape, and a directive lift is a one-file commit to the home.

```text
You are the maintenance scheduler for the repository at {REPO_ROOT}. Run the maintenance skill (agents/skills/maintenance/SKILL.md) scheduler turn end to end: survey the work surface, apply the guards in order, decide per lane and schedule at most one execution and one authoring child per the skill, update the scheduler state file. Standing pre-authorization: never block on questions, decide and proceed; never push to origin. If the skill says stand down, record the reason in the state file and stop.
```


- Re-arm hygiene (rewritten 2026-09-16 to the state-first duty shape governing the re-arm decision of its two named actors: the turn's Step 0 and rearm-on-touch sessions; the shape is the template other re-arm actors may follow, the watchdog, child, and Step 1 memory-note-reader duties carrying their own embedded shapes): consult `.ai-playbook/scheduler-state.json` first and decide state-first from the recorded `parent_automation_id`, the pending `children[]` entries, and `parent_absent_since`, so two parents never run the same cadence; Chain default (activated 2026-11-03 by the promotion review): a session already bound to an armed automation record defaults to arming the chain through the launchd clocked-order chain at the next slot, and no delete is entered when the creation form is the chain; fresh or unbound sessions and sessions whose delete-own-spawner leg lifted the cap keep the automation-primitive create; after a recorded-but-unexecuted mutation, the recorded mutations are the only permitted next primitive calls, other than a listing a duty mandates as its decision input (the state-file-cannot-decide listing, the pending-rearm armed verification); a listing after the mutations have executed stays governed by the dispatch-discipline bounds (the two zero-listings exception lists are deliberately asymmetric subsets; the asymmetry is safe because the turn-start duty runs before any dispatch, so a listing it mandates as its decision input always precedes the turn's first mutation, and any later listing stays governed by the dispatch-discipline bounds whose exception list carries the dispatch-side entries); in an automation-born session whose state file records the armed carrier as a one-shot, the FIRST automation primitive of the decided re-arm is the delete of that record by the state-recorded id, emitted before any listing that is not itself duty-mandated and before the create (already-gone is success; the delete lifts the automation-born cap, so the refusal path no longer gates the ordering); the delete is the earlier call of the one assistant message that also emits the create, whose arguments never depend on the delete result, and a create cap-refusal after an in-message delete takes the existing escalation paths with no further emission; Ownership allowlist (every automation delete on this ladder): the only records a session may delete are ids its own lineage's state file records as its own, either the recorded parent_automation_id or a children[] automation_id that the same lineage wrote; a delete that would target any other listing record, lingered completed included, is never emitted: the session parks that dispatch for the operator, names the record's id in its turn output, and continues with any work that needs no delete, since a foreign record's presence in a listing is never by itself a stand-down. A null recorded id has no deletable record: the ladder's null-id sole-span-match fallback delete is retired and its cap-refused create parks for the operator. The allowlist never removes the own-record deletes the ladder already orders: the state-recorded carrier id and the session's own spawner record, whatever its form, stay the delete-first targets. Bind at create: a successful create's returned id is written into the state file (the entry's automation_id, or parent_automation_id for the carrier) before the next automation call, so the allowlist holds its key the moment the record exists. Witness: the 2026-10-16 incident deleted two peer-lineage lingered spawner records that recognition matching could not discriminate (state file notes 2026-10-16T15:52). Form-unknown or a recorded recurring form keeps the delete at the cap-refused create; a delete-first target whose delete reports a live rather than lingered-completed record proceeds with the same-message create regardless, the targeted edit records the form the delete observed so the next read self-corrects, and the drift is named in the turn output; when a create instead reports the parent already exists, verify the ENABLED recognition match (title plus prompt opening, the prompt containing the resolved repository root) and treat it as success; when the listing shows an ENABLED repo-contained recognition match, the session also clears `parent_absent_since` in its targeted edit. After re-arming, update `parent_automation_id` in the state file to the new parent's automation id so the id-first parent exclusion in SKILL.md `G1e` / `G1a` stays accurate (a null id forces the span fallback; a stale id makes the live parent a differing-id span match, which the duplicate-parent tripwire's self-heal arm adopts automatically when it is the sole live span match). The parent may also be intentionally absent while a child is in flight: the dispatch ladder surrenders the parent slot to the child (the fallback delete-plus-create: the parent record is deleted and the child one-shot carries a fresh id; the demoted recycling leg kept the same id in child form), and the child re-arms the parent as its payload's first action and updates the recorded id, so a turn must never schedule a second parent merely because it sees none besides its own spawner. The already-gone outcome is success too: a delete reporting the record already gone after its confirming listing is success-shaped (the listing's goal state already holds), recorded as success with no escalation and no retry; a delete-first emission reporting the record already gone is success-shaped the same way, its own report standing in for the listing.
