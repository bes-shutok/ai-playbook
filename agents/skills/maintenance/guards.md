### Step 2: guards (fixed order)

Evaluate in this order; each guard names its observable signal. The proposed slot for this turn's child is now plus 5 minutes, unless the quota leg (Step 4) later moves it.

- `G1e (execution lane)`: trips when an execution child (classified per the markers in `agents/skills/maintenance/zcode.md`) occupies the lane per any arm below, checked in this order:
  - State-file arm (release rules): a recorded child holds the lane while `fire_at` has not elapsed, or while its 6-hour horizon has not elapsed and (outcome is `pending`, or outcome is `progress` and the completion evidence is absent); completion evidence is, for an authoring child, the target plan passing the certification oracle, for an execution child, the target plan archived, and, for an audit child, the audit state file's digest and `next_due` updated after the entry's `created_at`, and for a re-triage child, the re-triage record's corpus digest and `next_due` updated after the entry's `created_at`, and for a registry-task audit child, the task's state record `next_due` and `last_run_at` updated after the entry's `created_at` (the audit lane hold releases on evidenced audit completion instead of the unsatisfiable target-plan certification), and, for an ad-hoc child, the run's own landing receipt (the target item's absence attributable to this run's landing commit, beside the recorded panel pass; never bare absence); an unblock child's completion evidence (added 2026-09-25) is its ledger entry cleared plus the serialized plan present in `execution_queue`, with the branch landing verified through the landed-commit test; evidenced completion releases the execution lane immediately instead of holding `G1e` to the six-hour horizon, and the horizon plus failure cap otherwise read the entry like any execution child; an execution child with `outcome: progress` whose manifest `updated:` is stale past one cadence period releases the lane as evidenced stopped (eligible for fast re-dispatch); an idle-time child (null `fire_at`) holds the lane until the runtime's idle-task listing (named in the overlay) no longer shows it queued or running, idle-time tasks being lane-occupying per the overlay's attribution rule (an entry whose session identifier matches the current session, or one a pending `children[]` entry records whose target carries the `(idle)` marker, `created_at` matched where the idle listing exposes it), or six hours pass after `created_at`, with the same outcome and completion-evidence conditions. An `(in-session)` children[] entry (Step 5's in-session dispatch mode, either lane) holds the lane while it is pending within the same horizon, joins no listing (no automation exists for it to appear in), and is released by the entry's own outcome write or its completion evidence (for an execution child, the target plan archived, the evidence class this arm already reads; for an authoring child, the certification oracle pass); a deciding turn that dies mid-in-session leaves it pending like any dead child. This arm is the primary in-flight detector for children this repository dispatched itself.
  - Armed arm: an execution-child automation armed to fire within `CHILD_LANE_SPACING_HOURS` (default 5, sized to outlast a typical child run; observed runs span one to four hours) of the proposed slot.
  - Fired arm: a fired execution child fewer than six hours past its `fire_at` (the post-fire outcome-horizon floor; the spacing constant governs pre-fire arming), computed from the automation listing when the child still appears there; a listing record counts only while it is ENABLED. The hold releases for a same-directive session when the fired child is a standing operator-defined recurring payload (the fired automation's prompt carries the same standing operator directive the deciding session's prompt carries, the standing user surface the User-directed override's presence predicate lacks for automation-born sessions) and the session's candidate target is distinct from the fired child's target, the comparison reading the target-bearing span of the fired child's listing prompt against the candidate plan path. A fired scheduler-dispatched child holds the lane as today, and the six-hour horizon and the post-fire outcome-horizon floor stay byte-for-byte with every integrity guard non-overridable.
  - Widened arm: catch-all for children not covered by the arms above. Evaluate in order: (1) exclude the recorded parent by id; (2) when the recorded id is null, exclude a sole ENABLED automation whose prompt begins with the scheduler template's opening line and contains the resolved repository root; (3) for each remaining automation whose fire or last-run time falls inside the spacing window, classify its prompt only when the prompt contains the resolved repository root (the same containment the recognition matchers and the duplicate-parent tripwire require); a prompt without that containment occupies nothing, because a foreign repository's plan work is not this repository's lane occupant; a prompt not visible in full is not classifiable and counts as a potential child per the not-visible fail-safe (the lane is treated as busy). Among contained prompts: a match for this lane's markers occupies this lane, an authoring marker occupies only `G1a`, an audit marker occupies only `G1a`, an execution marker occupies only `G1e`, an ad-hoc marker occupies only `G1e` (the ad-hoc backlog arm's marker, occupying only the execution lane; its overlay-side catalog entry is the definition home), a re-triage marker occupies only `G1a`, a prompt affirmatively unrelated to plan/backlog work occupies nothing, and anything else occupies both lanes. The classification ignores records whose `lifecycleStatus` is completed or `enabled` is false (a lingered completed child record occupies nothing; the state-file arms are the in-flight detectors), so the fast re-dispatch, successor chaining, and early release paths are not re-blocked by a corpse record. When the lane of an in-flight child is uncertain, treat both lanes as busy.
  - Discovery arm: a live execution session otherwise discoverable (an execute-plan claim check via the execute-plan live-session discovery ladder, the `## Live-session discovery ladder` section of `agents/skills/execute-plan/SKILL.md` with its mechanism pin under the same heading in `agents/skills/execute-plan/runtime-contract.md`, or active child session traces on the checkout). Execution-claim check (added 2026-09-24, P54, mirroring the authoring-side discovery arm): a claim file under the resolved tmp directory's `execution-claims/` (facts key `tmp_dir`, `docs/tmp/` default) whose `updated:` is fresher than one cadence period occupies the execution lane unless a pending execution `children[]` entry explains it (target-keyed matching on the plan slug); a stale claim (its `updated:` one cadence period old or older) occupies nothing.
  When uncertain whether an execution child is in flight, treat the lane as busy.
- `G1a (authoring lane)`: the same arms as `G1e`, evaluated only against authoring children (markers per the overlay; the widened arm's lane-classification rule applies symmetrically), except that the discovery arm is its own below, replacing the execution-side arm inherited by reference (authoring claim files are authoring-only artifacts). Every inherited arm is subject to the target-distinctness carve-out: an authoring child's hold under the state-file, armed, fired, and widened arms releases when the recorded or listed child's target is distinct from the candidate target and the standing-directive sanction exists; the occupant's target resolves through a three-rung ladder, because a scheduled peer has no claim file before its session starts: the pending `children[]` entry keyed on the plan or item slug first (the pre-fire witness, present from dispatch time), then the claim file by target-keyed matching, then the listed prompt's target-bearing span; a record none of the three explains occupies, the not-visible fail-safe unchanged; the execution-side semantics of the shared arms stay untouched, and the audit-child and re-triage-child holds stay unconditional. The two lanes are independent by policy: an authoring child never trips `G1e` and an execution child never trips `G1a`. Executions are fleet members and may overlap, each in its own per-execution worktree (isolation landed 2026-09-24, P57, superseding the strictly-sequential wording); an authoring child may run alongside an execution child, and it lands via its own merge-lock-serialized self-landing onto the default branch from its ad-hoc worktree (mid-round fold landings included, each through the same lock), carrying the plan-document commits. An authoring occupant holds the lane when its claim target matches the candidate target, and does not hold the lane when the targets are distinct and a standing directive to author is recorded (the session's bound mode being dual or author, or an explicit standing directive in the dispatching payload); a standing user directive outranks a lane-occupancy stand-down (the target-distinctness rule; witness: the 2026-09-28 09:32 stand-down, where the lane stood down on a live peer's claim without checking the candidate target's distinctness). An audit child occupies this same lane: an audit child never runs alongside an authoring child or another audit child; a re-triage child occupies this same lane and never runs alongside an authoring child, another re-triage child, or an audit child. The audit child's marker carriage follows the widened-arm rule: an audit marker occupies only `G1a`, never `G1e` (added 2026-09-24, P54 deferred low 1).
  - Discovery arm (authoring-side): an authoring claim file under the resolved tmp directory's `authoring-claims/` (facts key `tmp_dir`, `docs/tmp/` default) whose `updated:` is fresher than one cadence period occupies the authoring lane, UNLESS the state file's pending `children[]` entries explain it: a claim whose item basename matches the target's item basename in a pending authoring child entry is that child's own witness (not foreign; that explanation match is target-keyed matching against the state file, its data source because listing records carry no session ids and `children[]` entries carry automation ids), a claim whose item matches no pending entry is foreign, and it occupies the lane only under the target-distinctness rule's mirror: it occupies when its item target matches the candidate target or when no standing directive sanction exists, and it stands aside when the two targets are distinct and the sanction is recorded; the claim file's item slug and the live worktree branch names are the witness set for the distinctness read; a stale claim (its `updated:` one cadence period old or older) occupies nothing. Path caveat: the authoring payload writes the literal `docs/tmp/authoring-claims/` (it cannot resolve facts keys) while this guard reads the resolved tmp directory's `authoring-claims/`, so a facts `tmp_dir` override must revisit both sides. The execution-side live-session mechanism, named for the mirror, is the execute-plan live-session discovery ladder (`G1e` discovery arm) in `agents/skills/execute-plan/SKILL.md`; the claim procedure is under `## Run-level ownership and repository placement` in `agents/skills/execute-plan/runtime-contract.md`. The authoring payload writes and refreshes its claim file per `agents/skills/maintenance/prompt-templates.md` and deletes it at closeout, so an explained hold ends with its own child.
- Fleet cap (added 2026-09-24, P54, reworking the `G1e`/`G1a` single-occupancy guards into fleet counting): both lanes also trip when the repo-wide count of live children reaches 4; the count sums live peer sessions found by the discovery arms, pending `children[]` entries under the release rules, and armed child automations in the listing; a child is counted once, the strongest arm winning in the order state-file arm, then discovery arm, then listing arm; below the cap, D1 and D2 dispatch. EXECUTION ISOLATION (landed 2026-09-24, P57, retiring the review r1 F1 interim constraint): execution children run in per-execution ad-hoc worktrees per the Worktree-first standard, so executions are fleet members counted toward the cap of four like the authoring, audit, and re-triage kinds; the per-turn dispatch limits (at most one execution and one authoring per turn) stand unchanged, and the authoring-lane occupancy rules extend to the re-triage child per its consult.
- Duplicate-parent tripwire: when the automation listing shows an ENABLED automation whose visible prompt begins with the scheduler prompt template's opening line and contains the resolved repository root (the tripwire's span shape: the two title-less conjuncts it shares with the recognition rule defined at Step 0, deliberately without that rule's title conjunct, so a hand re-created duplicate with a drifted title still trips; the span literal, the scheduler prompt template's opening line, is pinned in the runtime overlay's child-classification markers), and whose id differs from the recorded `parent_automation_id`, or more than one such ENABLED span match while the recorded id is null, treat the extra as lane-occupying (both lane guards trip) and record a `turn_error` with reason `duplicate-parent-candidate` in the state file (Step 6) so a human collapses the duplicates. Self-heal arm: when the recorded `parent_automation_id` is absent from the listing and exactly one ENABLED span match exists under the same title-less span shape as the tripwire above (not the full recognition rule), the turn adopts that id into the recorded value, clears a `duplicate-parent-candidate` turn error, and schedules normally; the human deletion remedy applies only when the recorded id is still present in the listing.
- duplicate-user-directed-dispatch tripwire (added 2026-09-24, P54): when the automation listing shows an ENABLED non-recurring automation whose prompt contains the resolved repository root and a plan-execution payload that is USER-DIRECTED by the mechanical negative shape (a plan-execution payload that neither is a scheduler-parent recognition match nor opens with the execution blueprint's payload opening literal, the first line the Step 5 dispatch slice places at the head of every scheduler-dispatched child prompt, whose stable prefix is "You are an unattended scheduled session in the repository at"), and this turn is about to create another user-directed execution dispatch for the same repository, defer the create instead (record the existing record's id in `decision_reason`); the overlap predicate is the armed record's existence itself (ENABLED with a future `nextRunAt` for the same repository), not directive-text matching, so two wordings of the same directive still collide and two genuinely different directives still serialize; a turn may collapse the duplicate only with an explicit user instruction.
- `G2 (failure cap)`: trips when an alert is present in the state file or recovered from the memory index read-back, from either the child cap (three consecutive no-progress child outcomes) or the turn tripwire (three consecutive `turn_error` records, or an N >= 3 write-failure streak note).
- `G3 (joint state)`: trips when a merge or rebase is in progress on the checkout or the done-lock (`scripts/done-lock.sh`) is held, standing down the whole turn; a tripped G3 records the stand-down as a D3 no-op in the state file (Step 6) before stopping.
- `G3b (landing in flight)`: evaluated immediately after `G3 (joint state)`; trips when the merge landing lock is held (observable: `bash scripts/done-lock.sh merge-status` reporting a holder). Unlike `G3` it never stands the turn down: the survey, the guards, the decisions, and the state write all still run, and its effect is confined to Step 5's final-slot precondition and the Step 3 lane resolutions. When the hold is fresh (younger than `MERGE_LOCK_STALE_SECS`, default 600 seconds), the affected lane's dispatch creation defers with `pending_dispatch` retained per the existing Step 1 reader semantics and the reason `merge-lock-held` recorded in `decision_reason` (the lane per the Step 3 label mapping). When the hold is at or past the stale threshold it is crash evidence: record `turn_error: merge-lock-stale`, name `merge-stale-clean` as the operator escape, and proceed with scheduling (a stale lock blocks no scheduler decision; a stale holder whose process is still alive keeps landing children in the bounded wait until an operator runs `merge-stale-clean`, while a verified-dead stale holder is auto-reclaimed by the lock's own recovery rules -- dead-holder grace -- without operator action, so such a hold does not keep children waiting). The escape's reach is scoped: `merge-stale-clean` removes a hold whose meta parses once it is at the stale threshold and an aged meta-less hold (crash leftover past the incomplete threshold), while a corrupted-meta hold refuses `merge-stale-clean` by design (fail-closed) and needs manual removal after inspecting the `merge-status` dump. A hold whose age cannot be resolved at all (metadata missing or unparseable, `merge-status` printing `metadata missing` or `age_secs: unknown`) classifies as the same stale crash evidence under the same rule (same `turn_error` reason, same operator escape; the `G2` interaction below is unchanged), so an unresolvable holder can never defer the lane alertlessly forever. Failure-cap interaction, stated explicitly: a persistently stale lock records `turn_error: merge-lock-stale` every turn, so three consecutive stale turns trip `G2` and stand the loop down with an alert until a human runs `merge-stale-clean` (per the escape scoping above: a corrupted-meta hold refuses it and needs manual removal after inspecting the `merge-status` dump) and clears the alert; that is intended crash-evidence behavior, not indefinite loop continuity. Beside the guard (no guard semantics changed): a prescribed release term never sits at the tail of an `&&` chain (always-run position, so a mid-chain failure cannot skip the release), and release stderr is never suppressed (a hidden refusal is the stranded-hold shape).

- `User-directed override (interactive sessions)`: (2026-09-30, witness: the origin `docs/history/backlog/2026-09-28-user-direct-request-overrides-standdown.md`, the 2026-09-28 18:21 stand-down corrected within the turn by the operator) when the session is interactive - the current turn's directive arrived in a live user message, the same interactive sense the trigger-verb bindings paragraph pins - and a deferral-class trip fires (the `G1e`/`G1a` occupancy arms including the plain fleet-cap arms, both discovery arms, and D2's fresh-foreign-claim consult skip, `G3`'s done-lock-held arm, `G3b`, the execution-claim take refusal (the run-worktree creation gateway refusing over a fresh foreign claim; its refusal names this rule as the override route), and the landing gate (the Invariants post-review pre-landed cap) together with its Step 5 final-slot read), the session proceeds instead of standing down: it states the tripped guard and its evidence in one line in the lane's `decision_reason`, chooses a non-colliding surface (its own per-execution worktree, landing-completion work for a completed unlanded run, or a target verified disjoint from the peer's in-flight target, fresh claim set, and uncommitted dirt on shared paths), and proceeds; the `decision_reason` line carries `user-directed-override` plus the tripped guard's name (for example `user-directed-override:G3 done-lock hold`). Integrity guards are never overridable: the `G2` failure cap, `G3`'s merge-or-rebase-in-progress arm, corrupted merge-lock metadata, the foreign-dirt landing gates (the done gate's refusal to land over a peer's uncommitted dirt), the duplicate-parent and duplicate-user-directed-dispatch tripwires, rate pressure, and the cycle gate refuse the override. Unattended sessions keep today's stand-down semantics unchanged. The override predicate is user presence, never confidence. Precedence: for every site that resolves a deferral-class trip without naming this rule - `G3`'s whole-turn stand-down, the Step 3 guard-trip resolution mapping, the Step 5 final-slot precondition, and the in-session dispatch mode's done-lock pre-work gate - the resolution reads as today for an unattended session and as proceed-per-this-rule for an interactive one, while an integrity or non-overridable trip resolves as today everywhere. Collision floor: never a peer's in-flight target, never a stolen fresh lock, never a same-target proceed; isolation, not inaction, is the answer, and the merge lock still serializes every landing. An interactive proceed past the execution-claim take refusal also records its override row in the guard liveness ledger (`record --guard execution-claim-gateway --kind override`, the done step's advisory append), so the gateway's false-refusal cost stays visible at the next census; the append rides echo-and-continue and never blocks the proceed.
