# Child prompt templates (maintenance skill)

The scheduler turn assembles each child prompt from one of the two blueprints below and schedules it as a one-shot session (SKILL.md Step 5). Source of record: `docs/history/backlog/completed/2026-09-13-maintenance-scheduler-skill.md`, section "Current manual baseline". Both blueprints are copied verbatim from that section except for exactly these documented deviations:

- Project-name normalization: the execution blueprint's opening sentence becomes "You are an unattended scheduled session in the repository at {REPO_ROOT}." (project-name normalization only, per the repo's never-hardcode-project-names guideline; every other word of both blueprints is verbatim).
- Execution chaining guard: the execution inner block's opening sentence carries an appended guard forbidding further automation creates or schedules with named exceptions, originally the re-arm duty alone and, since the 2026-09-16 amendment, also the single completion-time successor duty (both exceptions paraphrased here; the exact guard sentence is pinned by the pins suite), so the scheduled session carries the same prohibition the authoring payload has (not part of the backlog source text).
- Execution fire-time checkout gate: the execution inner block carries, before its PRE-STEP, the sentence "Before Phase 0: verify no merge or rebase is in progress and the done lock is free; if either fails, stand down and write nothing." so a child never starts plan work on a checkout mid-merge, mid-rebase, or under a held done lock (mirrors the authoring fire-time gate; not part of the backlog source text).
- Authoring tail fix: in the backlog source the authoring blueprint's fill-in fields were mangled onto the end of the prompt body. The fenced body here ends with the 2026-09-15 stranding note (registered in the fire-time gate bullet below), not at the backlog source's final sentence; the source's ending sentence remains inside the body.
- Authoring role line: the authoring blueprint's fenced body opens with "You are the scheduled session, not a scheduler: perform the task below now in this session; do not create or schedule further automations beyond the re-arm duty below." followed by the clarifying clause that the "Schedule at {schedule_time} the following task:" sentence is the deciding turn's instruction (the child session performs the task itself now); chaining guard, not part of the backlog source text.
- Authoring fire-time gate: a pre-work check paragraph inserted right after the re-arm duty: "Before writing anything: verify no merge or rebase is in progress and the done lock is free; if either check fails, stand down and write nothing." The original gate also required the repository default branch; that clause was removed on 2026-09-15 with the dual-lane revision and replaced by two sanctioned additions (not part of the backlog source text): the explicit branch permission sentence "The current branch does not matter: commit on whatever branch the checkout holds, including an in-flight execution child's Phase 0 branch; the plan-document commits ride that branch's final squash merge as joint-state content." and the end-of-run stranding note "Before the done skill runs, if the current branch is not the repository default branch, your final report must note that your commits ride the current branch and are stranded if it is later abandoned unmerged."
- Child re-arm duty (2026-09-15, dispatch-ladder discovery; rewritten 2026-09-16 to the state-driven recycling form): both inner payloads carry, as their FIRST ACTION before any gate or phase, an identical paragraph that re-arms the recurring parent by reading the shared scheduler state file first and applying the first applicable step: reshape the session's own spawner record into the parent form when the recorded parent id belongs to this session's record (the ladder left it in child form), confirm an already-armed parent with at most one listing when a different id is recorded, and create or recycle only when no id is recorded, deleting the session's own lingered completed spawner record before a cap-refused create. An anti-loop guard stops all automation calls once two listings happen without an intervening mutation, and any other refusal escalates after two retries to the state file `rearm_note` field plus a `loop-parent-missing` memory note. The parent is recognized by title plus prompt opening and by the resolved repository root contained in the prompt (single dated record in the r2 hardening entry below); the literals live only in the overlay recipe and the pins suite, never in this file; creation and recycling follow the recipe in `agents/skills/maintenance/zcode.md` "Recurring automation recipe" as the single creation source; every state-file write is a targeted field edit. The duty exists because the dispatch ladder leaves the parent record in child form while the child is armed and the child session is the only unblocked session able to restore it. Not part of the backlog source text; this state-driven rewrite supersedes the 2026-09-15 listing-driven form, and the verified-live-2026-09-15 verdict certifies only that superseded listing-driven form; the recycling update this rewrite relies on is not yet verified live, tracked beside the verification recipe in agents/skills/maintenance/zcode.md ("Automation primitive verification").
- Authoring review-loop cap: the authoring body's review-loop clause carries "(cap 5 total rounds; at the cap finalize with the best available draft and record the residual findings in the plan)" (bounds the loop so an authoring child cannot outlive the 6-hour outcome horizon; not part of the backlog source text).
- Fill-in field line annotations: the field lines carry inline path annotations per plan Task 2: on the execution blueprint, `{execution_time}: at` and `{some_plan}: <plan-path-under-docs/plans>`; the authoring blueprint's field lines are already covered by the tail fix above.
- Post-completion compaction step (2026-09-16, user request): both inner payloads carry, as their final sentence, a duty to compact the session after the report (the runtime's session-compact command, e.g. /compact) so the next scheduled payload inherits a short transcript: compacting at the clean boundary right after a child's report means all state is already on disk, instead of letting the harness auto-compact fire at the context brink where its lossy summary degrades later turns (a plausible feeder of the re-arm action-selection-loop witnesses). A runtime exposing no session-invokable compact gets a one-sentence no-primitive note at the end of the report instead (ZCode as of 2026-09-16: the command is user-side, so the step is presently report-only; see the overlay's "Child dispatch ladder" session-compaction bullet). Not part of the backlog source text.
- Completion-time successor chaining (2026-09-16): the execution payload carries, immediately before its final compaction step, a single successor-dispatch duty paragraph (its anchor literal is pinned exactly once in this file, so it is paraphrased here): on a clean closeout it chains the next execution child by reshaping the session's own spawner record into the successor one-shot, selecting the target by the scheduler's first decision rule (memory dependency order, then the oldest open plan passing the certification oracle, then the oldest open plan outright, skipping plans the memory index marks dependency-blocked), honoring the quota leg's deferred-window and floor rules, refusing to chain when any other child entry is pending or the run was not a clean closeout, falling back to a delete-plus-create of the spawner record whatever form it then has, re-creating the armed parent when both fallback legs fail, and writing a memory note only when even the parent re-create is refused; exactly one successor per completed child, never after a stood-down or failed run. Not part of the backlog source text.
- Successor duty hardening (2026-09-17, r1 review address): the parent re-create leg that runs when both fallback legs fail now lists at most once before re-creating; when the listing shows an ENABLED recognition match (the recipe's title plus prompt opening literals), its id is adopted into "parent_automation_id" (targeted field edit) and the session ends without creating, and the re-create runs only when the listing shows no such match. The same paragraph gained a loop guard of the re-arm duty's shape: after two listings with no mutating step between them, the session stops touching automation primitives and ends, leaving the decision to the next scheduler turn. Not part of the backlog source text.
- closed: successor paragraph punctuation bridge (2026-09-17, r1 review; closed 2026-09-17): as landed then, the successor paragraph bridged its fallback leg into the both-legs-fail clause with a semicolon and a lowercase continuation where the plan's Task 3 exact-text block then showed a period and a capital at that seam; the pins suite pins the landed lowercase form and the plan block was synced to the landed form on 2026-09-17 (r2 review CC-1), so this seam deviation is closed and the entry is historical.
- Re-arm and successor r2 hardening (2026-09-17, r2 review address): the confirm, adopt, and already-exists matchers in the re-arm duty now require the automation's prompt to contain the resolved repository root, not just the recognition title and opening (mirroring the duplicate-parent tripwire); the idle-time dispatch reading is registered here, not pinned (it takes no record, and proceeds exactly as if "parent_automation_id" were null); the successor children[] entry records the post-mutation id per leg (the same automation id when the reshape leg ran, the fresh id of the created successor after the fallback create); the deferred-blocker skip rule matches the scheduler's D1 (a blocker that is still an open plan or a deferred plan under the resolved plans directory keeps the plan skipped). Not part of the backlog source text.
- Execution resume rule (2026-09-16): the execution payload carries, right after its pre-work readiness block, one sentence defining a continuation run: when the target plan already carries checked checkboxes at fire time, the child reads the execute-plan session manifest first, refreshes its update timestamp, and continues from the first unchecked task without redoing completed ones; the readiness re-certification covers the digest drift the checkbox marks cause. The manifest path is written as the literal repository-relative docs/tmp location on purpose: child payloads are self-contained and cannot resolve user-facts keys, and the facts currently pin that key to docs/tmp/, so a future facts override must revisit this payload text (recorded rationale, not an oversight). Not part of the backlog source text.
- Worktree review migration (2026-09-19, user request): both inner payloads carry a sentence requiring an ad-hoc-worktree run to move the review artifacts it wrote (review staging docs and .stats.json sidecars) from the worktree's docs/reviews/ into the primary checkout's docs/reviews/ and verify them present there. In the execution payload the sentence sits in the final merge paragraph, gated before the worktree removal that follows the squash merge; in the authoring payload it sits with the closeout sentences before the done skill (the authoring child never merges itself, so there is no merge step to hang the gate on). Rationale: docs/reviews/ is gitignored in this repository, so review artifacts never ride the branch commits, the authoring child's plain commits, or the final squash merge; an ad-hoc worktree's gitignored directory starts empty and is destroyed with the worktree, so an unmigrated run loses its entire review record (witnessed 2026-09-18: a dedicated-worktree execution run recorded that its staging docs survive only if they reach the primary checkout). The path is the literal repository-relative docs/reviews/ on purpose, same rationale as the resume rule's docs/tmp/ literal: child payloads are self-contained and cannot resolve user-facts keys, and the facts currently pin reviews_dir to docs/reviews/, so a future facts override must revisit this payload text. Not part of the backlog source text.

Legend: the deciding turn (the scheduler turn that made the decision) fills the four listed placeholders plus `{REPO_ROOT}` (in the execution blueprint's opening sentence and in the re-arm duty paragraph of both blueprints) when assembling the child prompt. `{execution_time}` (execution child fire time) is a scheduling-call input, never payload: it goes into the scheduling call's delay or cron fields. `{schedule_time}` (authoring child fire time) goes into the scheduling call and is additionally filled into the authoring payload's "Schedule at {schedule_time}" sentence, which the payload keeps as the chaining-guard explanation (the authoring child performs the task itself now); for an idle-time dispatch there is no scheduled fire time and `{schedule_time}` is filled with the literal `an idle-time run (no scheduled fire time)`. `{backlog_item}` (target backlog item path under `docs/history/backlog/`) and `{some_plan}` (target plan path under `docs/plans/`) are filled into the payload.

Distinguishable by the span "decline the plans skill". The fill-in fields follow the block:

