# ZCode runtime overlay for the maintenance skill

This file is the ZCode runtime overlay for the `maintenance` skill (`agents/skills/maintenance/SKILL.md`). SKILL.md stays runtime-agnostic; this overlay is loaded only when the runtime is ZCode. It carries the concrete scheduling primitives behind the skill's scheduling and guard steps, the recurring automation recipe that arms the loop, and the quota-leg procedure for Step 4. Wherever SKILL.md says "the runtime's scheduling primitive", this overlay names the concrete primitive.

## Scheduling primitives

- Recurring parent: create the recurring parent automation with `CronCreate`, passing a cron expression and `recurring: true`. There is one parent per repository; it fires scheduler turns on the cadence in "Recurring automation recipe".
- Child sessions: create each clocked child as a one-shot delayMinutes automation (the backlog's verified child shape: relative delayMinutes, no cron expression, `recurring: false`). delayMinutes is preferred for children because a self-computed absolute time that has just passed silently rolls a full year forward under a cron-pinned one-shot, though cron-pinned one-shots with `recurring: false` are also observed working in this repo's automation fleet (2026-09-13). An idle-time child uses the idle-time task primitive instead (see "Child dispatch ladder").
- In-session authoring primitive (added 2026-09-20): beside the idle-time primitive, the authoring lane can dispatch in-session: no child automation is created and the deciding turn runs the authoring blueprint's task paragraph itself (SKILL.md Step 5's in-session dispatch mode). The quota-signal input decides: when the quota leg's probe report is usable, used_percent is below the max-percent threshold, its decision is continue, and this session can carry the full authoring loop, the D2 rule authors in-session; when quota is scarce (used_percent at or above the threshold, or the decision is not continue) or a pricing deferral is active, or the session cannot carry the work, dispatch out through the clocked one-shot or the idle-time primitive instead. The child entry records the `(in-session)` target marker with a null automation id and the dispatch's quota_signal (SKILL.md Step 6).
- Rescheduling a live child (verified 2026-09-15): `CronUpdate` has no delay field, so pulling in a `delayMinutes` one-shot means converting it to a cron-pinned one-shot via `CronUpdate` (observed working). The cron fields are the user's LOCAL timezone: pinning a UTC hour lands in the past and silently rolls `nextRunAt` a full year forward (the same year-roll trap as a just-passed self-computed one-shot). Compute the local wall-clock hour, add margin, and verify the returned `nextRunAt` before treating the update as landed.
- Listing: list armed automations with `CronList`. The lane guards `G1e` / `G1a` (SKILL.md Step 2) read this listing: armed fire times, last-run timestamps, and the prompts of armed or recently fired automations. Observed listing fields (orchestrator first-hand evidence, 2026-09-14): every automation carries `automationId`, `title`, `cronExpr`, `prompt`, `enabled`, `lifecycleStatus`, `nextRunAt`, `runCount`, `recurring`; `lastRunAt` appears only after the first run and `maxRuns` only when set (both conditional). A one-shot child lingers listed after completion (enabled false, lifecycleStatus completed; linger model, corrected 2026-09-16: supersedes the 2026-09-15 disappears-at-completion claim) and still binds its spawner session before it ages out, so a child still running after firing is tracked by the lane guards' state-file arm, not by this listing. Fail-safe: an automation whose prompt is not visible in the listing counts as a potential child; treat the lane as busy.
- Merge landing lock (added 2026-09-20): landing critical sections on the default branch serialize under a second lock family in `scripts/done-lock.sh` beside the done lock (a holder may hold both at once): `merge-acquire [--label TEXT]` tries once, `merge-wait-acquire [--label TEXT] [--max-wait SECS]` polls with a bounded wait (the child blueprints cap the wait at 300 seconds), `merge-release` and `merge-release-repo` release token-fenced from the environment (`merge-release-repo` requires the env and never session-loads), `merge-status` prints the holder or `free`, and `merge-stale-clean` is the operator escape for a stale hold. Acquisition prints the `MERGE_LOCK_DIR` and `MERGE_LOCK_TOKEN` exports; the holder keeps both across the whole landing critical section. Stale threshold: `MERGE_LOCK_STALE_SECS`, default 600 seconds. A hold at or past that threshold, or one whose age cannot be resolved at all (metadata missing or unparseable), is the scheduler's `G3b` stale crash evidence (`turn_error: merge-lock-stale`, operator escape `merge-stale-clean`): it blocks no scheduler decision; a stale holder whose process is still alive keeps landing children in the bounded wait until an operator runs `merge-stale-clean`, while a verified-dead stale holder is auto-reclaimed by the lock's own recovery rules (dead-holder grace) without operator action. The escape's reach is scoped: `merge-stale-clean` removes a hold whose meta parses at the stale threshold and an aged meta-less hold (crash leftover), while a corrupted-meta hold refuses it by design and needs manual removal after inspecting the `merge-status` dump. Contention behavior for a child: bounded wait, then stand down keeping the branch and worktree and report.
- Child classification markers, applied to the prompts visible in the `CronList` output; the same markers catch manually scheduled children:
  - Execution child: a prompt containing `execute-plan skill` plus a path under the resolved `plans_dir` and the resolved repository root (the relative plans-dir substring alone also matches foreign repositories' prompts; the SKILL.md widened-arm containment gate applies before classification; SKILL.md Configuration; default `docs/plans/`).
  - Authoring child: a prompt containing `author a plan`; in flight it is also witnessed by its claim file at the literal `docs/tmp/authoring-claims/<backlog-item-basename>.md` in the primary checkout (frontmatter `session:`, `item:`, `created:`, `updated:`), which the guards' `G1a` discovery arm (SKILL.md Step 2) reads with the freshness constant: a claim whose `updated:` is fresher than one cadence period (2 hours) is fresh, and one at or past that age is stale. The occupancy rule (which claim occupies the authoring lane, and the pending authoring `children[]` entry whose target item basename can explain one) lives in that discovery arm, and the claim lifecycle with the worktree/primary-checkout rationale lives in the authoring payload's AUTHORING CLAIM duty (`agents/skills/maintenance/prompt-templates.md`); the guards' discovery arm and the payload agree on this literal directory (the payload cannot resolve facts keys; the same literal-path rationale as the resume rule's `docs/tmp/`).
  - The markers are a shortcut, not a necessary condition; the full lane rules are SKILL.md `G1e` / `G1a` (per lane; the lanes are independent: executions are strictly sequential, authoring children may run alongside an execution and land via self-landings under the merge landing lock instead of committing on whatever branch the shared checkout holds; a held merge lock is a `G3b` defer condition, never a whole-turn stand-down). The duplicate-parent tripwire matches the title-less span shape, not the full recognition rule: an ENABLED automation whose prompt begins with the scheduler prompt template's first line, "You are the maintenance scheduler for the repository at", and whose prompt contains the resolved repository root; the recognition rule's title conjunct is deliberately not required (per the residuals plan's triage notes and development lesson #391: a hand re-created duplicate with a drifted title must still trip). Child payloads never begin with that line and never carry it as a literal (the re-arm duty names the recognition rule by reference to the recipe), so they never span-match. The execute-plan claim check the guards' discovery arm cites is `scripts/execute_plan_runtime.py`. When uncertain, treat that lane as busy.

## Recurring automation recipe

- Cadence: `15 */2 * * *` (every 2 hours at :15; raised from every 4 hours to hourly on 2026-09-15 and to every 2 hours the same day by user request; token-frugal: the turn itself is a few greps plus one primitive call).
- Title: `Maintenance scheduler turn (every 2 hours)` (the recognition title the child payloads' re-arm duties match by reference to this recipe; the payloads and sibling files never carry the literal, so there is nothing to keep in sync with them; pinned by `scripts/check_maintenance_pins.sh`).
- Prompt: the scheduler prompt template below, with `{REPO_ROOT}` replaced by this repository's absolute path at automation-creation time. Never commit the resolved absolute path into the repo; this template keeps the placeholder literal.

```text
You are the maintenance scheduler for the repository at {REPO_ROOT}. Run the maintenance skill (agents/skills/maintenance/SKILL.md) scheduler turn end to end: survey the work surface, apply the guards in order, decide per lane and schedule at most one execution and one authoring child per the skill, update the scheduler state file. Standing pre-authorization: never block on questions, decide and proceed; never push to origin. If the skill says stand down, record the reason in the state file and stop.
```

- Re-arm hygiene (rewritten 2026-09-16 to the state-first duty shape governing the re-arm decision of its two named actors: the turn's Step 0 and rearm-on-touch sessions; the shape is the template other re-arm actors may follow, the watchdog, child, and Step 1 memory-note-reader duties carrying their own embedded shapes): consult `.ai-playbook/scheduler-state.json` first and decide state-first from the recorded `parent_automation_id`, the pending `children[]` entries, and `parent_absent_since`, so two parents never run the same cadence; at most one listing is permitted, after the mutation decision and never before it; delete the own lingered record before a create the automation-born cap refused; when a create instead reports the parent already exists, verify the ENABLED recognition match (title plus prompt opening, the prompt containing the resolved repository root) and treat it as success; when the listing shows an ENABLED repo-contained recognition match, the session also clears `parent_absent_since` in its targeted edit. After re-arming, update `parent_automation_id` in the state file to the new parent's automation id so the id-first parent exclusion in SKILL.md `G1e` / `G1a` stays accurate (a null id forces the span fallback; a stale id makes the live parent a differing-id span match, which the duplicate-parent tripwire's self-heal arm adopts automatically when it is the sole live span match). Loop guard: if you have listed twice without a mutating step between listings, write the `rearm_note` field via a Bash state edit naming the loop and stop touching automation primitives; when the recipe re-arm instead succeeds, clear `rearm_note` in the same targeted state edit that records the new `parent_automation_id`. The parent may also be intentionally absent while a child is in flight: the dispatch ladder surrenders the parent slot to the child (operative delete-plus-create: the parent record is deleted and the child one-shot carries a fresh id; the demoted recycling leg kept the same id in child form), and the child re-arms the parent as its payload's first action and updates the recorded id, so a turn must never schedule a second parent merely because it sees none besides its own spawner.

```text
Schedule at {schedule_time} the following task: Using the plans skill, author a plan covering backlog item: {backlog_item} ...
```

This block is for interactive asks from a fresh session (no child re-arm duty). The standing pre-authorization and authoring-constraint sentences are carried verbatim by the authoring blueprint in `agents/skills/maintenance/prompt-templates.md`; this section references that blueprint for them instead of restating them. ## Child dispatch ladder

- Ladder precheck (added 2026-09-19): before entering the ladder, assert the session's toolset exposes the mutating primitives the decided dispatch needs (user-level lesson #341: verify the executing context's primitives before dispatch), per the path the decided dispatch takes: a fresh unbound chat needs only `CronCreate` (ladder step 1 takes no delete); an automation-born session needs `CronCreate` plus `CronDelete` (its own lingered record must be deleted before a cap-refused create); `CronUpdate` is only a recycling-optimization input (the step 2 optimization leg is its only consumer and is gated on a live-verified flip recorded in "Automation primitive verification"), so its absence alone never blocks dispatch; an idle-time child needs `OffPeakCreate`; an in-session authoring dispatch (the D2 quota-signal decision, SKILL.md Step 3) needs no mutating primitives at all, because the decided dispatch runs in the deciding turn itself, so its precheck is satisfied without any primitive and the ladder's create steps below are not entered for that lane. The precheck is lane-scoped: on absence, stand down only the lane whose decided dispatch lacks its primitives, park or retain that dispatch per the selection-loop trap rule in the step 3 bullet below (`pending_dispatch` via a Bash state edit), and evaluate the other lane's precheck independently: record `turn_error: clocked-primitives-absent` for the clocked lane, `turn_error: idle-primitive-absent` for the idle lane. When both lanes' prechecks trip in one turn, record a single `turn_error` with the most severe reason (`clocked-primitives-absent` over `idle-primitive-absent`), mirroring the existing most-severe-reason precedence for the single `turn_error` field; `pending_dispatch` is single-valued (one object or null, SKILL.md state schema), so it holds the more severe lane's park while the other lane's decided dispatch is recorded alongside it (named in the same state edit's `decision_reason`), so nothing is silently lost. A tripped precheck stands its lane down with zero listings performed, so the selection-loop guard in "Dispatch discipline and loop stand-down" fires only on genuine listing-without-mutation loops and is never burned reaching for a statically absent primitive.
- Child dispatch: create the child per the ladder below, using the SKILL.md Step 5 dispatch slice for the payload (the clocked child shape is pinned under "Scheduling primitives" above); record the child in the state file per SKILL.md Step 6.
- Cron-tool boundary (witnessed 2026-09-16): the automation primitive family is main-session only. A spawned sub-agent's toolset carries none of `CronCreate`/`CronUpdate`/`CronDelete`/`CronList`/`OffPeakCreate`, so delegating a scheduled-child create fails with the tool absent; the payload-owning session must issue the create itself, and the dispatch ladder below (including its report-only last resort) applies to that session alone. See user-level lesson #341 (verify the executing context's primitives before dispatch).
- Automation-born create cap (verified live 2026-09-15): a session bound to a scheduled task (spawned by one, or having created one) is refused `CronCreate` with "Cannot create a scheduled task inside a session that already belongs to a scheduled task" while an automation it is bound to is armed; deleting that armed automation lifts the block in the same session, and every successful create re-arms the block. One session lineage can therefore hold at most one armed created automation at a time: the parent and a child cannot both stay armed when created from the same lineage. `CronUpdate` and `OffPeakCreate` are not gated by this check; completed one-shots linger listed (enabled false, lifecycleStatus completed) and stay deletable by remembered id, still binding their spawner session before they age out. Cap-model refinement (verified live 2026-09-16): the block also fires with NOTHING armed: a completed bound spawner record still held its child session's binding and the create was refused until that completed record was deleted by remembered id, after which the same create succeeded. Completed records are therefore not inert for the cap: a bound session that must create recycles or deletes its lingering record first (the successor-chaining backlog's record-recycling candidate builds on exactly this), and the earlier "deleting the completed record did not lift" witness (2026-09-02) is superseded by this observation.
- Session compaction (verified absent 2026-09-16): ZCode exposes no session-invokable compaction primitive: the /compact command is user-side and the harness auto-compacts only at the context limit. Both child payloads still carry a post-completion compaction step (see prompt-templates.md's deviation list): it is report-only today (the child ends its report with the no-primitive note), and it binds without further edits once a future runtime exposes the primitive. Rationale: compacting right after a child's report records all state on disk at a clean boundary and keeps the long-lived loop chat away from the auto-compact brink, where the lossy summary degrades later turns (the re-arm action-selection loop was first witnessed in long, duty-saturated turns; the 2026-09-18 witness fired in a fresh, non-duty-saturated session between the mutation decision and its emission, so turn length is not a reliable predictor).

  3. - Watchdog backstop: after a successful step 2 dispatch, arm a one-off idle-time watchdog with `OffPeakCreate` (ungated). Slot caution (verified 2026-09-15): a session holds one pending idle-time task and a queued one has NO cancel primitive (`CronDelete` and `TaskStop` both refuse it; it is invisible to `CronList`), so arming the watchdog burns the idle slot a second-lane dispatch would need; when the second lane may dispatch this turn, dispatch it first and skip the watchdog (the authoring payload's re-arm duty covers the same check), or defer the watchdog. Its payload checks the listing when it runs and, if no ENABLED automation matching the recognition rule (title plus prompt opening) whose prompt contains the resolved repository root, and no armed child, exists for this repository, re-creates the parent per the recipe, updates `parent_automation_id`, and clears the state file's `rearm_note` plus a repo-matching `loop-parent-missing` memory note when present. Refusal handling names two levels explicitly (`docs/plans/completed/2026-09-16-maintenance-scheduler-liveness.md` Task 2, which folds r4 item 4, reworded 2026-09-16 for the recycling ladder). Level 1, arming refusal by the dispatching turn: when the turn's watchdog arming (the OffPeakCreate arming after a successful step-2 dispatch) is refused for any reason, treat it as a no-op: the detector will not exist this cycle, and the `rearm_note` human check and the staleness rail remain. Level 2, the watchdog payload's own re-arm create refusal: the payload lists immediately before its create and reuses that listing as its re-arm decision input (no second listing before the create), treating an already-exists refusal as success only after the same ENABLED verification the child duty applies; when that verification fails, the already-exists case routes to the child duty's escalation (record `rearm_note`, write the repo-keyed `loop-parent-missing` memory note, continue) instead of silently succeeding (`docs/plans/completed/2026-09-16-maintenance-scheduler-liveness.md` Task 2, watchdog side), and any other refusal keeps the level 1 no-op semantics. The watchdog runs inside the dispatching turn's session and only works while that session survives to receive idle compute. This is the only out-of-lineage detector for a child that dies before its re-arm.
- Idle-time lane visibility: children dispatched via `OffPeakCreate` never appear in the automation listing; run `OffPeakList` during the Step 1 survey and treat a queued or running idle-time child as lane-occupying for its lane (`G1e` / `G1a`) when its ` sessionId matches the current session` OR a pending `children[]` entry in the state file records that task (an entry whose target carries the `(idle)` marker, `created_at` matched where the idle listing exposes it; the state-file hold outlives the dispatching session, so a later scheduler turn still sees it); a foreign-session queued task is demoted to report-only (never lane-occupying) only when no pending entry records it (watchdog-shaped residue). The own-session half of the attribution is evidenced, not assumed: the idle-task listing exposes a session identifier matching the current session (observed 2026-09-16). Convert from the UTC+8 anchor at runtime and never pin local hours: the local offset moves with DST (the window reads 07:00-11:00 local at UTC+1 but 06:00-10:00 at UTC+0).
- Usage multipliers: GLM-5.3-Flash deducts 0.4x off-peak and 1.2x peak; GLM-5.3 deducts 1x off-peak and 3x peak. - Runtime-fit rule (supersedes the 2026-09-15 60-minute fire-time horizon; every lane estimate below is at least 60 minutes, and the witness carries over: a mid-run exhaustion surfaces as a provider 429 that kills the child session): before a clocked dispatch, answer the fire-time fit question with the probe's --fire-at <iso> --need-minutes <lane-estimate> mode: can a child of this lane finish in the window remaining at the planned fire time? Lane estimates are the upper bounds (execution 240 minutes; authoring 120 minutes). Exit 3 (defer-reset) defers the fire past reset_at_epoch regardless of pricing preference; exit 2 (defer-peak) defers to the peak window's end. The starvation exception beats pricing (exit 2), never fit (exit 3).
- --fire-at mode contract: python3 scripts/quota_window_probe.py --fire-at <iso> [--need-minutes <N>] [--straddle-minutes <N>] [--peak-window HH:MM-HH:MM] [--peak-offset-hours <N>] answers both dispatch questions for any proposed fire time, from any session type; the fire-at value must carry a UTC offset (+HH:MM). Exit 0 = fire as planned (off-peak and fits); exit 1 = status unknown or unusable window data (fall back to the per-lane cap; never invent a deferral); exit 2 = peak with a fitting deferred slot (defer to the window's end, 18:00 UTC+8 the same day); exit 3 = unfit at the fire instant or at the deferred slot (defer past the containing window's reset). The deferred slot is fit-checked before exit 2 is blessed, so exit 3 already encodes the fit-over-pricing precedence. Without --need-minutes the mode is a pure pricing computation and never touches the network. Argparse usage errors also exit 2 with no JSON on stdout, so parse the verdict from the JSON and treat an empty report as status unknown. The default window constants mirror this file's tracked seed (Mon-Fri 14:00-18:00 UTC+8, weekend off-peak, --peak-window 14:00-18:00 --peak-offset-hours 8); a turn holding a fresher pricing_cache extracts the HH:MM-HH:MM range and the UTC offset from the cache's peak_window value (which carries the prose form, for example Mon-Fri 14:00-18:00 UTC+8) and passes them as --peak-window 14:00-18:00 --peak-offset-hours 8.
- Off-peak preference (the Step 4 pricing rule): when the final fire time for a child lands inside the peak window, defer it to that window's end (18:00 UTC+8 the same day) so the child's run bills at off-peak rates; a fire time in the last hour before the window opens defers too when the lane is the execution lane, whose observed runs of one to four hours would otherwise straddle the window (pass --straddle-minutes 60 for the execution lane so the --fire-at mode applies the same straddle rule). Before deferring for pricing, verify the deferred slot passes the runtime-fit rule; when it does not, the --fire-at verdict is defer-reset and the fire moves past the containing window's reset (the mode fit-checks the deferred slot before blessing exit 2). Exception: when the execution lane has had no dispatch in the last 24 hours or more (per SKILL.md Step 4's starvation observation), starvation beats pricing and the child fires immediately despite peak; starvation never beats the runtime-fit rule. The rule stays fire-time-based by design: a run that starts off-peak may still reach the window, and that residual is accepted.
