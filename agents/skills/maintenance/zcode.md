# ZCode runtime overlay for the maintenance skill

This file is the ZCode runtime overlay for the `maintenance` skill (`agents/skills/maintenance/SKILL.md`). SKILL.md stays runtime-agnostic; this overlay is loaded only when the runtime is ZCode. It carries the concrete scheduling primitives behind the skill's scheduling and guard steps, the recurring automation recipe that arms the loop, and the quota-leg procedure for Step 4. Wherever SKILL.md says "the runtime's scheduling primitive", this overlay names the concrete primitive.

## Execution-claim runtime identity

ZCode passes `--runtime zcode` on execution-claim create and refresh; this inventory ID is never inferred.

Load the named module in full when its consuming step runs (load-on-dispatch). For that lookup, read this router and the active module. Do not load the full pre-split body. ## Headless clocked-order fire sessions

A clocked order's payload runs in a headless `zcode --prompt` session the order's launchd carrier starts in the recorded repository root; the generated shell wrapper registers the order's 60-minute handoff lease in the order ledger (`clocked-order-begin-fire`) before the launch and clears it when the launch fails, so the due scan defers while the lease is live and recovers the order after it expires. The session's own sequence: the maintenance child re-arm FIRST ACTION (`agents/skills/maintenance/duties-core.md`) first, then the discharge operation (`clocked-order-discharge-on-fire`) with the session id taken from THIS runtime's context and passed explicitly through `scripts/session_channel.py --session-id` (never an inherited environment variable; no runtime-context id stops the session before any ledger write, discharge, or payload). The operation holds the order ledger lock across order validation, the live-lease check, the executor-session-id recording on the exact order id, and the one-time pending/armed-to-discharged transition, so a concurrent fire waits and then refuses without replacing the recorded id, and an expired lease refuses the discharge too. On any blocked result the session stops before the stored payload (the order keeps its payload retained for the failure-cap repair window); a refused re-arm keeps its `rearm_note` plus paired `pending_rearm` park untouched, the refusal is never a dispatch gate, and recovery of an order the session never discharged belongs to the due scan's missed classification after the lease expiry.
