## Plan Lifecycle

- **Landing closeout - origin coverage and duplicate-origin refusal (hard gate):** Under the primary resolution these landing-critical-section steps read against the primary placement's completion: the completion closeout's immediate-commit commits replace the rider-and-squash sequence, there is no source branch to keep or remove, and the closeout migration's transfer is a no-op by construction. When a newly authored plan lands, resolve every scripted landing gate below repo-local first, then the deployed `~/.ai-playbook/scripts/` copy, and first run the coverage gate `python3 scripts/check_plan_origins_closed.py --check-coverage <repo-relative plan path>`; the gates branch on the outcome contract: exit 0 (`OUTCOME: pass`) lets the landing proceed; exit 1 (`OUTCOME: fail`) refuses the landing, the coverage gate's refusal naming the covering plan and the remedy: first-landed wins - fold the later plan into the covering plan as an amendment, or reject the later plan as superseded through the rejected archive; exit 2 (`OUTCOME: indeterminate`) and exit 3 (`OUTCOME: tool_error`) stop the landing without a refuse verdict and are never read as a pass (the state is re-derived from disk before any retry), and a run that ends without its final `OUTCOME:` line is treated as a tool error the same way. After the gate passes, run `--mark-covered <repo-relative plan path>` so the covered flip of each named open origin rides the landing commit with the covering-plan witness recorded repo-relative as the pending-execution token `covered-pending-execution (<repo-relative plan path>)` (plan docs/history/plans/2026-11-04-execution-lane-authored-plans-misread-as-landed.md Task 3; the execution landing's `--execution-flip --recorded-tip <pre-squash tip>` invocation returns the row to the legacy `covered (<plan path>)` witness and flips the plan-header `Executed:` field); that run branches the same way: exit 1 (`OUTCOME: fail`, an origin already covered by a different plan), exit 2 (`OUTCOME: indeterminate`, an origin unreadable at classification time), and exit 0 (`OUTCOME: pass`) completes the flip. The flip runs before the landing critical section and the flipped origin files are committed on the authoring branch as rider commits, so the landing commit carries them; also before the rider commit the landing runs the reverse-squash guard's `check-claim-fence --base <merge-base> --head HEAD` over the landing range and branches the same way: exit 1 (`OUTCOME: fail`, a plans-root deletion under a live claim) refuses the landing and takes the deferred-landing path keeping the branch and worktree; the PLAN-PROMPTS prune rule is evaluated against the tree the landing carries and a matched entry's deletion joins the same rider commit, the landing pruning only its own dispatch entry plus discovery-listed collateral served entries under the log's `Coverage and removal rule` label (the entry whose prompt authored the plan being landed; any other removal routes through the maintenance monitor's rolling prompt log duties, never a landing side effect), the prune evaluated per the log preamble's Standing rules block's `Prune rule` and `Coverage and removal rule` labels (range inventory, per-origin coverage, partial narrowing with freeze retention, the single full-removal receipt, receipt preservation, and target refusal are that rule's, not restated here) and printing one `PLAN-PROMPTS-PRUNE: <slug> -> <witness path>` receipt line per fully removed entry, a partial removal adding none (the witness path names the landing-time plans-root path; a later execution archives the plan into the completed archive under the same basename, so a receipt path that no longer resolves at the plans root is looked up there, never read as a missing witness); before the rider commit the landing runs the prune audit `python3 scripts/check_prompt_log_origins.py --prune-audit --repair --base <merge-base>` (the landing-only automatic repair mode: a flagged receipt-line deletion is restored from its exact committed bytes into both pending images and the audit reruns; the landing continues only when the rerun passes, and an exact source that cannot be established, a repair that cannot be safely applied after one fresh-read retry, or a rerun that still fails names its specific condition and stops the landing) and branches the same way: exit 1 (`OUTCOME: fail`, a log removal without its plan-file witness) refuses the landing and takes the deferred-landing path keeping the branch and worktree; a flip or prune landing on main after the landing commit is the defect the check-single-commit sweep flags. A landing whose merge or rebase resolved conflicts routes the resolution to the canonical conflict-content discipline (union-of-intents with its post-resolution re-verification duty) in the landing critical section of agents/skills/execute-plan/SKILL.md. The committed-bytes precedent: the covered flip's `Status: covered-pending-execution (<repo-relative plan path>)` witness format is the digest-free shape all closeout riders follow (the legacy `covered` token reads as pending execution under the row-lifecycle semantics until the execution flip). **Post-squash certification diagnostic (warning-only):** after squash, lock release, and worktree reconciliation the lifecycle runs a warning-only certification diagnostic adding no closeout condition, runtime branch, retry loop, or lock: it runs before the archive move, so the plan path and the review identity it resolves are the pre-archive active path's, while the verification head, landed-byte, and seal-anchor checks still verify the post-squash state. Bind the receipt to its own run first: from the captured `DONE_RUN_ID` and `DONE_RUN_MANIFEST` select the setup manifest at the facts-resolved `{tmp_dir}/done-session/run-manifest-<run_id>.json` path; the expected source worktree root derives from that path and both the diagnostic's source-worktree root and `git rev-parse --show-toplevel` must equal it; the manifest `repo_root` must equal that root's canonical SHA-256 digest, the `run_id` must match, the sole `owned_plan_paths` entry must be this plan, and the expected `source_worktree_head` reads from that same root, so a different worktree with the same HEAD fails the root-path comparison. Then prove the context: capture the primary checkout's landed base tip once as a full commit OID (`git -C <primary-checkout> rev-parse --verify HEAD^{commit}`) and the source worktree's tip the same way, confirm the primary OID readable in the source repository (`git -C <source-worktree> cat-file -e <verification-oid>^{commit}`), read both anchor ids from the untracked seal, and run `git -C <source-worktree> merge-base --is-ancestor <anchor> <verification-oid>` per anchor, each required to exit 1; with context established run `python3 scripts/plan_readiness.py --verification-head <verification-oid> <repo-relative plan path>` and, only after readiness passes, `python3 scripts/validate_review_staging.py --verification-head <same verification-oid> --hard <highest ready review record for this plan> --source-plan <repo-relative plan path>`, both validators reading plan and seal files from the source worktree with every HEAD-dependent check on that same explicit immutable OID (never `GIT_DIR` or `GIT_WORK_TREE` overrides), the landed OID, source-worktree HEAD, plan-byte digest, and seal-byte digest captured before and after each validator call and at the full diagnostic boundaries; the staging validator's stderr is the observable degraded-grading signal (`corrections grading degraded`); each run appends one serialized receipt to `docs/history/certification-seal-landing-diagnostics.md` in the primary checkout, row-routed by the matrix below; mask before append (the ledger's content contract owns the duty): before the append write, mask every embedded resolved filesystem root in the assembled receipt body to the procedure's placeholder tokens or a repo-relative form, and run the pre-append probe over the body (scan for non-placeholder resolved filesystem roots, home-directory prefix or absolute checkout/worktree path); a probe hit refuses the append with the named remediation (mask the hit, re-express the receipt, re-run the probe once), an unresolvable hit takes the matrix's terminal arm below, so recurrence never depends on the release privacy gate; this bounded mask-and-re-probe cycle is the one excepted in-diagnostic re-run to the no-retry-loop preamble above.
- **Post-squash diagnostic outcome matrix (single source for receipt branch behavior; both receipt ledgers name it; the archived certifying-plan matrix is historical):** every row warning-only - report it and leave refusals actionable through needs-recert without blocking closeout; rows in order:
    - Run identity missing, unreadable, ambiguous, or unequal: neither validator runs; record expected and observed plan and worktree identities, warning `not_observed`, append directly to the fallback ledger as an identity mismatch, never a primary-write failure.
    - Primary append fails: the same serialized receipt plus the primary-write error routes to the fallback ledger `docs/history/certification-seal-landing-diagnostic-write-failures.md`, the escalation chain's single home; a failing fallback append (either route) emits the receipt and write error to the running maintenance session transcript for the existing sunset recovery, no retry, no closeout stop.
    - Pre-append probe refuses and masking cannot clear the hit (a legitimized literal): the receipt is appended to the primary ledger in the best achievable masked form with the unresolved hit named in its body, outcome recorded with the warning value carried; the receipt is never silently dropped.
    - Landing-context proof fails or is inconclusive, a source-worktree ref, plan, or seal write cannot be excluded from the first identity snapshot through receipt creation, or identities change between captures or the seal is absent: neither validator runs, outcome recorded inconclusive, warning `not_observed`, primary ledger.
    - Readiness identities match and readiness does not pass: staging does not run, warning `not_observed`, primary ledger.
    - Readiness passes with matching post-call identities and staging passes: the confirmed outcome, warning `absent`, primary ledger.

- When all items are `[x]`, move the file to `{plans_completed_dir}/` and, in the same pass, append exactly one ownership-registry row for it (row shape per `doc-hierarchy`; at minimum fill the cells `identity`, `sot: no`, `state: completed`, `archived: YYYY-MM-DD (the actual archive date of this completion pass; never a date copied from the plan filename or prescribed by a plan task)`, and `src` in registry column order; on a routine completion the `audit` cell stays empty, and the execution summary lives in the landing commit message and the archived plan's disposition section, never in the registry row); completion is this archive move plus that single row append. The archive step's commit must not add an archive file whose live basename survives the same commit un-deleted and un-renamed; a surviving live twin is a defect the completion pass fixes before commit (it is the failure signature of copy-not-move routing and re-presents executed work as open). **Archive-egress check (commit-then-inspect, before any publication or handoff step):** once the archive commit is built on its placement branch (the authoring branch under the worktrees resolution; the primary placement's completion commits under the primary resolution), and before any publication or handoff step (the done handoff, the cross-repo commit, the docs-branch sync), run `python3 scripts/reverse_squash_guard.py check-archive --rev <archive-commit> --repo <root>`; exit 1 resets the branch tip back one commit keeping the working tree, and reports the guard's named evidence and the sanctioned exits (verify the work and check the boxes, land the marked backfill completion record, take the rejected path, or the operator-directed ack); exit 2 is a tool failure: stop and report; the posture is commit-then-inspect on the built archive commit, never a staged-input call. The archive pass's one allowed body edit, the promoted-backlog disposition section, changes the plan bytes, so the archive rider refreshes the execution receipt's digest to the final archived plan bytes before the archive commit and its `check-archive` run. The ack rules match the execute-plan landing critical section's plans-egress archive gate: `--ack-egress` is passable only on the operator-directed-archive exception, the operator direction recorded in the scheduler state file's turn record (the same record home as the landing leg), and the acked egress path restated in the archive commit's message as an `Archive-egress-ack:` trailer. **Cited-receipt existence check (fail closed, before the archive move):** every review record path the plan header cites (the header's review-record link, whichever label form it uses, `Plan review:` or `Plan review record:`, plus any cited review records) must exist in `{reviews_dir}` before the archive lands. A missing cited review record blocks the archive, with two remedies in order: first land or restore the stranded receipt (a worktree's gitignored `.ai-playbook/reviews/` is the witnessed stranding cause); only when no copy exists anywhere, demote the archive to an explicitly recorded reconstruction - append a reconstruction note to the archived plan naming the missing receipt and the re-verification evidence replacing it (the shape of a marked backfill completion record) - never a certified archive over a silent missing receipt. Do not rewrite task checklists or Gist after archive; the only allowed body edits in the same pass are the short promoted-backlog disposition section described in the next bullet, and an explicitly marked backfill completion record plus per-checkbox `(backfilled ...)` markings on an already-archived plan, licensed only when the record documents the contemporaneous evidence the backfill substitutes for. Committed witness lines (registry audit notes on new rows, disposition sections, and Status lines) name repo-relative paths and dates, never a landing digest; the digest belongs to the commit message and the session-side receipts. (the registry row's audit note and the disposition section it lands with follow the same rule). Review records that cite the pre-archive plans-root path (coverage artifact/sidecar links and a closeout re-validation's `--source-plan` operand) resolve through the completed twin under `{plans_completed_dir}/` at validation time (the staging validator's archive-twin resolution, scoped to the facts-resolved plans layout, with identity staying the pre-archive path and, on the `--source-plan` arm, the stale-digest gate binding the twin's bytes), so the archive move relocates or rewrites no review record.
- When the plan promoted a `{backlog_dir}` item, in the same completion pass: append a short disposition on the archived plan under `{plans_completed_dir}/` (the disposition is a `## Disposition of migrated backlog items` section whose body names the former backlog path; the per-origin row may still be a one-row table or bullet, but theme naming survives only inside the section body, never as the heading: a theme-named heading never matches the archive consult's anchor and leaves the deleted origin unexplained), append one ownership-registry row for the promoted backlog identity (same cell shape as the plan row per `doc-hierarchy`), then **delete** the `{backlog_dir}` file. When the origin was flipped covered earlier in the run, this completion pass is where the fold, the registry row, and the delete land; never a separate later pass. Do **not** move dated item files into `{backlog_completed_dir}/`; that directory may exist for tooling compatibility but must stay empty of per-item archives. If several same-theme backlog files complete with no single matching plan name, squash their dispositions into one section on the completed plan rather than leaving multiple completed backlog files. The same section also admits rejected follow-up rulings: rows inside the section body (the heading stays literal per the archive consult's anchor rule; rejected rulings read as the section's non-migrated arm and are never a reason to rename it), each marked as a rejected ruling with its ruling evidence and no former-origin path claim. The section is appended whenever rejected rulings exist even with zero promoted items, and the archive-egress check's inline section naming above covers the rejected-only arm the same way. A manual-lane run's conversion duty (the manual-execution paragraph's pointer to execute-plan's Phase 4, ordered before the archive move) feeds the same section with its promoted and rejected rows. **Deletion-side witness sweep (ordered duty, before the pass's deleting change is built):** grep `scripts/machinery_registry.json` and `scripts/check_maintenance_pins.sh` for every tracked path the pass's diff deletes or moves, re-point each hit to its verified durable home in the same change (verified with `git ls-tree` plus a content-head check, never exit code alone; citation precedence: the covering plan's `{plans_completed_dir}/` twin), explicitly including registry rows the same pass created, and run `python3 scripts/machinery_inventory.py --check` green before the deleting change lands. This deletion-side witness sweep is an ordered text duty, not a new gate: a sweep finding no hits costs two greps and one check run, a hit whose durable twin cannot be verified stops the pass for operator disposition rather than re-pointing blind, and the survey's machinery regrowth guard consult remains the backstop.
- When superseded, archive the plan instead of deleting it: move it to `{plans_completed_dir}/` and append a registry row with `state: superseded` and the superseding plan's identity in the `successor` column (`superseded_by`). Record the superseded backlog disposition on that plan (or the superseding plan), then **delete** the `{backlog_dir}` item in the same pass instead of moving it to `{backlog_completed_dir}/`.
- When rejected (an explicit decision against doing the work), archive the plan instead of deleting it: move it to the plans `rejected/` archive (conventional `{plans_dir}/rejected/`, see its README) with the body preserved verbatim, and append one registry row with `state: rejected`, `archived: <rejection date YYYY-MM-DD>`, and a non-empty `reason` cell. Move rejected `{backlog_dir}` items to the backlog `rejected/` archive in the same pass, recording the decision inline as `Status: rejected (YYYY-MM-DD; reason)`, plus one registry row each (same cells). Rejected records are permanent history: lifecycle tools treat them as closed/archived, and revival is a new decision through the normal lifecycle, never an in-place edit of the archive.
- **docs/tmp cleanup (same completion pass, after the archive):** delete the finished plan's `{tmp_dir}` scratch so it cannot accumulate: `{tmp_dir}/plan-requirements-<slug>.md` and its machine-state companion `{tmp_dir}/plan-requirements-<slug>.json` (the watcher state file is deleted in the same completion pass as the `.md` notes so the state file cannot outlive its owner under the done sweep) and `{tmp_dir}/execute-plan/<plan-slug>/` (session logs of a successfully completed plan), plus `{tmp_dir}/review-loop*` / `{tmp_dir}/code-review/` staging that this plan's own review rounds created, but only when that loop's staging is final (the loop reported a clean round); an ACTIVE loop's unsynced staging is never deleted here (same liveness caveat as the landing sweep's docs-tmp-sweep gate). When ownership is unclear, leave it in place. Archive first, then clean. The `docs-branch` sync keeps `{tmp_dir}` local-only and does not clean it; cleanup remains with the lifecycle or `done` tmp-sweep owner.
