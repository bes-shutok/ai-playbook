## Budget gate (plan-authoring pause and resume)

Plan authoring runs the same long review loops that quota exhaustion kills mid-flight, so this skill carries its own quota-window pause-and-resume gate. Resolve `budget_pause_minutes_before_reset` (fallback `20`), `budget_pause_max_used_percent` (fallback `90`), `budget_pause_min_protocol_minutes` (fallback `10`), and `budget_probe_runtime` (fallback `auto`, unchanged semantics) from the opening TOML block of `.ai-playbook/facts.md`.

**Boundaries:** the orchestrator runs the probe before launching each review-plan round in the Plan Quality Gate loop, before every fold batch and every mechanical audit pass inside the loop (the between-boundary probes), and before the final done handoff; never mid-worker and never mid-fold. The runtime budget-guard backstop hook (`agents/hooks/budget-guard/`) enforces the pause at the tool-call level once registered (fixture-verified on one runtime; pending the first-start trust-prompt approval and the deny-envelope drive on the other runtime, see the budget-guard README), so a mid-round quota exhaustion cannot silently burn the window. A wall that kills the run off-boundary (the backstop hook unregistered, or a provider exhaustion kill mid-worker or mid-fold) routes to the maintenance decisions' 5h-wall arm: the arm records the wall and its reset-anchored one-shot carries the resume right after the reset. A mid-run usage-wall refusal this boundary can still act on (the at-boundary class, distinct from the off-boundary kill above) routes instead to the quota leg's mid-run wall arm in `agents/skills/maintenance/quota-policy.md` for the conversion, coverage consult, carrier arming, and pause-surface recording, per that arm by reference. Under the kill-case arming route this Boundaries paragraph owns, the first capable turn after the reset arms from the lane's recorded quota evidence (a relayed quota reset notice included, carried by the lane's stop record or an operator or peer relay) when no standing carrier covers it; the kill case's arm slot keys on the wall notice's own reset instant, never the fresh probe's next-window reset; the coverage consult's scheduler-slot leg does not satisfy this route's coverage check, only a carrier carrying this lane's own marker does; and the arm's prompt carries the lane marker the coverage consult matches; a turn capable only after that slot has passed never arms a past instant (the runtime's silent year-roll): it checks the lane live (a live lane session ends the duty as already resumed) and otherwise leaves the resume to the first fresh-probe boundary after the reset, recording the wall evidence in its decision_reason.

unsupported harness budget skip: before resolving the probe, run scripts/harness_detection.py (resolved like BUDGET_PROBE minus its env-override leg: repo-local copy first, then the deployed home copy); when it reports `harness: none` and no `budget_probe_runtime` override is configured, record `budget_skip` in `{tmp_dir}/plan-requirements-<slug>.md`, skip the probe, the pause protocol, and the resume watcher, and continue, leaving any existing pending resume watcher to its own stand-down checks; the skip path never arms or clears the guard flag (when a `budget_probe_runtime` override routes the run back through the probe, the probe's own flag semantics apply, and that override is the only way to run the family on an unsupported harness); a missing or erroring helper counts as unsupported (record the evidence; the family must not run against an unknown harness).

At each boundary, resolve and run the probe:

```bash
# Three-step probe resolution mirroring the execute-plan Budget gate: BUDGET_PROBE env override first; then the repo-local `scripts/quota_window_probe.py` when present; then the deployed $HOME/.ai-playbook/scripts/quota_window_probe.py.
BUDGET_TOP="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"
BUDGET_PROBE="${BUDGET_PROBE:-}"
if [ -z "$BUDGET_PROBE" ] && [ -f "$BUDGET_TOP/scripts/quota_window_probe.py" ]; then
  BUDGET_PROBE="$BUDGET_TOP/scripts/quota_window_probe.py"
  echo "budget gate: using repo-local probe at $BUDGET_PROBE" >&2
fi
BUDGET_PROBE="${BUDGET_PROBE:-$HOME/.ai-playbook/scripts/quota_window_probe.py}"
python3 "$BUDGET_PROBE" --minutes-before <N> --max-percent <P> [--runtime <id>] --plan <plan-slug> --write-flag ~/.ai-playbook/runtime/budget-guard.flag [--min-protocol-minutes <N>] [--plan-cost <percent>]
```

- Exit codes: `0` = pause decision, `1` = continue, wait-for-reset, or `status: unknown`. Parse `pause_decision` from the probe's stdout JSON report, never from the exit code.
- Usage gate first: a pause is a candidate only when used_percent is at or above the max-percent threshold or when the next round cannot fit the remaining quota; clock proximity with low usage is a continue.
- When the notes name a comparable earlier round panel's observed window cost, pass it as --plan-cost <percent> and follow the report's wave_recommendation (full / split with wave_size / pause; on pause run the pause protocol instead of launching the round). A pause decision always outranks any wave_recommendation: on pause_decision: pause run the pause protocol instead of launching. Without a recorded comparable cost, omit the flag.
- On `pause_decision: continue`, continue the normal flow. A missing or unopenable probe script is treated as `status: unknown`, noted in `{tmp_dir}/plan-requirements-<slug>.md`, and the flow continues; it must never block authoring.
- On `pause_decision: wait-for-reset`, ride the boundary through in-session: the authoring loop records the boundary supersede through `plans-watcher-supersede` before waiting (the wait-for-reset boundary supersedes and clears any pending resume watcher, arms no flag, writes no receipt and no `budget_pause` record), waits the reported wait_minutes minutes, re-runs the probe, and the fresh report governs the boundary (continue schedules per the known-binding-only watcher branch below; pause runs the pause protocol below). Details stay canonical: this section defers to the execute-plan Budget gate section on conflict.
- The `--write-flag` argument makes `write_flag_if_paused` arm the guard flag (`~/.ai-playbook/runtime/budget-guard.flag`) on a pause decision, so the registered backstop hook has something to enforce. The weekly `secondary` binding still writes no flag and schedules nothing.
- On `pause_decision: continue` with a trusted binding reset epoch, schedule the same standing resume watcher the canonical Standing resume watcher subsection defines, at the authoring boundaries (before launching each review-plan round in the Plan Quality Gate loop; at every between-boundary probe inside the loop; before the final done handoff): reset time plus one minute, self-disarming, replaced at each later boundary, stood down on progressed, peer-resumed, archived or completed, or aborted or interrupted where the authoring runtime records an interrupt (same newer-than-scheduling comparison against the authoring machine state, so a latched old interrupt never trips a later watcher); otherwise the scheduling-snapshot and plan-state checks carry the stand-down. This is the known-binding-only watcher branch: a `status: unknown` report or a weekly `secondary` binding schedules no watcher, and every non-schedulable boundary (unknown, weekly secondary, pause, wait-for-reset, abort, complete) supersedes and clears a pending watcher per the canonical record rule. The authoring pause-protocol fallback chain is unchanged (the sentinel self-disable one-shot-scheduler case and the report-only naming stay as written above).

**Authoring watcher state:** the machine-state home for that mirror is `{tmp_dir}/plan-requirements-<slug>.json`: it stores `progress_revision`, `user_interrupt`, and the fenced `resume_watcher` receipt (watcher id, plan slug, canonical repository root, canonical plan path, plan-byte digest, scheduling epoch, reset epoch, expected generation, expected progress revision, current boundary generation, binding, status, and replacement predecessor), written under the shared watcher lock with the same compare-and-swap replacement and cancellation fences. `{tmp_dir}/plan-requirements-<slug>.md` remains the human notes and audit projection: it receives a projection line only after a lock-held state transition, and the watcher never infers authoring progress from Markdown `updated:` text. The authoring loop updates the machine state under the shared watcher lock before and after each review round and done handoff, so a scheduled watcher's expected progress revision goes stale exactly when authoring moved. The plans `WatcherStateAdapter` in `scripts/execute_plan_resume_watcher.py` invokes the one shared watcher state machine and owns the replacement, cancellation, boundary generation, canonical plan path and digest, semantic-progress, peer-resume, archive, completion, abort, and interrupt fences (the plan digest is recomputed from the canonical plan-file bytes at every watch). The machine state is driven through the authoring CLI operations (r2 F11), each taking the payload `state_path` naming `{tmp_dir}/plan-requirements-<slug>.json` (plans-watcher-schedule additionally takes the FULL probe report JSON as probe_report, plus plan_path and the plan slug as plan_slug (the same slug the state filename carries): never a subset, because the classifier reads `status`, `binding`, `pause_decision`, and the binding limit's `reset_at_epoch` from `limits[]`; a subset classifies unknown and the boundary degrades to the report-only supersede, so read the receipt's reason after every scheduling call): `plans-watcher-schedule` records the boundary decision and runs the fallback chain at this boundary, `plans-watcher-supersede` clears a pending watcher, `plans-watcher-fire` is the automation prompt's fire entry over the authoring state, `plans-resume-marker` records a resume-path re-entry so a scheduled watcher stands down on the peer fence, and `plans-progress`, `plans-interrupt`, and `plans-terminal` record the progress revision, the user-interrupt fence, and completion, archival, or abort (the CLI exposes these explicit authoring operations). The fresh-install boundary (verified 2026-09-25, plan 2026-09-25-done-sweep-residuals-and-stale-origin-dispositions Task 4): a fresh (absent) state file at a trusted continue boundary installs at generation 0 inside the lock-held compare-and-swap and schedules (`status: success`, `reason_code: resume-watcher-scheduled`), so the compare-and-swap stale verdict stays reserved for genuinely raced boundaries; a refused install degrades to the named report-only supersede with the inner reason carried in the outcome evidence, recorded deliberately instead of retried blind. No absent-file fast path exists outside the existing compare-and-swap predicate, and none may be added: the concurrent-fresh-install race (two fresh installs at the same boundary) is absorbed by the compare-and-swap itself, exactly one succeeding and the other answering stale-attempt. The per-tick plan-digest recompute stays an exact-byte drift fence because the corrections record's identity-digest boundary keeps equality as the check (identity digests sit outside the graded surface): a firing after a recorded correction is an expected drift refusal, and the resumed session re-adjudicates the delta through the graded Step 0.5 digest rule.
- On `pause`, run the pause protocol:
  1. Finish the current boundary only; do not start new work.
  2. Keep the guard flag armed (it is host-global: while armed it gates every session's tool calls on the host until expiry or manual removal). When the binding window is the weekly `secondary`, write no flag, still append the record (step 4) with resume_scheduled: no, schedule nothing, and report for user decision instead.
  3. On a host whose agent runtime supports one-shot scheduled automations, create the resume automation FIRST at the reset time rounded up to the whole minute plus one, then record the boundary through `plans-watcher-schedule`: at this boundary the pause decision supersedes and clears any pending watcher, writes no `resume_watcher` receipt, and runs no scheduler chain (the canonical record rule; a pause boundary is non-schedulable), so the created automation carries the resume. Suppression risk (loop-quality hygiene plan, 2026-09-23): that automation-first create is a mutating emission, and a pause-boundary resume decided but not emitted must be carried by a state write, not narration (the emission-suppression stand-down in the maintenance skill's runtime overlay, its Dispatch discipline and loop stand-down section). On the automation-born lineage-cap refusal the authoring boundary deletes the session's own completed spawner record and retries the create once (or, when the session's automation lineage is the armed recurring parent, skip the deletion and walk the fallback rungs directly; details stay canonical), and when no gated create can land it falls to the host idle-time automation rung before report-only, per the canonical lineage-cap branch and Resume carrier fallback ordering in the execute-plan Budget gate section (details stay canonical). The automation's self-contained prompt carries the same two-half resume contract as the canonical pause protocol's step 5: on a pause boundary (no receipt was written) there is nothing for the fire operation to evaluate, so the prompt performs the epoch-checked manual clear itself - re-enter the plans review loop on the plan path, read this run's `budget_pause` record from `{tmp_dir}/plan-requirements-<slug>.md`, verify the latest review sidecar digest still matches the plan bytes (a budget pause never edits the plan, so no re-certification is needed), clear `~/.ai-playbook/runtime/budget-guard.flag` and `budget-guard.fired` before relaunching only if the flag's `reset_at_epoch` matches the reset epoch recorded in this run's `budget_pause` record (otherwise leave both in place and report the mismatch: the flag encodes a different, still-live window, another runtime's or a newer window of the same runtime; if the flag (or fired marker) is already absent, nothing is armed, so proceed with the relaunch and note the pre-cleanup in the record), re-reading the flag immediately before each deletion and aborting the clear if its `reset_at_epoch` changed since the match check (mirror the hook core's re-read-before-unlink pattern: a concurrent probe may have replaced the flag in between), and stand down if the plan is archived or completed or a peer session resumed the work; this manual procedure is the no-CLI fallback path of the protocol, and on a pause boundary it is the only path. When a pending receipt exists (a watcher scheduled at a continue boundary), the prompt's fire contract is the authoring fire entry `plans-watcher-fire` (the manifest-free CLI over the payload `state_path`): the operation applies the fences and the four stand-down checks and clears the guard flag and fired marker only on a resume decision, so the prompt must not re-apply the stand-down checks or delete the guards by hand. A cleanup call issued before the window resets may itself be denied once by the guard; retry it after that single block.
  4. Append a `budget_pause` record (runtime, reset epoch and ISO time, thresholds used (including the protocol margin), next step that would have run, and resume_scheduled: yes|no - `yes` when step 3's orchestrator-created automation exists (the call's supersede leaves nothing else pending) or when the host idle-time automation rung carries the resume (step 3's fallback walk); `no` when nothing could be scheduled (the report-only and weekly-secondary cases)) to `{tmp_dir}/plan-requirements-<slug>.md`. Beside the record, the pause path writes or refreshes the authoring claim's `parked-state:` line per the convention home's write arm in the AUTHORING CLAIM paragraph (agents/skills/maintenance/template-authoring.md, by reference) -- this claim-file parked-state record is distinct from the `plans-resume-marker` watcher operation named above, which records a resume-path re-entry, not parked state.
  5. Fall back to a host one-shot scheduler job with a sentinel self-disable file when automations are unavailable on a schedulable boundary (a continue with a trusted binding reset epoch); if neither capability exists, end report-only naming the exact resume command and time. On a pause boundary there is no one-shot-scheduler carrier either (a pause runs no scheduler chain): the resume follows step 3's fallback walk in the canonical ordering, the host idle-time automation rung before report-only (the canonical Resume carrier fallback ordering paragraph governs; details stay canonical), and when no rung can land, report the exact manual resume command and reset time and treat the resume as manual, per the canonical pause protocol's report-only step. (This compresses the canonical two-case one-shot-scheduler split into one step; the compression is a declared delta, see the Canonical home note below. The one-shot scheduler job and the report-only naming are rendered by the shared schedulers in `scripts/execute_plan_resume_watcher.py`, whose arm now bootstraps the job into the host scheduler and treats a failed bootstrap as not-scheduled falling through to report-only, r2 F4; the plans-authoring boundary uses the `PlansAuthoringWatcherAdapter` over `{tmp_dir}/plan-requirements-<slug>.json` and its `plans-watcher-*` operations, with `plans-watcher-fire` as this mirror's fire entry.)

Every resume path (the scheduled automation's prompt, a fired standing resume watcher, and any manual resume) first reconciles a budget_pause record carrying resume_scheduled: no by completing the scheduling step before continuing work. Beside that reconciliation, and per the canonical Budget gate's carrier discharge duty (added 2026-11-09; plan `docs/history/plans/2026-11-06-budget-resume-carrier-gc.md`): a resume by any route other than its own carrier's verified fire, or a run reaching its closeout boundary with its own carrier still armed or still loaded, discharges the run's own armed carrier through the `budget-carrier-discharge` operation when a recorded `armed_launchd` receipt exists (or the fired history event retained one); the resume-path duty's home is the canonical Budget gate section of `agents/skills/execute-plan/SKILL.md`, and the closeout duty's home is the `Terminal closeout ownership` paragraph of `agents/skills/execute-plan/worktree-first.md`. Exception: a record whose binding is the weekly secondary window stays report-only - report for user decision and never schedule.
