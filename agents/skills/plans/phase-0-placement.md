## Phase 0: Authoring Placement Setup (Run at Every Authoring Session Start)

**Agent-type affinity (authoring entry; blocking hold per the contract):** before any placement setup or plan work, apply the shared compatibility contract (`projects/.ai-playbook/agent-runtime-layout.md`, the Agent-type affinity contract section, the rule's one home; this entry references it and never restates it) between the session's backlog origin or target plan and the invoking agent's active identity: a declared `Required agent type` mismatch is reported naming both identities before authoring, the origin's declared value is carried into the plan's metadata block as the line `Required agent type: <id>` per the contract's propagation rule, an unrecognized declared target or an absent or unknown active identity holds only this authoring work open with the identity reported, and an origin or plan without the line stays runtime-neutral.

Before any plan work, resolve the session's authoring placement per the project worktree policy (Phase 0's steps below are placement-conditional). The **Worktree-first standard** section in `agents/skills/execute-plan/SKILL.md` owns the canonical lifecycle; this phase adds only the authoring specifics below and never restates those steps. Plan creation, ordinary plan updates, and completion all run this setup (see **Create vs update** above); an active execute-plan referral follows **Active-plan referral placement** below and adopts that run's recorded placement without independent provisioning. The worktree-setup steps below run under the policy paragraph's worktrees resolution (and the absent-key fallback); under the primary resolution the same steps read against the primary checkout on its current branch as the placement root, with no worktree, no authoring branch (beside a company-profile run's recorded task branch), and no squash landing (the completion closeout commits per the immediate-commit rule instead).

**Announce:** "Before writing or editing the plan, I'll resolve the authoring placement per the project worktree policy. Under the worktrees resolution I'll set up the session's ad-hoc worktree, which keeps authoring isolated from the primary checkout; under the primary resolution all authoring work runs in the primary checkout with no run worktree."
**Authoring claim:** before any plan work, run the AUTHORING CLAIM duty. An interactive session with no backlog origin (a direct user request) extends the duty's `item:` line to carry the plan slug instead of a backlog path; under the gate's three-key match a plan-slug claim can still match a backlog-item target through its other two keys (a filename stem equal to the target's origin row basename or entry slug), so a selection consult skips on a fresh matching plan-slug claim exactly as on any other matching claim. Do not restate the recipe's operational steps in this file.

**Active-plan referral placement:** when execute-plan refers a scope change for its active plan, use that run's existing placement. Before editing, verify the exact plan path, session manifest identity and `source_digest`, the plan's current digest immediately before editing, and the execution claim's session and branch against the recorded worktree and branch or primary checkout and branch tuple. Run the existing lock-free pre-work guard: inspect merge/rebase state and the read-only `done-lock.sh status` plus `merge-status` results. Any identity mismatch, digest drift, active merge/rebase, or held finalization lock leaves the referral pending without a write or new task claim. Do not create a second worktree or second branch, second execution run, closeout baseline, or acquire a nested done lock. With the checks clear, create or refresh the normal plans authoring claim through the AUTHORING CLAIM duty and keep it through execute-plan completion. Delete the claim only after execute-plan closeout verifies placement-matched completion-claims evidence, using the maintenance-template claim-deletion procedure.

**Authoring-run continuation ownership (entry boundary):** before resuming or mutating an existing authoring run this session did not start, prove ownership from the run's durable records in this order: the plan header's permanent `Authoring claim:` line is the durable provenance naming the originating run's session, the live claim file's `session:` line is the current-ownership record, and the run worktree and the `authoring/<claim-file-stem>` branch are placement evidence only and never proof of ownership. User authorization to work on a plan never substitutes for the ownership proof. Continuation proceeds only when one of exactly three pass conditions holds: this session's id equals the header marker's session id; the live claim's `session:` line names this session; or an owner-recognized transfer exists (the operator's explicit transfer direction recorded beside the run, or the claim lifecycle's own hand through the stale-foreign-claim takeover path). The rule fires at the continuation entry, before this session's own claim or worktree provisioning for the target; when no pass condition holds, the outcome is preserve-and-route: the session preserves the run's work untouched and reports the provenance evidence needed to continue (marker session id, claim session id and `updated:` timestamp, worktree path, branch name), routing to the operator decision (authorizing a transfer or declining) per the self-heal skill's Recovery step 5. The tie-breaker is scoped to that ambiguous path: when no pass condition holds and the durable surfaces disagree or one is missing, attribute the run through the session store's message payload per development lesson #229 in the project lessons corpus to establish the evidence for the transfer or operator decision; a held pass condition is never re-adjudicated by the session store, and a session-store attribution never overrides a matching marker-and-claim pair. Claim discovery for parallel-origin races and execute-plan resume selection stay within their separate contracts. The session's boundary listing at this entry also runs the parked-state pickup read per the convention home's pickup clause in the AUTHORING CLAIM paragraph (deferred by reference, never restated here). Closed runs are out of scope: a run is closed when no claim file, no run worktree, and no standing authoring branch remain for it; a plan-update round proceeds per the Authoring ownership marker's update-round rule, a completion (marking a plan done) per Create vs update, and an Active-plan referral per Active-plan referral placement above, the session identifying itself in its own claim file in each case; this entry boundary governs only resuming a run with standing live state (a claim file, live or stale, a run worktree, or a standing authoring branch).

**Entry freeze (entry-keyed authoring runs):** a run whose claim file is keyed to a `PLAN-PROMPTS.md` entry slug or to one of that entry's `Origins:` rows writes the entry's `Frozen:` line at the primary checkout's tracked log on the default branch, committed there as part of Phase 0, beside the claim write and before plan work, witnessed by the slug-keyed claim file; placement, timing, and the negative branch-only shape are owned by the log preamble's Standing rules block's `Freeze rule:` placement clause, which this duty points at and does not restate, and a freeze already present is verified, never rewritten (on a primary-placement run whose current branch is not the default branch, the freeze rides the run's current branch and the completion record names it). The freeze write is a primary-checkout log write under the log preamble's Standing rules block's `Write boundary rule` label in `docs/history/backlog/PLAN-PROMPTS.md` (lock order, owned-path staging, and recovery live there), the primary done lock keyed from primary-checkout context per that rule; this duty's delta: on any lock refusal the session releases each acquired lock, removes only this session's claim file through the AUTHORING CLAIM procedure's ownership-checked delete, and stands down before any plan-file work. A worktree-placement freeze whose default-branch target differs from primary `HEAD` uses recovery naming the required checkout alignment and resumes only after primary `HEAD` reaches the default branch; unchanged state is never retried and the transaction recipe is not restated here.

### Step 0.1: Create the worktree and transfer the facts in

The setup consults the project worktree policy per the Worktree-first standard's policy paragraph before creating or adopting anything: a project resolving the policy paragraph's primary resolution runs this authoring lane in the primary checkout on its current branch with no run worktree, under the primary resolution's serialization and immediate-commit rule, and no placement conflict exists to report (the consolidated policy spells no conflict-and-stop arm). Under the worktrees resolution: create the ad-hoc worktree on its own branch off the base branch resolved by the canonical section's **Base-branch resolution rule**, and report the worktree path and branch name. Then transfer the project facts document in per the canonical section's **Transfer-in implementation** (this phase's literals: `.ai-playbook/facts.md`, plus any other gitignored inputs this authoring session resolves, such as the reviews directory, in before any gate or plan-file write). Under the primary resolution: skip creation and transfer-in; the facts file already resolves in the primary checkout; record the primary placement in the session's placement report.

**Closeout-evidence establishment duty:** before any gate or plan-file write, the setup establishes the closeout baseline the Final Step's `done` closeout consumes, exactly per the execute-plan skill's bootstrap capture contract, whose block owns the invocation shape, the sibling body, and the guard semantics. Per the establishment boundary, the worktree setup is incomplete until one of the two records exists. The capture arm: from the session's placement root (the worktree root, or the primary checkout under the primary resolution) run `capture --out {tmp_dir}/execute-plan/<PLAN_SLUG>/closeout-baseline.json` over the facts-resolved dirs. The failure arm: on capture failure write the sibling `closeout-baseline-skip.json` per that block's failure arm and fail this step loudly as the degraded arm: the step is reported degraded, and because one of the two records now exists the setup is complete and the session proceeds (never as if a baseline exists), the closeout later degrading to the sanctioned scoped copy. The executable owner: `scripts/worktree_closeout_migrate.py` owns both records' semantics, and this duty never fabricates a skip record without a failed capture nor infers an empty baseline. The slug rule: the plan slug in the capture path is fixed for every session shape and derived by the execute-plan canonical session-slug rule (execute-plan run-setup's Step 0.4, session bootstrap): a date-prefixed plan file or claim stem contributes the name after stripping the leading date and the `.md` extension, which is the same canonical path the done runner's consumer (`plan_session_slug()` in `scripts/done_run.sh`) resolves for the baseline lookup; a creation session fixes that canonical slug before setup completes (recording it in the claim when it differs from the date-prefixed dispatch stem) and keeps it as the saved filename stem, and the stem the readiness gate and the Final Step handoff later resolve is one and the same.

Already-provisioned recognition arm: when the authoring session already runs inside its dispatch-provisioned ad-hoc worktree, that payload-created worktree satisfies this phase per the canonical section's provisioned-worktree adoption rule (Worktree-first standard, lifecycle step 1): adopt it instead of creating a second, key plan-file writes to its root per Step 0.3, and treat the worktree setup as complete once the adoption check passes and the closeout-evidence establishment duty above has produced one of its two records. The worktree's own branch is the authoring branch.

### Step 0.3: Key plan-file writes to the worktree root

Every plan-file write in this session lands inside the worktree, and the skill-gate marker recipe keys its project root from the write target (see **Writing** above); this phase's literal is the write target itself: the worktree root. Under the primary resolution, the write target is the primary checkout itself. On a runtime whose adapter passes a session id (Claude, Cursor), the recipe's `--session-id "$SID"` flag is required, or the marker is keyed no-session and the gate refuses the edit; in the worktree case, the session moves its working directory into the worktree before the first plan-file write and refreshes the marker with `--cwd` set to that worktree, so the consult keys the write-target derivation (never a second marker for the primary checkout).

**Hard gate:** Do not write the plan file until the worktree setup is complete. A worktree creation failure stands the session down per the canonical section's fail-closed stand-downs: report the failure and end the session without writing anything (no plan writes, no marker writes, no session logs); never improvise a fallback placement, because the primary checkout is authorized only by the policy paragraph's primary resolution.

**Authoring ownership marker:** from the first plan-file write onward, the plan header carries one line under the metadata block, `Authoring claim: <claim basename> (session <session id>)`, identifying the Phase 0 claim without recording its temporary-storage path. The line is permanent provenance once written: it remains unchanged through certification, landing, and archival, per the canonical marker-lifetime rule owned by the AUTHORING CLAIM procedure in `agents/skills/maintenance/template-authoring.md`; this skill prescribes no marker removal. Existing path-form markers remain readable as legacy provenance. The marker write is scoped to the plan's first authoring round: a plan authored before the permanent-provenance rule carries no header marker and an update round never adds one; on a plan-update round the existing header line stays as written, and the updating session identifies itself in the mutable claim file it writes for the update (the AUTHORING CLAIM procedure's claim filename keys to the target backlog item's basename, so the update session's own claim file fits that procedure), never by editing the header line. Digest binding starts at certification, so pre-certification header churn costs no recertification round. The maintenance liveness probe never reads the plan header: it matches a candidate plan's slug or identity against fresh claim-file text, never the header marker.

### Step 0.4: Authoring checkpoint duty (D-10, the wip-auto-checkpoint plan)

**Announce:** "I'll checkpoint the plan file under the `wip:` marker at every authored plan write and verify the round-start anchor commit before the first review round."

At every authored plan write (not only at task boundaries), the authoring session commits the plan file on its authoring branch under the `wip:` checkpoint marker (the execute-plan skill's checkpoint commit-marker convention; mechanical plan-bytes-only safety commits, never operator-approved), so a worktree loss or session death never destroys an authored-but-uncommitted plan; the final squash landing absorbs the checkpoint commits unchanged; under the primary resolution they accumulate on the current branch and the completion closeout accounts for them per the immediate-commit rule. **Round-start anchor (canonical authoring sequence):** before the first review round, verify the latest `wip:` checkpoint commit contains the plan path and its plan bytes hash to the digest recorded as `round_start_digest`; use that commit as `round_start_commit`. Every later plan-file edit takes a new `wip:` checkpoint, a fresh review round, and a new exact-byte anchor for the changed plan; review-plan's round-close seal consumes it. Rule 12's fold-prevalidation fix edits excepted: a fix edit takes its own wip checkpoint whose subject carries the marker fix-edit:, and never takes a fresh round of its own; its delta joins the batch's fold delta.
