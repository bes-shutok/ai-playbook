## Integration Points

### With `bootstrap-ai-playbook` skill
Writes and refreshes `.ai-playbook/facts.md` when Terms triggers fire (`using-skills` Step 0). This skill reads `{plans_dir}`, `{plans_completed_dir}`, `{reviews_dir}`, `{tmp_dir}`, and `{rfcs_dir}` from that file.

### With `execute-plan` skill
Consumer of plan format, task order, `## Validation Commands`, `## Review Scope`, per-task commit lines, and completed-plan archival. Each task's `Files:` declaration, optional `Primary class anchors:` block, and acceptance checkbox witnesses define the intended implementation scope and observable outcome. Keep supporting test paths, fixtures, and exact task commands out of plan prose; execute-plan selects those from repository evidence and records them in the task log. Execute-plan tasks run one at a time through the host-native sub-agent capability; the parent owns task selection, validation, checkpointing, commits, and review handoff. Tasks are admitted only by the Checklist inclusion gate: repository implementation, or a release gate with a current bound exception receipt plus `why executable now` and observable `completion evidence`. External prerequisites are never exception-admissible. Both skills run under the **Worktree-first standard** section in `agents/skills/execute-plan/SKILL.md`: `plans` resolves its authoring placement through the standard's policy paragraph at every authoring session start (creation, update, and completion; the ad-hoc worktree setup under the worktrees resolution, the primary checkout under the primary resolution); `execute-plan` runs the same standard's lifecycle as its Phase 0 run setup. After plan creation or update, hand off to `execute-plan` only on a separate request for that exact plan; Step 1.4 confirms writing only. Scope control happens at plan authoring: execute-plan stays faithful to the plan and never re-grills or re-opens scope mid-implementation; overscope discovered during execution is reported, not silently implemented beyond the plan, and not silently dropped. Reverse record: execute-plan's missing-plan remedy routes stranded inputs through this skill's Final Step handoff (the stranded-input pre-pass), by reference.
The active-plan referral contract is classified under execute-plan's `## User Interruption`, which owns worker evidence, same-run digest refresh, and the closeout handoff after placement-matched completion-claims evidence. Phase 0 here owns placement and claim retention; the maintenance-template claim-deletion procedure remains the sole deletion policy. The two skills also share the follow-up disposition contract: this skill's Outcome composition carries the authoring-time declaration duty, and execute-plan's Phase 4 carries the closure-time conversion duty.

### With `self-heal` skill

An edit to either surface carries the sync obligation to the other.
### With `maintenance` skill
Bidirectional authoring-claim contract. Producer side (this skill): Phase 0's Authoring claim step writes the claim surface (the resolved tmp directory's `authoring-claims/` at the primary checkout) that the maintenance Step 1 survey and D2 authoring selection consult, so a same-origin collision refuses at authoring start instead of after review rounds; this skill's Final Step invokes the template-owned deletion procedure after the verified completion-claims boundary for the session's placement and deletes on an owned stand-down, per the AUTHORING CLAIM procedure's refusal-retention and ownership rules (provider: the AUTHORING CLAIM paragraph in `agents/skills/maintenance/template-authoring.md`; this skill owns only its closeout order and placement evidence). Reader side (maintenance): the Step 1 survey reports an occupied target from that surface, and the D2 selection skips it, records the skip in `decision_reason`, and admits it as a sanctioned must-dispatch exemption reason, per the D2 paragraph and the survey's Authoring-claim consult in `agents/skills/maintenance/SKILL.md`. Authorization handoff: the maintenance authoring payload's standing authorization selects the Phase 1 maintenance-selected arm for the D2-selected item and scope; every other invocation keeps the ordinary confirmation and grill paths.

Loop-duty binding: any session performing maintenance-lane work through this skill whose plan lands under the resolved `{plans_dir}` or whose origin is an open backlog row binds, by reference, the D-18 exit duties (`docs/maintenance/operator-directives.md`) - the closing `loop-liveness:` line (its dispatched-child duty in `agents/skills/maintenance/duties-core.md`), the exit-token recording, the boundary quota probe per the Step 4 quota leg, and the starvation composition per the Loop modes Starvation switch paragraph in `agents/skills/maintenance/SKILL.md`, with the composed D2 scan-hold sentence in `agents/skills/maintenance/decisions.md` as the in-file composition home. The binding's structural trigger is the work happening in a repository whose scheduler state file exists at the primary checkout (the first `git worktree list --porcelain` entry's `.ai-playbook/scheduler-state.json`); an interactive one-shot ask whose picks are complete records its exit through D-18's per-run-directive composition clause (`directive-cap` naming the ask), never `queue-empty`. The composition never fires where the Project-class guard's survey-only resolution or the state file's `survey_only` flag stands the lanes down, a condition the session resolves by reading the facts document's `project_type` under the guard's confirmation semantics (the Project-class guard paragraph, `agents/skills/maintenance/SKILL.md`) and the `survey_only` flag at the primary checkout's state file before composing.

### With `review-plan` skill
The `plans` skill provides the Checklist inclusion gate to its consumer, `review-plan`. Plan review verifies that checklist items are repository implementation, and that every release-gate exception has a current bound receipt plus a meaningful `why executable now` and observable `completion evidence`. A task checkbox that is an external prerequisite stays blocking and is never exception-admissible; an owned one under Ship when is the sanctioned form (review-plan Step 2 item 8).

review-plan's Declaration findings paragraph verifies the Outcome `Gate delta` declaration and escalates unpaid counted-class additions (consumer: review-plan); the authoring rules consume the origin `Class:` line owned by receiving-review's Backlog capture.

Plan review's Step 1 tracker-source audit consumes the Sources inspected record this skill renders at Step 1.4 confirmation and carries into the plan's Assumptions; plans owns the record's shape, review-plan owns the audit and its finding class (provider: plans; consumer: review-plan).

Plan review's Step 1 dependency-derived scope audit (item 10) consumes the reconciliation decisions this skill's Phase 1 dependency-derived deliverable reconciliation records in the confirmation block's Scope extensions entry (provider: plans; consumer: review-plan).

Review-plan Step 5 rule 12 owns the fold-gate-dispatch ordering this loop's Plan Quality Gate rule 14 mirrors on every authoring-loop fold batch, and its prevalidation outcome lines are the reflection input plans Plan Quality Gate rule 12 reads (provider: review-plan; consumer: plans). The ordering consumes plans Validation rules 22 and 29, the Pre-review text-policy sweep's pins member, and plans Plan Quality Gate rule 14's fold-receipts audit by reference (provider: plans; consumer: review-plan).

### With `grill-with-docs` skill
The Phase 1 confidence gate invokes `grill-with-docs` for every unclear point rated low-confidence on the direct interactive path (the maintenance-selected arm resolves by recorded receipt instead, per the maintenance-selected arm paragraph). That skill runs a `grilling` interview with `domain-modeling` active throughout, capturing glossary terms and ADRs inline while each point is resolved; confirmed answers feed the requirements buffer, and the plan references the updated glossary/decision docs instead of duplicating terms. High-confidence points skip the grill and land in the plan's `## Assumptions` section instead. The Phase 1 scope-extension hard gate routes every proposed scope extension through this skill before the plan file admits it; the confirmed outcome (in / split / defer) lands in the Step 1.4 confirmation block as a grilled scope extension (the maintenance-selected arm excepted: under the maintenance authoring payload's standing authorization the extension resolves as `omit-extension` by recorded receipt, never a backlog row).

### With `grilling` skill
When the user (not the confidence gate) asks to grill a decision during Phase 1, invoke `grilling` for one-question-at-a-time resolution without doc capture. Do not replace the plans interview structure; grilling deepens specific decisions. Agent-detected low-confidence unclear points route to `grill-with-docs` (see above).

Sync note: the Step 1.4 confirmation meta-rule in this skill restates grilling's generic-acknowledgement, lifecycle-verb, answer-state, and opt-in-phrase rules for confirmation-time self-containment, so an edit to either set of clauses must update the peer in the same change.

### With `done` and `docs-branch` skills (docs/tmp cleanup)
Plan completion deletes the plan's `{tmp_dir}` scratch (Plan Lifecycle bullet). The landing sweep's docs-tmp-sweep gate sweeps ownerless `{tmp_dir}` entries before sync, and the `docs-branch` sync drops branch-tracked `{tmp_dir}` paths absent on disk (its one sweep-eligible root), so branch copies propagate without hand-editing the docs branch.

### With `receiving-review` skill
Provider of the backlog lifecycle that **Backlog capture** points at: captured items live under `{backlog_dir}` with `Status` / `Workflow: backlog` header lines. This skill promotes an item by referencing it from a plan header (**Backlog origin**) and, when the implementing plan completes (**Plan Lifecycle**), folds disposition into the completed plan then deletes the backlog file (no per-item `{backlog_completed_dir}` archive).
