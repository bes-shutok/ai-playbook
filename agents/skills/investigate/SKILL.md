# Investigate

**Purpose:** pre-authoring investigation for one open backlog item or a small set of related items, producing a dispatch prompt routed by the work-type verdict. The skill runs autonomously, asks the user nothing, and produces exactly one artifact per investigation: a single entry in one of the two tracked rolling prompt logs, ordered most urgent first. A plan-worthy verdict lands the entry in the plan-creation log (`docs/history/backlog/PLAN-PROMPTS.md`); an ad-hoc-able verdict lands it in the ad-hoc work log (`docs/history/backlog/EXEC-PROMPTS.md`).

**Corpus-level invocation:** an ask whose object is the whole backlog corpus runs this skill's contract over the corpus: the Stage 0 cluster survey doubles as the corpus roster, the pass emits one entry per investigated group (the entry count is the group count, not one per pass), an open item the survey leaves ungrouped is its own single-origin group under the same contract, and the per-turn single-investigation bound stays the maintenance scheduler's binding and never a skill bound. Run the pass as bounded units: the census doubles as the roster, and the pass runs one group per unit through the existing stages to a validated same-turn-committed entry or a recorded skip disposition (a targeted header-line edit on the group's origin rows). A unit is complete only from repository truth: its group's members are covered by an existing entry's `Origins:` lines, a plans-root plan, or a recorded skip disposition's header line on the origins; conversational memory is never the progress record. The next unit is the next uncovered group in the logs' urgency order; a resumed pass re-runs the census and continues at that group without redoing or dropping a unit, and a pass yields only at a real gate. The completeness check is a fresh census: report the pass complete only when it finds zero eligible groups lacking an entry, a covering plan, and a recorded skip disposition; the census reads the origins' own header lines, so the check needs no new surface. Origin repository or organization does not restrict investigation; keep foreign identifiers, personal data, and details outside this repository out of cluster annotations and emitted entries.

**Boundary:** investigate runs autonomously with no user interview and stops at the log entry. A plan-worthy entry routes to `docs/history/backlog/PLAN-PROMPTS.md`, whose plans Phase 1 owns user-facing requirements discovery and consumes the entry as design input; an ad-hoc-able entry routes to `docs/history/backlog/EXEC-PROMPTS.md` for an exec-mode session's ad-hoc run and never produces a plan file.

Run the four stages in order; the skill ends when Stage 4's write is committed.

### Stage 0: backlog-wide cluster survey (runs on every anchored invocation)

- Before the anchored pass, sweep every open top-level backlog item in the resolved `backlog_dir` and group items sharing a mechanism, surface, or defect class (the Stage 1 grouping criteria). Skip an origin only when it is already represented by an existing entry's `Origins:` line in either rolling log (`docs/history/backlog/PLAN-PROMPTS.md` or `docs/history/backlog/EXEC-PROMPTS.md`; the EXEC log is never swept as an ungrouped item either) or a plans-root plan file; origin repository and organization do not affect eligibility. Keep cluster annotations within this repository's safe, repo-relative vocabulary and omit foreign identifiers or personal data.
- For each computed roster of two or more, write one additive `Cluster:` line per sibling into each member's header region (repo-relative paths, the member itself excluded). Idempotent: an unchanged roster never rewrites, and an item with no cluster is never touched. The sweep emits no log entries and changes no status: the roster lines are advisory input for Stage 1, never dispositions.

### Stage 1: group discovery

- Read the input item's `Cluster:` lines (the Stage 0 sweep's rosters) as discovered-sibling input before the similarity search.
- Check the open backlog (the resolved `backlog_dir`) for items similar to or grouped with the input: shared mechanism, shared surfaces, or the same defect class.
- Apply the same eligibility check to the anchored search: origin repository and organization do not exclude the input item or a relevant sibling. Do not group items merely because they share an organization or consumer repository; group only by shared mechanism, surface, or defect class, and redact foreign identifiers and personal data from the roster and emitted entry.
- When a group exists, investigate the group as one unit and record the roster (each member's repo-relative path) in the log entry, so a parallel session (an ownership survey, a parallel triage) sees the grouping instead of rejecting grouped origins as unrelated (the witnessed 2026-09-27 mass-rejection cause).
- When no siblings exist, proceed with single-origin scope and record the roster as the one origin.

### Stage 2: issue archaeology

- For each guard, contract, or mechanism the item touches, establish when and why it was introduced before judging it: history search such as `git log -S` over the mechanism's distinctive spans, the motivating plan or incident that introduced it, and its current dependents.
- Read the motivating record itself rather than inferring intent from the current text alone; a decision whose framing inverts its own original fix is the failure this stage prevents.
- Judge the mechanism only after its introduction story is established.

### Stage 3: possibility space

- Enumerate the alternative resolutions before recommending one, including two standing axes:
  - the remove-or-keep axis: remove, keep, keep and narrow, or keep and widen the mechanism;
  - the missing-complement axis: a correct mechanism with a missing complement is completed, not removed (witnessed case: a seed gate whose recovery path was missing; the correct scope was both arms, not removal and not the one-arm fix).
- Continuity lens: when the investigated evidence shows a blocker (a refusal, gate, or recovery path) interrupting otherwise authorized work, name that signal in the possibility space and price removing, narrowing, replacing, or simplifying the blocker through the remove-or-keep and cost-pricing duties above, preserving protections tied to witnessed harms; a blocker with demonstrated independent protective value (a witnessed incident, a red test, or an explicit user decision) stays, with its value and any viable narrower recovery path stated; an investigation whose evidence shows no relevant blocker signal manufactures none and adds no analysis step; the continuity disposition rides the existing recommendation and rejected-alternative dispositions and adds no entry field, gate, validator, ledger, review round, or mandatory user question.
- Every rejected-alternative disposition cites its evidence basis: a disk witness (a repo-relative path), a landed mechanism (a file or section that exists), a commit, or a witnessed incident - never a bare assertion.
- The enumeration includes at least one alternative from outside the recommended mechanism's family (a pins-suite change versus a skill-text change are different families); the two standing axes are the minimum, not the whole space.
- Price the witnessed cost from records before pricing the urgency: an entry whose recommended fix formalizes a duty an existing mechanism already performs, or builds a surface ahead of any current consumer, is itself a rejected shape, and the smallest arm that removes the witnessed cost outranks the architectural one (witnessed correction: a two-task posture-machinery entry retracted when the operator's economics challenge showed the cost was per-run narration an existing note already covered, not per-claim rediscovery).
- Admission step: a recommended resolution that adds a gate, validator, lock, ledger, or required ceremony carries the machinery admission test in the entry: the concrete incident it prevents (with a link), the expected catch frequency, the false-positive cost, and a sunset or review date; or routes that arm as rejected with the missing-incident absence named in checker-passing form ("no witnessed incident", which carries the evidence-basis marker the entry checker requires; the protocol's durable home is the repository guidelines' Machinery admission protocol section); removal-shaped recommendations need no admission wording.
- An entry whose alternatives were contested on evidence (an operator or peer correction, recorded in the entry or its origin, arguing against a disposition with evidence) carries no `Standing pre-authorization` line, or scopes it to the non-contested arms, so a contested recommendation gets a genuine authoring-side look.
- The recommendation must name what was rejected and why; these one-line dispositions carry into the log entry.

### Stage 4: log entry emission

- Work-type verdict (added 2026-10-06, the two-mode loop policy plan; this step routes the entry): classify the investigated item per the eligibility test referenced by name from the maintenance skill's Ad-hoc backlog arm bullet (`agents/skills/maintenance/SKILL.md`): the item passing that test is ad-hoc-able and its entry routes to `docs/history/backlog/EXEC-PROMPTS.md`; otherwise it is plan-worthy and its entry routes to `docs/history/backlog/PLAN-PROMPTS.md`. The verdict runs per origin item against the eligibility test; composition per the plan's Terms Composition rule: a group whose members classify uniformly routes as one entry by that verdict, and a mixed group splits so each entry routes by its members' shared verdict.
- The entry passes `python3 scripts/check_investigate_entries.py --log <destination log>` (the structural minimum the script owns: non-empty rejected alternatives, evidence-cited dispositions), the `--log` naming the log the work-type verdict routed the entry to (`docs/history/backlog/PLAN-PROMPTS.md` or `docs/history/backlog/EXEC-PROMPTS.md`; or run once per destination log when a pass writes both) before the write is committed; the script's module docstring owns the marker semantics (the file-precision marker floor included), and the phrasing here is only the summary.
- Write one entry into the destination rolling prompt log routed by the work-type verdict (`docs/history/backlog/PLAN-PROMPTS.md` for plan-worthy, `docs/history/backlog/EXEC-PROMPTS.md` for ad-hoc-able) at the urgency position the entry merits (the log is ordered most urgent first; the position is judged when the entry is written).
- The entry carries: origins (repo-relative backlog paths, including the Stage 1 roster when a group was investigated), scope arms, orientation, the full ready-to-dispatch prompt payload, and one-line dispositions for each rejected alternative (Stage 3).
- An entry whose recommendation adds machinery carries the admission line: the four admission fields of the guidelines' Machinery admission protocol section, or the explicit rejection of the machinery arm with the missing-incident absence named. An entry omitting both is not a valid emission. An open item whose survey record carries skip reason `machinery-quarantine` is not eligible for entry emission: the work-type verdict records the quarantine skip instead of routing the item to either log.
- The entry is the artifact: no side record under the gitignored scratch directory (`docs/tmp/`).
- The write follows the log's standing rules: a targeted section edit (the entry's own section) prepared from a fresh read; re-read and compare before every write, and any difference is drift: retry once from the fresh read, then attempt a pure append of the entry at the end of the file; only when that append also fails the drift check, abort and report the full intended entry text in the turn output as the fallback record; the entry carries repo-relative paths only and no personal, machine-specific, or foreign-project data (no ticket prefixes, organization, service, or module names, and no internal document titles of a repository this one does not own); before the commit, the same-turn entry commit runs the same mechanical own-edit check the learn Step 1.8 commit rule prescribes (word-diff each staged non-backlog path against HEAD; a pure-deletion hunk, a pure-addition hunk the session did not write, or a path whose last landing date is newer than the session's read of it is foreign: skip the path and report it; lesson 134); the write is committed in the same turn that performs it, printing the `committed: <sha> <subject>` receipt line for the entry commit (the receipt the consuming spans record: the boundary's `task_boundary:` manifest row and its mirrors in agent-logs, review-loop, done, and learn).
- Record re-derivation before the entry write (added 2026-10-03; origin `docs/history/backlog/2026-10-02-stale-read-record-derivation-fence.md`; witness: the 2026-10-02 ~17:17 stale-false reads that recorded a wrong conclusion into durable records): the emitted entry is a **record-bearing claim**, a fact statement about repository state written into a durable channel (a user-facing report, a memory file, a backlog row, a commit message, a session note) whose wrongness outlives the session, so every repository-state fact the entry asserts gets **two-command disk re-derivation**: immediately before a record write, re-derive the claimed fact with two independent commands: an existence claim via a filesystem probe (`ls`/`stat`) plus a git probe (`git cat-file -e <tip>:<path>` or `git show <tip>:<path>`); an absence claim via a working-tree `grep` plus `git grep` at the tip commit. A cross-check mismatch stops the record write until resolved.

## Hard gates

- Never execute or dispatch anything: the skill ends at the log entry in the log the work-type verdict routed it to; the prompt payload is work for a later turn (an authoring turn for a plan-worthy entry, an exec-mode ad-hoc run for an ad-hoc-able entry), never for the turn that writes it.
- Never cite either rolling log as a plan's Backlog origin: neither log is a backlog item; a plan produced from a log entry cites it as design input in prose.
- Keep every path repo-relative: no absolute or machine-specific paths in the skill's edits or emitted entry.

## Integration Points

### With `maintenance` skill
Consumer. The maintenance scheduler turn's monitor step invokes this skill, at most one investigation per turn, on the highest-priority remaining ungrouped open backlog item when neither rolling log has a ready entry (it first skips any ungrouped item whose origins intersect an existing entry's `Origins:` line in either log or a plans-root plan file, recording the skip reason), and it reads the emitted entries for its read, prune, freeze, and dispatch duties in both logs. The verdict routing closes the loop from the maintenance side: the monitor's investigate leg appends each entry to the log the work-type verdict routed it to, the EXEC-PROMPTS.md destination feeding the maintenance skill's Exec-mode selection rule candidate set for exec-mode sessions, and the monitor's ad-hoc completion duty freezes and prunes superseded PLAN-PROMPTS.md entries around an ad-hoc landing. The maintenance loop's per-cycle harvest duty (maintenance SKILL.md Step 3) is the second consumer form: it runs one investigate pass per completed cycle under a live standing directive, taking the highest-priority ungrouped open item among the findings the cycle witnessed (the same selection rule this entry prescribes), while the scheduler turn's monitor step remains the first form. A corpus pass continues under the standing directive that opened it, each turn taking the next uncovered unit while its window allows; the monitor's investigate leg stays scoped to its own ready-entry trigger, not the pass continuation. The anchored invocation opens with the Stage 0 survey sweep, whose `Cluster:` annotation writes the scheduler turn commits and reads around exactly as before.

### With `learn` skill
Consumer. learn's Step 1.9 (project issue backlog capture) invokes this skill anchored on the backlog rows it created or updated, within the same learn run; investigate's stages, verdict routing, boundary, and hard gates apply unchanged, and its same-turn entry commit lands where the anchored rows live (the boundary's checkout for in-tree rows, the destination checkout for off-tree rows; inside a run worktree it lands with the run's squash landing).

### With `plans` skill
Downstream consumer of the emitted prompt: a later plans session authors from the log entry as design input, per the Boundary line above; the routing bounds this section, because only a plan-worthy entry (routed to `docs/history/backlog/PLAN-PROMPTS.md`) is a plans session's design input, while an ad-hoc-able entry routes to `docs/history/backlog/EXEC-PROMPTS.md` and is consumed by an exec-mode session's ad-hoc run, never by plans. Investigate never authors the plan file itself.
