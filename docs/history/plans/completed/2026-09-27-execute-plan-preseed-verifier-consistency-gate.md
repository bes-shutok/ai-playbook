## Outcome

Before a run seeds its machine manifest, each task's evidence contract is checked so that no task verifier requires an artifact a later task has not produced and no task merely repeats the global validation gate; and a run already held by a malformed evidence contract has a driver-mediated, receipted exit that does not require editing the machine manifest by hand.

- A malformed task evidence contract is refused at manifest seeding, before any worker launch, instead of blocking an already-successful worker result mid-run.
- A run held by the read-only malformed-result refusal can exit through the driver: the operator supplies a corrected contract, the driver validates it, the manifest generation is bumped, a fenced receipt records the recovery, and the task re-enters the normal claim queue with a fresh identity.
- The plan's global Validation Commands block remains the final whole-plan gate and is documented as never cloned into per-task verifiers; manual manifest edits stay prohibited.
- A two-task regression fixture pins both malformed shapes (later-task artifact dependency, global-checklist clone) plus the accepted targeted shape, and the full driver suite stays green.

## Terms

- **Machine manifest**: `runtime_state.json`, the authoritative driver-owned run state seeded by the `create` operation from the plan task list.
- **Verification evidence envelope**: the per-task immutable contract (`required_criteria`, `verification_commands`) and the receipts the driver captures against it.
- **Task-to-evidence mapping**: the derivation of each task's criteria and commands from that task's own acceptance criteria and Files list, runnable at that task boundary.
- **Pre-seed consistency gate**: the seeding-time refusal of the two malformed evidence-contract shapes this plan adds.
- **Launched hold**: the held state after the driver refuses a worker result read-only as `malformed-result` over unsatisfiable criteria: the refusal persists nothing, so the claim stays `state: launched` and the task stays `status: launched` with no durable trace of the refusal, and the claim keeps its durable adapter launch reservation; the run cannot proceed (the result was refused) and the existing exits do not serve the hold (reclaim refuses it over the live launch reservation, and a relaunch either is refused over the live claim or proceeds under the live token only to re-fail against the unchanged immutable contract; neither path replaces the contract), so the hold recurs. The recovery operation identifies this hold by its live shape plus an empty-worker inventory, not by a stored receipt.

## Assumptions

- assume the pre-seed gate lives in `create_manifest` (the shared seeding routine behind the CLI `create` operation and `--selftest`); basis: the execute-plan skill names `--operation create` the only documented path that translates plan checkboxes into machine manifest state, and manifest creation precedes any claim, so a create-time refusal satisfies "stop before any worker launch" by construction.
- assume detection is mechanical over the create payload only: the helper runs after the existing allowed-path canonicalization, compares each canonicalized argv token against canonical `allowed_paths` entries by exact equality, and treats identical whole `verification_commands` lists (deep equality, not argv-only equality) as the clone signature; basis: the manifest is immutable after seeding and the plan document's global block is never passed to the driver, so richer semantic matching is not mechanically supportable at this boundary.
- assume a verifier referencing an artifact declared in a same-or-earlier task's `allowed_paths` is legitimate; basis: the durable task state machine runs tasks in document ordinal order, so same-or-earlier tasks' artifacts exist at that task boundary.
- assume existing create-operation fixtures survive the gate; basis: verified at authoring time, the CLI fixtures derive distinct per-task verification fields via the test helper (distinct embedded criteria, so whole-list equality never fires) and the library fixtures declare no verification commands, which the gate skips, and no existing fixture declares an argv token equal to another task's allowed path.
- assume the hold is identified by its live shape (task `status: launched`, claim `state: launched` with its launch record) plus a fresh no-live-worker inventory, not by a stored refusal receipt; basis: verified at authoring time, the driver's `malformed-result` refusal is read-only (the checkpoint path returns before any claim lookup, latch, history append, or checkpoint write, and the launch and resume paths return without persisting), and the backlog origin records the run "held at a launched claim" with "the driver refuses the malformed result read-only"; durable refusal detection would require widening the frozen refusal sites, which this plan declines.
- assume the inventory precondition is evaluated on the reconcile-interruption discipline: a detached manifest view that omits the held claim's own durable launch reservation (or an equivalent adapter-inventory witness that does not route through the capacity reconciler's any-reservation-unavailable rule); basis: a launched claim durably holds a capacity launch reservation from launch time and the read-only refusal never releases it, so the reconciler's any-reservation rule would make the precondition unsatisfiable on exactly the state the operation targets, while reconcile-interruption evaluates its inventory on a reservation-stripped detached view.
- assume the recovery transition releases the held claim's durable launch reservation (keyed by task id, old token, and old generation) and adopts the reconciled worker and capacity state (retiring terminal worker rows and their capacity entries per the reclaim rotation), so the recovered task is actually claimable again; basis: without the release, the recovered task's next launch hits the capacity reconciler's durable-reservation refusal and the run exits the hold into a launch-reservation wedge.
- assume the recovery operation's old claim is closed as `closed` (claim state `closed`), not `replaced`; basis: the done-pending requeue precedent sets claim state `closed`, and after recovery a late receipt from the replaced worker fences read-only with no durable mutation as `stale-claim` ("claim already progressed past this receipt") for success and non-success receipts alike: a late success receipt is intercepted inside result validation (the launched-state owner check fires before any commit path, because the recovered task always carries non-empty required criteria) and the resulting blocked outcome routes through the progression guard, which classifies the closed claim as progressed; the success-commit fence's `owner-mismatch` is not reachable for any task carrying non-empty criteria, so it is never the pinned outcome; a `replaced` close would instead let a late success receipt pass the identity fence and re-block the freshly pending task through the latch tail.
- assume the replay fence is evaluated FIRST in the recovery precondition order (the manifest history is checked for an `evidence-contract-recovery` receipt naming the request's task id, token, and generation before the hold check), so a replayed request is refused with the recorded receipt named; basis: recovery bumps the generation and closes the claim, so under a hold-first order a replay would always fail the hold or identity precondition and could never name the recorded receipt; the fence-first order keeps the recorded receipt as the durable replay record.
- assume the recovery operation refuses a held claim owned by a live claim group (any group kind, mirroring the live-group ownership fence both the done-pending recovery and reclaim carry); basis: recovering a member of an active batch or parallel group would fight the group protocol, and both cited precedents refuse group-owned claims for exactly that reason.
- assume the recovery operation shares the evidence-envelope code with seeding (the same consistency helper, the same fail-closed path policy for canonicalization) and additionally enforces the per-task non-empty criteria-and-commands envelope rule the create operation enforces; basis: the revised task directive pins "same evidence-envelope code" for both arms, and an incomplete corrected contract would re-hold at the next success. The inventory witness itself is obtained through the driver's adapter, never from request payload fields.
Decision points requiring a grill: recovery-operation shape: driver-mediated CLI operation `recover-evidence-contract` that bumps the manifest generation and writes a fenced receipt; source: user revised task directive 2026-09-27 (this authoring session), affects Task 2 and runtime-contract.md; fail-closed-as-decision-point: every refusal path (not the launched hold, identity mismatch, corrected payload failing the gate or the envelope rule, missing inventory, replayed request) leaves the manifest byte-unchanged and returns evidence, never a deadlock; source: user revised task directive 2026-09-27, affects Task 2; manual-edit prohibition: the operation is the only sanctioned writer for this transition and no manual manifest edit path is added; source: user revised task directive 2026-09-27, affects Task 2; corrected-payload gate: the recovery payload must pass the same pre-seed consistency gate as create before any transition; source: user revised task directive 2026-09-27 (same evidence-envelope code), affects Tasks 1 and 2.

## Gist & Examples

TLDR: Execute-plan manifest seeding gains a consistency gate that refuses global-checklist clones and later-task artifact dependencies before any worker launches, and a receipted recovery operation lets a run held by the read-only malformed-result refusal exit without manual manifest edits, so the witnessed consumer-run block and its hold cannot recur; the plan answers the external consumer-feedback force.

Arm 1, what changes at seeding: `create_manifest` (the one seeding routine behind `--operation create`) validates the task-to-evidence mapping before writing the manifest. Two shapes are refused with an actionable error naming the task and the offending entry:

1. A task's verification command `argv` token names, after canonicalization through the same fail-closed path policy, an `allowed_paths` entry that appears only in a strictly later task. The verifier would demand an artifact that does not exist at that task boundary, which is the exact shape that blocked the witnessed consumer run: Task 1's worker and its focused test succeeded, then the driver rejected the result because later-task artifacts were missing.
2. Two or more tasks declare identical whole `verification_commands` lists (deep equality). That is the signature of the plan's global Validation Commands block copied into every task instead of being kept as the final whole-plan gate.

Everything else is accepted, including verifiers that reference same-or-earlier tasks' artifacts (already produced by ordinal order), artifacts declared in several tasks' `allowed_paths`, and tasks whose commands share an identical `argv` while their embedded criteria differ (deep list equality, not argv equality, is the clone signature).

Arm 2, what changes for a held run: the driver's `malformed-result` refusal is read-only by design, so after the refusal the claim and task both stay launched (with the claim's durable launch reservation still held) and no durable trace of the refusal exists. Today no exit serves this hold: reclaim refuses it over the live launch reservation, a relaunch either is refused over the live claim or proceeds under the live token only to re-fail against the unchanged immutable contract, and manual manifest edits are prohibited. The new `recover-evidence-contract` operation is the sanctioned exit. It refuses (leaving the manifest byte-unchanged) unless every precondition holds, checked in order: the replay fence first (the manifest history must not already carry an `evidence-contract-recovery` receipt naming the request's task id, token, and generation), then the launched hold (task `status: launched`, claim `state: launched`), the exact claim token and generation, no live claim-group ownership, a corrected contract satisfying the per-task non-empty envelope rule and passing the same pre-seed consistency gate as create over the merged task map (refusing only on problem shapes that involve the corrected task; sibling-only shapes are reported without refusing, because multi-malformed old-seeded runs recover task by task as they hold), and a fresh provider inventory (evaluated on a reservation-stripped detached view, obtained through the adapter) proving no worker is live. When it accepts, it bumps the manifest generation, releases the held claim's durable launch reservation inline in the same locked save and adopts the reconciled worker and capacity state, replaces the held task's evidence fields with the corrected contract, recomputes the `evidence_contract_digest`, closes the old claim as `closed`, returns the task to `pending`, and appends a fenced `evidence-contract-recovery` history receipt. A replay of the same request is refused by the receipt fence, and a late receipt from the replaced worker fences read-only as `stale-claim` with no durable mutation, for success and non-success receipts alike.

Example regression fixture (the backlog's shape): task-1 with a targeted verifier over its own output, task-2 producing `report.txt`, and the global gate referencing `report.txt`. The correctly derived payload (task-1 verifier touches only task-1 outputs) seeds fine; the malformed payload (task-1 verifier also references `report.txt`) is refused at seeding with task-1 and task-2 named; and a run already seeded the malformed way and holding on the launched claim exits through `recover-evidence-contract` with the corrected targeted payload. The final global gate is untouched throughout because it is never seeded into tasks at all.

The skill and contract docs change alongside the code so the parent deriving the payload knows the rule before it reaches the driver and the operator of a held run knows the sanctioned exit: per-task criteria and commands come from that task's own acceptance criteria and Files list and must be runnable at that task boundary; the global Validation Commands block stays the whole-plan gate checked at the done boundary; and the recovery operation, not a manual manifest edit, owns the contract transition.
