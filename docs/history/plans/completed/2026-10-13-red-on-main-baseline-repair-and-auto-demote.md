## Terms

- Pin: a named assertion row in scripts/check_maintenance_pins.sh; the suite has five distinct failure-emission shapes: the `pin "<name>" <command>` helper, the `expect_absent` helper, the `expect_absent_flat` helper, count-gated literal forms that print their own `PIN FAIL:` lines, and python heredoc blocks invoked as `python3 - ... <<'EOF' || fail=1` that print their own `PIN FAIL:` lines.
- Stable pin name: the fixed descriptive string a row uses as its identity in failure output, recorded-red notes, and provenance comments; never a count-bearing or variable-interpolated echo (a count-gated row's rendered message embeds live counts, so it is not a name).
- Checkpoint: a mid-suite `[ "$fail" -eq 1 ]` exit site; the suite emits its single final `OUTCOME:` line and exits at the first checkpoint reached with fail=1.
- Dormant tail: every pin row after the last executed checkpoint in a given run; those rows never execute while an earlier checkpoint fires.
- Census probe: a scratch copy of the suite with every checkpoint line neutralized, run against the repo to enumerate the complete failure set in one pass.
- Recorded red: a standing pin failure entered as an override row under the `check_maintenance_pins` guard in scripts/gate_liveness_ledger.json, whose note carries the keys `pin: <stable pin name>` and `review-by: YYYY-MM-DD` plus a witness; recorded reds warn and never fail the suite while unexpired.
- Register: scripts/gate_liveness_ledger.json; the posture record of record.
- Occurrence scan: the per-literal adjudication input: a tree-wide fixed-string search over tracked files for the pinned literal, plus per-fragment probes for component-assembled spans, never a probe of the pinned target file alone.
- Superseding origin: the landed, certified plan whose prescribed text removal or rewording a pin row failed to reconcile (the reconcile rule the suite's own comments state: a wording change to a pinned span is a change to the owning plan's prescribed text).
- Arm set: the four per-row dispositions, in precedence order: remove-beside-provenance (a superseding origin removed or reworded the span; the row's comment names the superseding plan and landing), re-aim (the contract lives under new bytes or at a new home; the pin follows the carrier), restore (the contract is load-bearing and its text was lost unprescribed; the span returns to the owning surface), record-red (the red is real, load-bearing, and unresolved; Task 3's CLI enters it in the register). Precedence: record-red is chosen only when no other arm restores the baseline; a row never weakens its literal to pass.
- Negative-arm probe: a validation run against a deliberately broken span that must fail, proving the check under test can fail (a green result paired with no negative arm proves nothing).
- Bounded-repair menu: the repository rule that a blocked lane's allowed responses are a bounded retry, skip-with-report, or park-for-operator, never editing the gate mid-lane.
- Foldable result: a discrepancy between this plan's authoring-time evidence and the working tip at execution that the executor resolves inside the plan's protocol and records in the task log, never a plan defect or a scope change.
- Canonical covered form: the origin-row status form `covered (<repo-relative witness path>)` the landing lifecycle flips rows to.
- Provenance comment: the comment a repaired pin row carries naming its arm, superseding origin or live carrier, and date, so every reconciliation is auditable in-repo.

- assume the authoring census is evidence, not normative: peers land changes continuously, so execution re-derives both censuses with the same probe and adjudicates the then-current set with the same protocol; a row that vanished or appeared since authoring is a foldable result, not a plan defect; basis: the standing red baseline's own history of byte-identical sets across tips.

- assume the ledger's unstaged advisory rows present at execution start are the executing session's own closeout concern under its standing finalize pattern; this plan's ledger edits are limited to the consult contract's rows.
- reject a separate wrapper or driver design (an external reader that runs the suite, parses PIN FAIL output, and rewrites the exit code): rejected because in-suite suppression keeps the tail live past recorded reds at the emission site, keeps the outcome contract in one file, and avoids a second process per lane run; the in-suite conversion cost is bounded by the scripted codemod with before/after failure-set byte-equality verification (Task 3).
- reject extracting the consult reader into a separate helper script with a companion test suite: rejected because the suite's own convention for embeddable logic is the permanent in-suite selftest section (the live-vs-archive seam), which Task 3 adds; extraction becomes a foldable result only if the selftest cannot exercise the reader.
- reject weakening any pin literal so a failing pin passes while the contract it froze is still load-bearing at its original surface: the pins are the drift detector, not the drift's remedy (the baseline row's own rejection).
- reject recording all 37 rows as standing reds without repair: the audit's ordering is fix the reds first; the register arm exists for genuinely load-bearing unresolved reds, not for reconciliation debt (the primary origin row's expected section).
- reject a separate landing-queue precondition gate for machinery landings: every lane's existing exit-0 pins gate is that precondition, and the consult makes it honest (recorded reds stop blocking, unrecorded reds keep blocking); a second gate would duplicate the first for net machinery growth (the admission protocol's default to fewer blockers).
- reject restructuring the suite's mid-suite checkpoints: the placement guidance plus the green baseline are the dormancy mitigation, and a restructure churns every exit site for no witnessed catch (the dormant-tail row's own fix shape).
