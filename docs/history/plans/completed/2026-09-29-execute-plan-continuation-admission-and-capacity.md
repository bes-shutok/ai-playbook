# Plan: Execute-plan continuation admission and Codex capacity recovery

Backlog origin: docs/history/backlog/2026-09-29-execute-plan-legacy-preflight-and-codex-inventory-recovery.md
Driving force: automation; secondary code-quality
Plan review record: the staging series docs/reviews/2026-09-29-plan-review-execute-plan-continuation-admission-and-capacity-r*.md (the highest rN is the authoritative record, including any deferred-residual list)

## Outcome

Close the two launch-admission gaps that stranded the CRM-<ID> continuation: an older active run seeded without a runtime id can re-enter through one audited driver transition, and the recognized adapter's process inventory survives unmatched shell quotes in host process rows.

- A manifest recorded by an older driver without a `runtime` id is migrated through one driver-owned, locked `recover-run-identity` operation that validates the full binding (registered runtime id, repository root, receipt pairing when a receipt is supplied, claim and handoff state, generation), refuses first when a runtime is already bound, clears the witnessed poisoned intermediate claim when that is the only obstruction, and appends the recovery family's fenced history receipt as the audit record; after it succeeds, the ordinary read-only `preflight` emits the canonical continuation command, with no hand-edited manifest bytes and no hand-assembled command line.
- On a manifest recording no runtime id, every claim-arm success exit (single-task, batch, parallel-group) refuses with the migration remedy unless the invocation evidence tuple carries both a non-empty canonical runtime id and a receipt path; receipt-only or runtime-only evidence refuses, and the manifest's recorded receipt never substitutes for the receipt flag.
- The recognized adapter's process inventory identifies `exec` invocations through a quote-tolerant token scan, so one live worker's unmatched shell quotes in its prompt arguments no longer quarantine the host's capacity; prompt text is never parsed as shell. Prompt text containing an embedded newline still fail-closes the snapshot (documented limitation).
- Fail-closed behavior is preserved everywhere else: failed process snapshots, malformed identity fields, and ambiguous target identity still refuse, and a real unrelated live `exec` process still consumes the single capacity slot.

## Assumptions

- assume the migration operation is named `recover-run-identity`; basis: the driver's recovery-operation naming family (`recover-handoff`, `recover-done-pending`, `recover-evidence-contract`) and the origin's "one atomic legacy-run binding operation".
- assume the adapter fix is the quote-tolerant token scan, not a structured argv process interface; basis: the origin's Recommended line, and the host `/bin/ps` on Darwin offers no argv-boundary output mode, so a structured interface is not available on the witnessed platform. Prompt arguments containing an embedded newline split the rendered `ps` row and keep failing closed; this residual is documented in the contract update, not fixed here.
- assume the migration payload carries the target repository root and a task id bound to the derived next incomplete task, and the binding is audited through the recovery family's fenced history receipt (which also records any cleared poisoned claim); basis: the origin's acceptance "bind a verified runtime and repository identity through one audited, locked transition".
- assume the migration takes the approval receipt path in its payload when the host records one, and succeeds without it when the manifest legitimately records none; basis: the create boundary's `--approval-receipt` is already optional ("supplies ... when the host records one", execute-plan SKILL.md seeding paragraph).
Decision points requiring a grill: none remain.

## Terms

- Legacy manifest: a machine manifest (`runtime_state.json`) seeded by an older driver version, carrying no `runtime` id (and possibly no resolved approval receipt), whose tasks and generation are otherwise valid.
- Poisoned intermediate claim: the failed remedy attempt's residue on a legacy manifest: the next incomplete task in `claimed` status with a claim in the `claimed` state, no launch record, and no prepared handoff intent; readiness cannot prove it and a second claim is stale-claim-blocked.
- Prepared handoff intent: a claimed claim backed by a `prepared` handoff intent whose task, token, and generation exactly agree, the done-successor state preflight admits preflight-local.
- Canonical continuation command: the self-sufficient emitted command line built by the driver preflight from the recorded runtime id, resolved repository root, and recorded receipt; hand-assembled variants are prohibited.
- Claim-boundary remedy: the canonical remedy text the driver preflight names for a manifest recording no usable runtime id: re-create the run with `--runtime` at the create boundary, or run the `recover-run-identity` migration operation (which requires a driver whose `--operation` table registers it; update the deployed driver first). A claim boundary that is supplied `--runtime` together with `--approval-receipt` remains a valid remedy path; a bare `--runtime` at a claim boundary is refused by this plan.
- Binding history receipt: the recovery family's fenced history receipt the migration appends on success, recording the runtime id, the resolved repository root, the receipt identity, the payload task id, and any cleared poisoned claim (task id and token) or claim group (group id, released-member id list, generations); it is the migration's audit record. The migration's replay fence is the already-bound check of the manifest's `runtime` field, evaluated before any host-state precondition.
- Tolerant token scan: the adapter's quote-tolerant tokenization of a process row's command text, in which quote characters read as literal characters and prompt text is never parsed as shell; one shared locator finds the wrapper binary, the `exec` subcommand, and any accepted `resume` form for both the inventory parse and the conversation-id extraction.
- Capacity slot: the adapter's single-slot live-worker exclusion; one live recognized `exec` process blocks a second launch.

## Gist & Examples

TLDR: one audited driver migration plus quote-tolerant token scanning, so legacy runs re-enter the admitted continuation path and prompt quotes stop quarantining capacity; force: automation (the continuation loop runs without manual unblocking), secondary code-quality (inventory correctness).

Today, a manifest seeded by an older driver has no `runtime` id. The read-only preflight correctly emits no command for it (the canonical command must pin the recorded runtime id), and the documented remedies stop at the claim boundary: a plain `claim` stamps `manifest["runtime"]` but creates a claimed task with no activation receipt or prepared handoff intent, which the next preflight refuses as unprovable. The run is stranded: re-create loses the run, hand-editing the manifest is prohibited, and hand-assembling the continuation command is prohibited. Witness: the CRM-<ID> continuation, 2026-09-29. The witnessed manifest also already carries the failed remedy attempt's poisoned intermediate claim, so the migration must handle that shape, not only the pristine one.

The fix adds one driver operation, `recover-run-identity` (Task 1). Under the manifest lock, after payload-shape checks, it refuses first when the manifest already records a runtime (the replay fence), then validates everything preflight would need to prove: registered runtime id, repository root supplied in the payload and resolving equal to the driver's root, payload task id equal to the derived next incomplete task, generation match, token semantics per shape, and receipt loaded and fingerprinted with its recorded runtime pairing to the payload runtime id. When the only obstruction is the poisoned intermediate claim, the same locked transition closes that claim per the recovery family's precedent (claim state closed, task reset to pending, any matching claim group closed), recorded in the binding history receipt; a live launch reservation or a non-admitted handoff intent still refuses. The binding persists through the existing validate-before-persist recovery transition, and the history receipt is the audit record. Any refusal leaves the manifest byte-identical.

The claim boundary closes separately (Task 2): one shared refusal gates every claim-arm success exit, positioned before the handoff, pending-enumeration, stale-claim, and no-pending evaluations, firing exactly when the manifest records no runtime and the invocation evidence tuple does not carry both a non-empty canonical runtime id and a receipt path. Most of the suite's claim fixtures seed legacy-shaped manifests, so Task 2 owns the seeder-granular fixture sweep that keeps the full suite green.

The adapter's process inventory (Task 3) runs `shlex.split` over each row's full command text. One live worker's prompt containing an unmatched quote makes `shlex.split` raise, the whole snapshot is reported unavailable, and capacity is quarantined even though the row's pid and start time were readable. The fix parses the row's command text with a quote-tolerant token scan: quotes become literal characters, one shared locator finds the `exec` (and accepted `resume`) shape as today, and prompt text is never parsed as shell. Malformed pid or start-time fields, failed snapshots, and empty snapshots keep failing closed; a real unrelated live `exec` process still occupies the slot. A prompt argument containing an embedded newline splits the rendered row and keeps failing closed (documented limitation, witnessed residual recorded in the contract update).
