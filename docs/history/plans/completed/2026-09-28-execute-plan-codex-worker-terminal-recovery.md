# Plan: Execute-plan recovery terminal evidence for completed Codex workers

Backlog origin: none
Driving force: code-quality
Plan review record: the staging series docs/reviews/2026-09-28-plan-review-execute-plan-codex-worker-terminal-recovery-r*.md (the highest rN is the authoritative record, including any deferred-residual list)

## Outcome

Make evidence-contract recovery accept a Codex worker whose turn completed by consuming fresh, identity-matched, conversation-keyed terminal evidence from the adapter, instead of refusing every Codex launch hold with stale-inventory.

- Recovery of a launched hold whose Codex worker completed succeeds through the supported `recover-evidence-contract` operation: the old claim closes, the durable launch reservation releases, the generation rotates, and the task returns to pending.
- Fail-closed behavior is preserved: a live worker, a missing or mismatched worker identity, and stale evidence still refuse recovery, and every refusal leaves the manifest byte-unchanged.
- An old worker cannot submit a valid receipt for the new generation after recovery.
- Regression tests pin the completed / live / stale / mismatched evidence matrix and the exact recovery state transitions.
- The runtime copy the workflow actually invokes is verified on disk and the finding is recorded, confirming whether the fix reaches the executing code path or naming the deployment step Ship when carries.

## Terms

- **Worker registry** (`scripts/execute_plan_worker_registry.py`): the pure reducer for the manifest's `workers` and `capacity` sections; provider-neutral, no adapter or file knowledge.
- **Provider session id** (`provider_session_id`): the worker identity string the registry keys workers and lifecycle receipts on; for Codex this is the conversation id returned at launch.
- **Terminal evidence / terminal receipt**: a lifecycle receipt (`terminal`) with verified `provider-terminal` proof that a worker finished; the registry releases the worker's capacity entry only on an identity-matched, proven receipt.
- **Evidence-contract recovery**: the driver operation `recover_evidence_contract` (CLI `--operation recover-evidence-contract`), the single sanctioned exit from a launched hold with a malformed contract; precondition 6 requires a fresh accepting provider inventory.
- **Provider inventory**: the adapter's neutral process-table observation (`observe_inventory`), consumed by `reconcile_worker_capacity` and reduced by the registry's `reconcile`.

## Gist & Examples

TLDR: The Codex adapter reports identity-matched, conversation-keyed terminal evidence for completed workers so evidence-contract recovery accepts a completed turn instead of refusing with stale-inventory, restoring correct recovery (code-quality).

Today two identity planes are disjoint. The registry registers a worker under the Codex conversation id the launch receipt returns (`register_launch` stores it as `provider_session_id`), while the adapter's `observe_inventory` snapshots the OS process table and synthesizes session ids of the form `codex-process-<pid>-<hash>`. The registry's `reconcile` joins inventory to workers by `provider_session_id` string equality, so a Codex worker is never observed: probed 2026-09-28 against `WorkerRegistry`, a worker registered under conversation id `conv-abc-123` with its process alive still reconciles to `{'status': 'quarantined', 'reason': 'stale-inventory', 'recovery_action': 'reconcile-provider-inventory'}`, and with the process exited the same refusal fires. Recovery precondition 6 then refuses: "provider inventory did not accept: stale-inventory". That is the CRM-<ID> Task 1 witness.

After the change: when a registered worker's process is absent from the inventory, the driver consults the adapter's terminal-evidence port for that worker's conversation. A conversation record proving the turn completed yields a fresh, verified, identity-matched terminal observation; the registry releases the worker, reconcile returns available, and recovery proceeds through its existing locked transition. Two production facts re-anchor the live row: the Codex launch is synchronous, so the launched hold's process has already exited by the time the launch receipt returns and the persisted worker identity is provider-session shaped (not pid plus start time), and a live process exists only from a concurrent `codex exec resume` of the same conversation; Task 0 decides the mechanism that joins such a process to its registered worker (the conversation id extracted from the resume argv, with the joined row reshaped to the worker's persisted identity), and a process that cannot be joined stays fail-closed quarantined exactly as today. Recovery carries its own guard on top: it refuses while the held claim's registered worker is not terminal, regardless of the inventory verdict. Process absence alone proves nothing: without provider-record evidence of completion the worker quarantines exactly as today, as does evidence whose read is stale or whose record is keyed to a different conversation.
