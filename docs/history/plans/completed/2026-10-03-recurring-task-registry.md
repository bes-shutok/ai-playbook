## Terms

- **Recurring-task registry**: the set of top-level `.md` task files under the resolved `recurring_tasks_dir` facts key (README files excluded), plus the per-task state records and the Step 1 registry consult that surveys, dispatches, and watersmarks them. The key has no fallback: when it is absent the consult is inert.
- **Task file**: one markdown file per recurring task, filename stem equal to its `id`. It opens with a TOML block in a fenced `toml` code block carrying `id` (kebab-case, equal to the filename stem), `cadence_days` (positive integer), an optional `kind` in the closed set `audit` or `rider` (default `audit`), and an optional repo-relative `state_file` override (resolving under the maintenance state directories); the file body below the block is the pluggable prompt: a self-contained instruction block a fresh session runs verbatim, ending with a `State advance` paragraph that advances the task's own state record and commits the tracked artifacts the run produced; tracked-artifact commits acquire the merge landing lock with a bounded wait (defer with the reason recorded on timeout), re-verify the checkout holds the default branch at commit time, and run the check-writes and em-dash gates over the changed paths before committing; the State advance orders commit before stamp, the completion stamp landing only after the tracked-artifact commit survives, a bounded-wait lock timeout deferring the stamp (the consult's one-day backoff semantics apply) and never leaving a completed record over uncommitted artifacts; on a commit-timeout the run also records the pending artifact paths in `last_result`, and the next run commits or discards them before re-executing; and the generic discipline is a no-op for a task body whose own absorbed mechanics already hold the lock (the deferred-retriage sweep's verbatim lock hold).
- **Per-task state record**: the JSON file backing one task, `<state_file>` or default `<maintenance_state_dir>/<id>.json`, schema version 1, fields `id`, `cadence_days`, `last_run_at` (null until the first completed run), `next_due`, `consecutive_failures`, `last_result`; a task may carry additive fields beside them (the audit and re-triage records keep their existing richer fields; the skill-review record carries its rotation cursor). A missing record is a cold start and reads due.
- **Overdue**: a task whose state record's `next_due` has passed at survey time, or whose state record is missing (cold start).
- **Audit-kind task / rider-kind task**: an audit-kind task runs as a dispatched child (the audit child path: an automation or in-session carrier per the dispatch discipline, occupying the authoring lane `G1a`); a rider-kind task runs in-turn in the scheduler turn's own Step 7 slot and never creates an automation.
- **Proof window**: the recorded condition under which the pre-registry pointer stubs, the overlay audit recipe section, and the legacy marker clauses delete in a later change set: every migrated entry's state record shows at least one registry-driven completion (`next_due` advanced once under registry dispatch). This plan lands the registry and the migration; the deletion pass is out of scope.

## Gist & Examples

TLDR: recurring maintenance work becomes per-project registry entries the loop itself surveys, dispatches, and watersmarks, so a consumer project registers its own tasks and this repository's three hardcoded lanes stop being machinery nobody else can use, per the new-capability and automation forces.

Before (today): a consumer project that wants a weekly model-freshness check builds the ad-hoc pattern homelab-llm landed (a self-contained task file with TOML timestamps plus a standalone weekly automation that no-ops until due): the trigger lives outside the maintenance loop, so it gets none of the loop's guards (failure cap, lane occupancy, quota-aware fire times), and the loop's own three recurring lanes (friction-audit, deferred re-triage, the weekly measurement rider) are hardcoded paragraphs naming this repository's scripts, report homes, and state files, meaningless when a consumer runs the skill. Nothing audits the `agents/skills/` corpus for decay: overcomplication, repetition, and internal controversy are found only when a human rereads a file.

After (this plan): the same consumer project sets `recurring_tasks_dir = "docs/maintenance/recurring-tasks/"` in its facts document, drops its model-freshness task file there (id `model-freshness-check`, `cadence_days = 7`, body the self-contained prompt it already wrote), deletes the standalone automation, and the next scheduler turn's registry consult reads the task's state record, finds `next_due` passed, and dispatches the body as an audit child with the loop's guards, caps, and watermark rules applied uniformly. In this repository the friction-audit, deferred re-triage, and weekly measurement rider lanes run as the registry's first three entries (their run procedures absorbed verbatim into their task files), and the weekly skill-review pass runs as the fourth: each run reviews the next rotation batch of skills for the three defect classes, appends an aggregates-only record, files one backlog origin per actionable finding, and advances its own watermark.

Example state flow for a registered task: the record starts absent (cold start, reads due); the first run completes and stamps `next_due = completion + cadence_days`, `last_run_at = completion`, `last_result` one line, `consecutive_failures = 0`; a run that dies mid-way records `last_result` with the failure reason, advances `next_due` by one day so a failing task cannot re-dispatch every turn, and increments `consecutive_failures`; six consecutive failures defer the task with `turn_error: registry-task-consecutive-failures` until a human resets the record; a corrupted record defers the task with a one-day backoff and `turn_error: registry-task-state-corrupt` until a human deletes the record (the sanctioned cold-start re-arm).
