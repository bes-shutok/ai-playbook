## Terms

- stack run: an execute-plan-stack run: serial task branches, one draft PR per task, ending at the verified draft-PR stack.
- stack-task mode: execute-plan's `--stack-task <plan> --task <N>` mode: one task's worker, intermediate review, validation, and commit, without the ordinary run's Phase 2/3/4/5 (which is why stack runs need the stack-final fresh review).
- Step 1.2b intermediate review: the per-task review between implementation exit and the boundary commit; workers return findings, the parent owns records, fixes, and backlog capture.
- pass verdict: the union of the review tier's worker verdicts: `clean`, `blocking`, or `backlogged-candidates`.
- `inter_review` line: the per-task manifest line Step 1.2b appends recording tier, workers, rounds, verdict, and backlog paths, and the worker's `unverified-runtime:` list when present.
- pass record: the Step 1.2b record appended to `task-<N>-review.log.md`.
- boundary commit: the Step 1.4 commit a task boundary produces.
- Hard Gate 25: the execute-plan rule blocking the boundary commit until the `inter_review` line records `clean` or `backlogged-candidates` with every recorded backlog path captured.
- off-plan finding: a valid finding not causally related to the plan; backlogged, never fixed in-task.
- in-diff carve-out: the bounded exit this plan adds to the off-plan rule: a non-blocking finding about text or code the task's own diff adds or changes, fixable in-task under a cumulative changed-line cap with no new surface.

- pivot: an operator-directed change made in chat after a task's review, before the stack publishes.
- claims census: the documentation-lens pattern: for each behavioral claim the change set adds or changes, name the code path and the test that witness it, and flag enumerations narrower or wider than the code's partitions.

## Why

A stack run defers valid findings and accepts pivots after the task-time reviews, and no full-diff review runs before the run releases the stack to the operator's PR lifecycle, so valid defects surface only on external review rounds that cost push-reply cycles and approval turns. A static-only round still records an ordinary pass verdict, so runtime claims nothing exercised ship silently. receiving-review fixes the first instance of a text finding class and leaves no record of its lessons search, so sibling instances surface one review round at a time.

## Gist & Examples

TLDR: task-time reviews keep small in-diff findings, record what static-only rounds could not run, lens patterns trace claims to code, and every stack publication passes a fresh full-diff review before its claim release, for reliability.

Before: a tier-H review backlogs a 25-line throttling-wording fix scoped to the task's own adapter; the stack publishes; the external reviewer re-raises the same wording, and five push-reply rounds follow. After: the same finding is fixed in-task under the carve-out cap, and only findings outside the diff, or in-diff findings beyond the cap, stay backlogged.

Before: a degraded host forces a static-only tier-H review; the verdict reads `backlogged-candidates` with no record of what could not run; a live reproduction later shows an undecodable success body returned 500. After: the worker returns `unverified-runtime:` naming each runtime-dependent claim, the pass record and `inter_review` line carry it, and at the stack-final fresh review the run parent runs or explicitly accepts each.

Before: a documentation table says an unknown status can fail list and detail while the adapter also rejects it on write; the pass verdict is `clean`. After: the documentation lens's claims census traces each behavioral claim to a code path and a test and flags the enumeration narrower than the code's partitions.

## Outcome
