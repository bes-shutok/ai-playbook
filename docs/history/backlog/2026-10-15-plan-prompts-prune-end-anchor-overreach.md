## Problem

The post-landing-reconciliation-enforcement landing (4818cc829, 2026-10-14) pruned its own dispatch entry with a section-removal step whose end anchor was `t.index('## codex-task-resource-cleanup-evidence-recovery')`, assuming the pruned entry was immediately followed by the codex entry. The log's actual order held nine more entries between the two headings, and the removal erased all of them: done-run-declared-deletion-path, execute-plan-closeout-cycle-and-filed-records, finite-string-state-values-need-enum-review-guidance, post-implementation-review-invariant-coverage, closeout-gate-review-series-expansion, framework-callback-readability-and-review-scope, configurable-artifact-paths-in-docs, execute-plan-sequential-trace-harness, and skill-monolith-module-extraction. Nine ready or frozen dispatch entries left the tracked log in a certified landing, and only the accidental later restoration (the stale-primary reversal of witness 7 in docs/history/plans/completed/2026-10-14-post-landing-reconciliation-enforcement.md, which committed the pre-landing bytes back) returned them to main.

## Why the prune audit did not catch it

`python3 scripts/check_prompt_log_origins.py --prune-audit --base 163ce04aa` ran before the rider commit and answered `OUTCOME: pass` with `0 removals across 0 log-touching commit(s)` while the working tree carried a PLAN-PROMPTS.md diff of roughly 216 deleted lines. The audit's log-touching-commit detection does not see the uncommitted worktree state the landing is about to commit, so a removal performed in the working tree before the rider commit is invisible to it; the audit's plan-file-witness rule never fires for entries removed without their witnesses.

Establish coverage per origin from the existing selector's witness, then remove only covered origins and their explicitly paired scope arms. An ordinary PLAN-PROMPTS monitor origin is covered only by a plan in the plans root or completed twin whose `Backlog origin:` header exactly equals that origin path; finding a plan by entry slug alone never covers the entry's unrelated origins. Keep PLAN-PROMPTS as the canonical home for shared prune and freeze behavior; EXEC-PROMPTS and operative procedures point to it and state only their log- or operation-specific deltas. For a partial entry, narrow the prompt and scope arms to unresolved origins; clear `Frozen:` only after landing and when the existing claim/worktree check finds no live claim or worktree for a retained origin. If origin-to-scope pairing is ambiguous, leave that entry unchanged and report the ambiguity. Preserve receipts and add a log-specific prune receipt only for a full-entry removal; monitor writes stay targeted and the separate audit remains report-only.

## No-exit analysis for target identity (2026-10-20, plan review r9)

The procedural fix also requires a no-edit refusal when authorization evidence does not identify one exact heading. This is necessary to keep the existing ownership classes safe while inventorying ranges:

- **Add a sanctioned exit:** none preserves the standing landing contract. A landing must remove only its own associated dispatch entry, and the collateral class must come from the existing discovery predicate; treating ambiguity as permission to skip can leave a completed prompt dispatchable, while deleting every same-slug heading can erase a different entry. Monitor/ad-hoc completion likewise prunes only an eligible target after its existing freeze and landing-witness steps. The no-edit result is therefore a refusal of that target, not successful completion of its required prune.
- **Remove a false positive:** the refusal is limited to cases where existing evidence cannot bind the selected slug to one exact heading, or where the target fails the existing eligibility predicate. The read-only collateral discovery supplies slug and origins, not a stable heading-occurrence identity, and the parser permits duplicate headings; the monitor's ad-hoc predicate requires a matching `Origins:` item plus a pre-landing freeze and recorded landing commit. Removing these checks would admit an unrelated or ambiguous section, not a false positive.
- **Simplify the flow:** full-range inventory and receipt preservation cannot decide which duplicate heading is authorized. Choosing the first/last occurrence, deleting all occurrences, or selecting by slug alone is simpler but can delete a neighboring valid entry; adding persistent occurrence IDs or a new selector schema would be new state/machinery. Resolve with the existing provenance and witness evidence, and refuse without edits when that evidence still cannot identify one exact target.

This analysis prices only the narrow target-identity refusal in the procedural arm; it adds no checker stop, persistent state, or lock. The separate pending-audit arm remains warning-only.
