# docs-branch sync leaves stale top-level backlog duplicates when an item is later archived on main

Evidence: 2026-09-19 manual cleanup (docs branch commit 190bd501) removed 202 top-level `docs/history/backlog/*.md` files that also existed under the docs branch's own `completed/`/`deferred/` directories. Root cause: the `done` skill's docs-branch sync adds and updates branch copies of `{backlog_dir}` files but never removes a top-level copy whose name reappears under `completed/`/`deferred/` (its deletion propagation only sweeps `{tmp_dir}`, the one sweep-eligible root). When a backlog item is archived on main — moved to `completed/` (usually with a status/closure update) or `deferred/` — the sync's add/update logic can leave the earlier open-state top-level copy in place, so the branch accumulates open-status duplicates next to their canonical archived versions. 181 of the 202 removed copies had drifted from their archived twins (e.g. `2026-08-28-fence-scanner-family.md` still said `Status: open` while the archived copy recorded the 2026-08-29 closure). All archived copies were byte-identical to main's, so the archive was canonical and nothing was lost — but the stale copies misrepresent item state to anyone reading the branch.

Direction: extend the docs-branch sync step (done SKILL.md, the same step that owns the `{tmp_dir}` sweep) with a mechanical duplicate sweep for the `{backlog_dir}` root: after sync, for every top-level `docs/history/backlog/<name>.md` that also exists at `docs/history/backlog/{completed,deferred}/<name>.md` on the branch, delete the top-level copy (keep a content-mismatch guard — if the top-level copy differs from the archived one in more than the status line, surface instead of deleting). Prefer implementing it as a small script alongside the existing validators rather than prose-only instructions, so it is testable and idempotent; wire it into the sync step with the same warn-and-continue posture as the other optional gates.
