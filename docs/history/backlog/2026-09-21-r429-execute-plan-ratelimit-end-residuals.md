# Backlog: r429 execute-plan rate-limited-end residuals

Driving force: harden the structured rate-limited end landed 2026-09-21 (provider-429-retry-storm-shaping, `agents/skills/execute-plan/SKILL.md`): the fan-out shaping and structured `rate_limited` reporting contracts define how the run ends but leave three operator-visible edges unpinned. Status: open

Suggested fix (one or more of):

1. Specify the task-claim boundary at a mid-task rate-limited end: when the run ends rate-limited while a driver task claim is open, park or close the claim per the budget-pause precedent (a budget pause leaves no blocked claim, so the blocked-claim `resume` operation does not apply on resume); otherwise the claim stays fenced and the resumed run waits out the full `CLAIM_LEASE_SECONDS` (driver-owned, 4-hour) lease before it can reclaim its own task.

   r5 closeout-review residuals on the same claim boundary (2026-09-21):

   - Receipt carrier: the structured rate-limited end's machine-receipt duty (the end records the rate-limited stop as a blocked receipt in `runtime_state.json` so `waiting-for-capacity` derives from durable artifacts) has no named carrier when no task claim is open — receipts enter `runtime_state.json` only through claim-scoped driver operations, so a claim-less rate-limited end (between tasks, or at a review-panel launch) cannot satisfy the duty as written. Fix options: name the claim-scoped `capacity-unavailable` checkpoint receipt as the carrier and scope the duty to ends with an open claim, add a workflow-scoped driver event for the claim-less end, or derive `waiting-for-capacity` for this end from the recorded stop lines instead of a receipt.
   - Cross-resumption decay: the resumed-run cap re-derivation counts recorded stop lines from the last 24 hours and drops a line when its throttle window ends (a post-backoff attempt succeeds), but that window end is observed only by the live run — no durable window-end/recovery marker exists, so a resumed run re-counts stop lines whose windows already closed and over-shapes its cap. Fix options: prescribe a recovery marker line in the session manifest free text, written when the post-backoff attempt succeeds, so the window end is durable for later re-derivations; or scope the 24-hour decay clause to the in-run case.
2. Pin a minimal backoff (a floor, e.g. one defined retry interval) for the resume-after-backoff arm of the throttle-window rule: today "resumes the launch after a backoff" admits a zero-length backoff, and a zero backoff makes the "does not relaunch into the same throttle window" clause vacuous (the first post-stop attempt immediately succeeds and ends the window without any shaping).
3. Scale the 20-minute panel/panel-artifact wall-clock timeout when the fan-out cap is halved: the Step 1.2b intermediate panel, the Step 3.1 lens panel, and their recovery paths bound artifact production at 20 minutes assuming parallel launch; with the cap halved to the floor of 1 the same panel's launches serialize and can exceed the bound, tripping the focused-relaunch path for a healthy panel.
