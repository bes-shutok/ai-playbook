# Backlog: learn captures session skill-usage issues as high-priority backlog items and owns its skills-repo commits

Status: done
Done by: docs/plans/completed/2026-09-16-learn-done-workflow-updates.md (executed 2026-09-18)
Priority: high

Workflow: backlog
Source: user-directed 2026-09-16; placement re-decided to learn the same day (first drafted as a done step, retargeted because learn is the session-analysis skill), and the commit-ownership split (learn commits its skills-repo artifacts; done keeps the project repo) proposed as the routing mechanism. Sessions occasionally hit skill-usage issues (gate failures rooted in skill or script bugs, wrong or ambiguous skill instructions, missing runtime deployments, trigger failures), and the only durable record of such an issue today is whatever the agent improvises. Prior witnesses that each needed manual capture include the dead quota-window probe (404-in-200 fail-open), done-lock recovery incidents, and the plan-readiness deployment-gap signature; every one became a backlog item only through ad-hoc diligence.
Severity: High (skill defects found in consumer-project sessions are lost or delayed; the maintenance loop never learns about them, so fixes wait on a human re-noticing and re-filing)

## The gap, precisely

1. learn is the step that already re-reads session content and classifies what happened, but its durable output artifact classes are lessons (corpus edits) and, when lessons promote into skills, skill-file edits. A skill-usage issue is usually not lesson material, and it is not a review finding (receiving-review's Backlog capture does not apply), so it has no artifact path at all: it survives only as chat text or an improvised memory note. A lesson and a fix-tracked backlog item are different artifacts: learn records principles for future behavior, while a backlog item is what the maintenance loop surveys and converts into fix plans (D2 authors for the highest-priority plan-uncovered open item). A skill defect captured only as a lesson or a note never enters that pipeline.
2. learn runs in any consumer project (standalone or as done Step 1), but the skills corpus lives in one repository (facts key `skills_repo_path`). Capturing the issue durably therefore means writing into a SECOND repository (its resolved backlog home, `docs/history/backlog/`) and committing it there; today nothing in learn's flow commits across that boundary reliably.
3. The current commit path for learn-authored skills-repo changes is done Step 4's sweep via `commit-skills.sh`, which stages the ENTIRE `agents/skills/` tree with a blanket add and an auto-generated message. That both (a) misses learn artifacts outside `agents/skills/` (a backlog file under `docs/history/backlog/` is invisible to it) and (b) can sweep unrelated uncommitted peer edits in the skills repo.
4. Capture quality is unbounded: an issue written from memory at session end tends to leak project names, personal paths, or client identifiers into the skills repo, which is public. The corpus rules (project-agnostic wording, facts-key externalization, sensitive-data scan discipline) exist but are not tied to this capture path.
5. Lossiness is asymmetric with incident cost: a broken skill silently degrades every subsequent session in every project until someone re-notices and manually files an item.

## Fix candidates (in preference order)

1. **New learn step in the lesson-extraction/classification flow.** Contract: while classifying session findings, also identify skill-usage issues; classify each as a corpus defect only when the fault traces to a skill's instructions, a bundled script, a gate validator, or a missing or wrong runtime deployment; consumer-project code bugs are out of scope. For each issue family, create one backlog file in the skills repo's resolved backlog home following the `YYYY-MM-DD-<slug>.md` convention with `Status: open` and `Priority: high` (the corpus's top priority value, which is what routes the item to the maintenance loop's authoring lane).
2. **Required item contents, project-agnostic and clear of sensitive data:** which skill and step (file path plus step number), observed versus expected behavior, trimmed reproduction evidence (error output with secrets, usernames, org domains, project names, and ticket prefixes scrubbed), environment context (runtime, date, vendored copy versus repo copy), and suspected root area. Follow receiving-review's Backlog capture for shape and apply the same sensitive-data discipline as done Step 2.7 to the new file before writing it. Phrase everything in skill terms so the item reads correctly without knowing which project the session ran in.
3. **Dedupe before create:** survey the skills repo's open backlog items for an existing item on the same skill and step; when found, append the new witness details there (and re-affirm its priority) instead of creating a duplicate. This mirrors the maintenance loop's coverage check and the done Step 2.645 inbox gate's misfiling concern.
4. **Commit-ownership split (user-directed; generalizes an existing carve-out):** learn already commits learn-authored skill changes in the skills repo in its skill-placement flow ("Commit workflow: commit skill changes in the skills repository, separately from project changes"); generalize that into the standing rule: learn stages and commits its OWN learn-authored skills-repo artifacts by explicit path with a descriptive message (skill-file edits from lessons, and the new backlog items). Never a blanket add. done keeps exclusive responsibility for the current project repo (Step 3, including item 4b's project-corpus commit) and the docs/facts repos (Step 5). done Step 4 narrows to a fallback for skills-repo changes learn did not author (user-requested direct edits, other skills' outputs), scoped to session-attributed paths under the same ask-before-staging discipline as Step 3 item 0; the blanket `git add agents/skills/` in `commit-skills.sh` dies or is scoped the same way. When done invokes learn, learn's commit lands during Step 1, so Step 4's sweep then sees only non-learn leftovers (and no-ops when clean); no double commit.
5. **One-pass rule migration:** the "learn never commits" contract is encoded in several places and every one must move in the same change: done SKILL.md frontmatter ("This is the only skill that performs git commits") and its Rules section; learn SKILL.md line "Do not commit changes; committing is the `done` skill's responsibility" and its "Commit ownership" section (learn writes the corpus, does not commit); README catalog rows for both skills; any consumer skill repeating the rule (receiving-review, review-loop hooks). State the new boundary precisely everywhere: learn commits only its own learn-authored artifacts in the skills repo; done commits the project repo and the docs/facts repos.
6. **Failure semantics and concurrency:** backlog creation and the learn commit must not block learn or the enclosing done run. When creation, scrubbing, or the commit fails, report the failure plus a one-line issue summary in the learn output (and, when done is running, the done Step 7 outcome report) as a manual follow-up; done Step 4's narrowed fallback may pick the file up. There is no lock on the skills repo today (done Steps 4/5 commit other repos unlocked too), so keep the blast radius small by staging only learn's own paths and retry once on git index contention before reporting.
7. **Integration notes:** learn owns analysis, artifact creation, and its own skills-repo commits; done owns project-repo and docs/facts commits; receiving-review's Backlog capture keeps owning the review-findings path (a disjoint source); the maintenance loop's D2 is the downstream consumer of the `Priority: high` marking; the done Step 2.645 backlog inbox location gate is unaffected because the file lands inside the resolved backlog home. A skill issue may ALSO yield a lesson when it generalizes; the backlog item is the fix-tracking artifact, not a replacement for the lesson. Standalone learn runs become self-contained (no dangling uncommitted artifacts awaiting some later done).

## Acceptance criteria

- A session that hit a skill-usage issue and then runs learn (standalone or via done) ends with a COMMITTED backlog item in the skills repo's resolved backlog home: `Status: open`, `Priority: high`, naming the skill and step, observed versus expected behavior, scrubbed reproduction evidence, and zero PII, personal paths, project names, org identifiers, or ticket prefixes.
- The commit that lands it stages only the learn-authored paths (no blanket `agents/skills/` add anywhere in the path), and no done step double-commits or sweeps it.
- done's responsibilities are unchanged for the project repo and the docs/facts repos; done Step 4 survives only as a narrowed, ask-first fallback for non-learn skills-repo changes.
- The rule migration is complete: no skill, README row, or consumer reference still states the unqualified "learn never commits" contract.
- A session with no skill issues creates no backlog items and reports nothing new (no noise items).
- Duplicate issues fold into an existing open item as added witnesses rather than new files.
