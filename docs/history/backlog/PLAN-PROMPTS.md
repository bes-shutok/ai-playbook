Tracked rolling log of ready-to-dispatch plan-creation prompts, most urgent first.

The Standing rules block below is the shared prompt-log write, freeze, prune, and recovery contract's canonical home, outside every entry range; no entry-range prune can remove it.
Standing rules:

- Order: entries sit most-urgent-first; a new entry inserts at the urgency position it merits, judged when it is written.
- Prune rule: an entry is removed when its plan file exists in the plans root. Every prune first reads the target entry through its actual next heading (never assumed adjacency) and inventories every receipt line in that range before any deletion; every pre-existing receipt line stays byte-for-byte and in its original order regardless of slug; and removal is evaluated per origin under the `Coverage and removal rule` below, so a landing or monitor prune removes only covered origin bullets and their explicitly paired scope arms. A landing prunes only its own dispatch entry (the entry whose prompt authored the plan that landing lands), and every removal carries its plan-file witness (the plans-root file or its `completed/` twin), printed as one `PLAN-PROMPTS-PRUNE: <slug> -> <witness path>` receipt line per removed entry; any other removal (a peer entry, a bulk sweep) is never a landing's side effect and routes through the maintenance monitor's rolling prompt log duties instead. The collateral served-entry class (added 2026-10-16, the prompt-log-collateral-served-prune plan): a landing may additionally prune a collateral served entry, one the closeout's read-only discovery mode (`python3 scripts/check_prompt_log_origins.py --collateral-served --base <merge-base>`) lists because every origin is served at HEAD or was served at base and deleted inside the landing range with at least one range-produced origin; the removal carries its own `PLAN-PROMPTS-PRUNE: <slug> -> <witness path>` receipt line whose witness is the covering landing's in-tree plan-file path (never the landing commit digest, which does not exist at rider time), the pruning entry is re-audited by the same prune audit on the net diff, and the blanket any-other-removal exclusion still stands for unserved or unlisted entries. The ad-hoc-superseded removal class (added 2026-10-06, the two-mode loop policy plan): when an ad-hoc run completes an item, the monitor freezes the entry naming it before the landing and prunes it strictly after the landing commit is recorded; where no plan file exists, the recorded landing commit digest substitutes for the plans-root witness and the pruning commit carries the `EXEC-PROMPTS-PRUNE: <slug> -> <landing commit>` receipt naming the removed slug, and the extended prune audit enumerates both rolling logs and accepts that witness class (the landing commit resolving to an existing commit). The pre-provision source-history close-as-covered class (added 2026-10-31, the plan-authoring-stand-down-before-charter plan): an origin the authoring selection's actionability probe (the D2 rule in `agents/skills/maintenance/decisions.md`) proves already landed closes before any claim, frozen prompt entry, or worktree exists, in one targeted commit that deletes the satisfied backlog row and prunes the entry together; the removal carries one `PLAN-PROMPTS-PRUNE: <slug> -> <implementing-commit>` receipt line naming the reachable implementing commit (the commit digest resolving to an existing commit, the same token resolution the audit applies to any receipt witness), and the same prune audit stays in force over it; a refused close preserves the row and the entry, and incomplete or ambiguous probe or history evidence closes nothing and keeps the origin dispatchable. Removals are mechanically audited by the prune audit (`python3 scripts/check_prompt_log_origins.py --prune-audit --base <merge-base>`): fail-closed at the landing closeout, consultative (report-only, never blocking) at the maintenance survey. The separate pending-change audit (warning-only detection of prompt-log changes no landing has recorded) is out of this rule's scope: it stays report-only under its own backlog row. The landing prune audit's receipt-loss class is flagged, not warning-only, and the landing closeout invokes it as `python3 scripts/check_prompt_log_origins.py --prune-audit --repair --base <merge-base>` (the landing-only automatic mode that restores an exact deleted receipt line from its committed bytes and reruns the audit); the maintenance survey keeps the default read-only invocation and never repairs.
- Coverage and removal rule: removal is evaluated per origin, and one operation removes every independently eligible origin bullet together with its explicitly paired scope arms. Coverage per origin: an own entry is covered by its unique binding, exactly one heading whose `Frozen:` witness names the plan's authoring claim, whose `Origins:` includes the plan's source backlog origin, and whose slug equals the canonical feature slug (the plan filename minus its leading date prefix); a collateral entry is covered only where the closeout's read-only origin discovery reports an origin removed inside the landing range; an ordinary monitor origin is covered only when a plan in the plans root or its `completed/` twin carries a `Backlog origin:` line exactly equal to that origin path, entry-slug discovery covering only the origin that plan itself names and never any other `Origins:` bullet; an ad-hoc origin (either log) is covered only when its entry was frozen before its recorded ad-hoc landing commit; a pre-provision source-history origin is covered only when the origin's own probe reruns green against current source, each explicit expectation the origin states matches, and a reachable implementing commit witnesses those exact expectations (the class the `Prune rule` names; ambiguous or incomplete evidence leaves the origin dispatchable and closes nothing). A partial removal (origins remain) deletes only covered origin bullets and their paired scope arms, keeps the unresolved origins dispatchable, and adds no receipt; the `Frozen:` mark stays while any retained origin has a live claim or worktree (a fresh check over the retained origins, never the landing plan's own authoring claim) and clears only after landing when that check finds none. Full removal (the heading empties) writes exactly one receipt using the last removed origin's class and witness in the original `Origins:` order: the covering landing plan for own and collateral PLAN removals, the exact-origin plan for ordinary monitor removals, the recorded landing commit for ad-hoc removals, the implementing commit for pre-provision source-history removals. Ambiguous origin-to-scope pairing or missing, duplicate, or shared binding evidence (duplicate own-entry headings included) leaves that target byte-identical with the reason reported; other independent targets stay eligible, and the log stays unchanged when no target qualifies.
- Freeze rule: when authoring for an entry has started (a live authoring claim file keyed to the entry slug or one of its origins under the tmp authoring-claims directory, live meaning its `updated:` fresher than one cadence period per the `G1a` discovery arm's bound (a stale claim taking the takeover path instead of freezing), or a live authoring worktree or branch for its plan), the entry is marked frozen before any further log processing: a `Frozen:` line naming the witness and date goes directly under the entry's heading. A frozen entry accepts no origin additions, no prompt rewrites, no repositioning, and is never a dispatch candidate; the mark is removed when the authoring aborts without a plan file in the plans root (the entry reopens), and the entry is pruned outright per the prune rule when its plan file lands; a landing that removes only some of the entry's origins keeps or clears the mark per the `Coverage and removal rule`'s freeze-retention clause. The matching ad-hoc case (added 2026-10-06, the two-mode loop policy plan): a freeze recorded for an ad-hoc run claim clears when the run's landing is stood down with a recorded reason or the run aborts without a landing commit (the entry reopens for dispatch). Frozen-line provenance (single-homed in this rule): a claim owner's self-freeze names its own session id; duty (b)'s mark arm (agents/skills/maintenance/decisions.md) stays a sanctioned writer recording the observed claim's session id, or `unowned` when the claim file stands but names no parseable session line, and when the trigger is worktree/branch-witnessed with no claim file standing the mark records `unowned` with the live worktree or branch as its witness slot; duty (b)'s mark-clears clause stays the sanctioned remover with no session-id recording duty, existing self-clear legs unchanged; the ad-hoc freeze writers (the ad-hoc arm's pre-landing freeze edits, duty (b)'s EXEC mark leg, duty (i)'s pre-landing PLAN-PROMPTS freeze) keep their existing witness shapes, this clause's session-id legs scoping to authoring-claim freezes; takeover succession (a mark naming the deposed predecessor a takeover consumed) is legitimate until the entry's prune, no succession record added, and the investigable class is a mark whose recorded session id matches neither the marked claim's own session id nor `unowned`, the test reading the live claim file only while it stands and being vacuous once the claim file's closeout deletes it; at clearance the monitor's parked-state pickup read runs per the convention home's pickup clause in the AUTHORING CLAIM paragraph (agents/skills/maintenance/template-authoring.md, by reference).
- Not a backlog item: never cite this file as a plan's Backlog origin.
- Writes are targeted section edits (an entry's own section), never a whole-file rewrite from a stale read.
- Before every write, re-read the file and compare it against the read the edit was prepared from; any difference is drift: retry once from the fresh read, then attempt a pure append of the entry at the end of the file (conflict-free under the targeted-edit rule); only when that append also fails the drift check, abort and report the full intended entry text in the turn output as the fallback record; the next write attempt re-emits from that record instead of re-running the investigation.
- Every log write is committed in the same turn that performs it.
- Write boundary rule: a log write that commits in the primary checkout (the monitor's prune, freeze, or investigate write, a Phase 0 freeze commit, a primary-placement checkpoint touching a log) acquires or reuses the primary done lock (the repository's `scripts/done-lock.sh` done lock), before any staging or index write and before the final log read, holding it through the commit and failure recovery; the caller selects the intended symbolic ref and starting OID after lock acquisition, verifies the selected pair against primary `HEAD` under the done lock before the final log read or edit, and on a mismatch recovers before changing the log; the write then passes the selected pair to the runner's ref-bound captured-tree transaction (`scripts/done_run.sh`) and never takes the repo-wide merge lock (the merge-lock acquisition refusal for primary log writes is retired 2026-10-28, plan `docs/history/plans/2026-10-25-primary-log-branch-drift-at-commit.md`). The runner refuses before staging when either rolling-log path already has a staged delta (the caller-side pre-staged-owned-path refusal is retired; the runner owns the two-path check), stages and commits only the declared owned paths through that transaction, and on every refusal before the captured-ref compare-and-swap succeeds the runner's cleanup unstages and verifies only this writer's declared owned delta before release (recovery that cannot be verified blocks later primary writes and reports through the existing recovery path); after the compare-and-swap succeeds, a later ledger-append or post-commit-hook error reports that the landed commit stands and never rolls it back. The writer declares each declared owned log path's expected post-edit blob id (`--log-expected`, computed over the authored bytes before the commit, never by hashing the file at commit time); a mismatch advisory names both blob ids as a divergence signal with reconciliation running from them, the carried foreign bytes' disposition staying operator-gated under this rule's foreign-bytes posture. Done-lock acquisition failure does no work. A session working from a worktree keys the primary done lock from primary-checkout context (the Phase 0 freeze included); worktree branch commits stay isolated under the existing merge-lock guard, and no new lock is added. When the runner's pre-stage guard (either the two-path staged-delta check or the staged-set enumeration) refuses the transaction naming a foreign staged path (staged in the shared primary index by a session other than this writer, whether or not the writer declared that path), the remedy is operator-gated and blob-preserving: never stage, discard, or commit that path autonomously; the remedy runs only on the operator's explicit direction for that foreign path, and without that direction the writer stands down or parks exactly as before. Under that direction: (a) record the foreign path's staged blob sha; (b) restore only that named path from the index (`git restore --staged -- <path>`, worktree bytes untouched); (c) rerun the refused transaction; (d) re-add the path; (e) verify the re-staged blob sha is byte-identical to the recorded sha. Unstaged-live-delta set-aside arm: Under done lock, snapshot declared logs before final read/edit. Automatically isolate unstaged-only declared deltas; staged bytes refused by either guard keep the operator gate. Create UUID and one zero-old-OID ref to record.json/blobs. Journal ref/start HEAD/subject; per path saved blob IDs (only recovery source), candidate/output IDs, class, before/after HEAD/index/worktree IDs+modes. CAS phases: captured, index-set-aside, candidate-installed, runner-staged, runner-resume-prepared, runner-resume-ready, committed, peer-reapplied, disposition-verified. Regular files 100644/100755 only; others park untouched; no symlink/gitlink following. Before mutation, recorded/current HEAD/index/worktree IDs+modes must match; else retain ref/park. Declared: save staged blob; set index to HEAD; merge captured worktree/HEAD/post-edit (base/ours/theirs); install candidate worktree-only. Undeclared: index=HEAD; install saved blob worktree-only; verify index before (a)-(e). Check ride-along after set-aside. Reapply worktree-only: undeclared after (e), declared after CAS; merge HEAD/base, committed writer/ours, saved worktree/theirs. Hash candidate/merge/reapply outputs separately; verify output IDs/modes, never inputs; rederive clean merge. Declared paths skip (d)/(e), never re-add staged blobs; report IDs. Early pre-stage refusal before cleanup: re-read journal/state; never retry/succeed; keep peer bytes out of index; park with ref/state. Post-stage refusal: verify candidate IDs/modes. Before restore, CAS runner-resume-prepared with candidate/HEAD index IDs+modes and worktree ID/mode; recheck ref/HEAD under lock; restore matching entries to HEAD, keep worktree. From prepared, candidate-index + candidate-worktree means repeat restore; HEAD-index + candidate-worktree means CAS `runner-resume-ready`; else park. From ready, rerun with declared `--stage` paths, recorded subject, `--expected-ref` and `--expected-oid`; do not reread/edit. Retry refusal with candidate staged returns to prepared; cleanup never resets index. Post-CAS: reapply only if landed commit is sole start-HEAD child and expected-ref target, with matching subject and declared tree IDs/modes; else retain/park. Before next primary read/edit, resume unverified refs under lock. A re-apply mismatch leaves bytes unstaged and parks for the operator with every recorded blob id. Automatic terminal: output ID/mode and unchanged index. Operator terminal: fresh current-session operation/path direction and confirmed final HEAD/index/worktree IDs+modes. Retain ref until terminal; recheck under lock and remove only it. Ride-along precondition: Under lock, compare HEAD/index/worktree IDs+modes before each mutation; mismatch preserves bytes/ref and parks.
