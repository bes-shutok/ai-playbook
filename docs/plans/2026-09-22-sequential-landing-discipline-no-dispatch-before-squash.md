# Plan: Sequential landing discipline (no dispatch before the previous run's squash lands)

Backlog origin (scope of record): `docs/history/backlog/2026-09-21-sequential-landing-discipline-no-dispatch-before-squash.md`.

Sequencing of record: this plan must not run in parallel with `docs/plans/2026-09-21-scheduler-maintenance-state-durability.md` (in-flight execution at authoring time, unlanded) because both edit the same SKILL.md State file section, Step 1, Step 3, and Revisions ledger, and the same prompt-templates.md successor-dispatch paragraph and deviation list. Two mechanisms carry the constraint, mirroring that plan's own pattern, in order: (1) this plan's landing is accompanied by a repo-keyed memory note marking this plan dependency-blocked by the state-durability plan (a duty of this plan's own authoring session at landing, not a task of this plan's execution), which the dependency skip honors and which self-heals exactly when the blocker is completed or absent from the resolved plans_dir (a deferred blocker keeps the mark binding, mirroring D1's self-heal); (2) Task 1's first checklist item is an edit-nothing stand-down precondition that verifies the same facts at execution time with a machine test and takes the sanctioned stand-down path (no failure credit) when either landing conjunct fails; a count- or dash-conjunct failure re-baselines instead of standing down. The machine test is content-based on purpose: the blocker's landing (not its archival) is what clears the collision hazard, and archival-without-landing is exactly the case this plan exists to govern.

## Terms

- **Landing**: a run's content being present on the repository default branch: for an execution run, its squash merge committed onto the default branch; for an authoring run, its self-landed commit on the default branch.
- **Landed-commit test**: the mechanical check that the default branch carries a run's bytes: `git cat-file -e refs/heads/<default>:<landed_path>` for the record's `landed_path` value; the clear arms of the read-back additionally require content equality with the recorded tip's copy of the path (sha256 comparison, below). For an execution run the `landed_path` is the run's archived plan path under the completed plans directory (the archive move rides the squash commit, so the archived file's presence under the default branch proves the squash landed); for an authoring run it is the landed plan path under the resolved plans_dir.
- **pending_landing**: additive top-level scheduler-state field carrying the deferred-landing intent record (shape in the State file section this plan edits); single-valued; the drain cursor for a queue of per-run notes.
- **pending-landing note**: the per-run repo-keyed memory note named `pending-landing-<plan-slug>` (the plan-slug suffix makes strandings non-colliding across plans; a same-slug re-stranding overwrites the note with fresh facts and the superseded run's branch and worktree leak unreferenced, accepted); the human-visible witness paired with the state field, the recovery input when the field is lost (carrying the attempts counter across a state-file loss), and the carrier for a race-produced second stranding the occupied-field guard refuses to overwrite.
- **Post-review, pre-landed state**: a child run whose work is complete (its plan archived for an execution run, its review loop exited for an authoring run) whose landing is not verified on the default branch.
- **Landing gate**: the conjunct that blocks a new child dispatch of either lane while an outstanding unlanded run survives the Step 1 resolution (the field set, or any repo-matching `pending-landing-<plan-slug>` note surviving the resolution; the gate is global, which subsumes the origin's same-lane clause); re-checked before creating any child or beginning an in-session run at the Step 5 final slot as the pre-dispatch landing gate.
- **Landing-completion work**: the scheduler turn's own bounded completion of an outstanding landing: the gate re-run executes in a temporary worktree of the recorded tip, and the landing critical section (the squash merge, the stash cycle, the record clear) executes in the primary checkout under the merge landing lock.

## Gist & Examples

What changes: the maintenance loop gains a sequential landing discipline. A completing child verifies its own landing mechanically and records a `pending_landing` intent when the landing deferred; the execution payload's successor duty chains nothing while the run's own landing is unverified or any landing record or queued note is outstanding; the scheduler turn's Step 1 reads the record and the per-run notes (re-creating a lost record from a note), and D1/D2 complete the landing themselves when the primary checkout is free, or defer; no lane dispatches while an outstanding unlanded run or a surviving note survives the resolution; the fleet invariant caps the post-review, pre-landed state at one recorded run.

**Before (today):** the execution blueprint's successor duty opens with "after the final squash merge passes", but nothing verifies the pass. The 2026-09-21 witness: a durability plan's `merge --squash` aborted on peer dirt overlapping branch files, the child kept the branch and reported, and the queue moved on; the plan sat executed-but-unlanded (archived, terminal receipt written) for hours until the operator ordered the landing by hand, while the next run's landing raced the same checkout. The authoring lane has the same hole in mirror: a self-landing stranding keeps the worktree and branch and reports, and nothing mechanical carries the owed landing to a later actor.

**After (this plan):** the execution payload's landing critical section ends with the landed-commit verification (`git cat-file -e refs/heads/<default>:<archived-plan-path>` after the squash commit, before the branch deletion); when it fails, or when any gate defers the merge, or when the lock wait times out, the child writes `pending_landing` (targeted state edit at the primary checkout root, immediately when the deferral is known and before the lock release) plus the per-run `pending-landing-<plan-slug>` note, cleans any conflicted squash state with `git reset --merge`, chains nothing, and ends. The authoring blueprint's stranding paths record the same pair before ending. The scheduler turn's Step 1 reads the field first: it clears the field and deletes the record's note when the landed-commit test passes with content equality against the recorded tip's copy; resolves the lane to the landing-completion work when the branch or worktree survives; re-targets the record when a ref or reflog search resolves the recorded tip after the branch name went stale; escalates `pending-landing-orphaned` when nothing resolves; and re-creates a lost field from a surviving note. D1 and D2 then gate on the resolution: the landing-completion work re-runs the deferred run's gate set in a temporary worktree of the recorded tip and executes the landing critical section in the primary checkout, guarding the squash against peer bytes, and defers with a recorded reason when the checkout is occupied by live peer work; no dispatch happens while the record or any queued note survives.

**Edge cases:** a stale `pending_landing` whose landed-commit test now passes with content equality is cleared, the record's note deleted, and the recorded branch and worktree deleted when they still exist (teardown gated on the verified landing, which the passing test provides; teardown failures are recorded in `decision_reason` and self-heal via the next turn's re-test). A record whose branch and worktree are both gone: the read-back searches `refs/heads/` and the reflogs once for the recorded branch name and branch tip (a for-each-ref match on the name, a reflog scan for the tip); when something resolves, the read-back re-targets the record's branch field to the resolving ref (or the resolved sha), clears the worktree field (it is gone), and routes the lane to the landing-completion work; only when nothing resolves does the turn record `turn_error: pending-landing-orphaned` (a renamed branch or a moved worktree is not an orphan). A record whose `landed_path` never lands because the run was fully rolled back by its own failure duties is human-procedure-only: the human clear procedure's landing addition confirms the run abandoned or landed, clears the field, and deletes the record's per-run note in the same action (a confirmed-abandoned clear also deletes the branch and worktree; a confirmed-landed clear verifies the landed-commit test first), because a surviving note would re-create the record on the next turn. A lost record (state-file loss, or a child that died between the failed landing and the state write) is re-created by the Step 1 reconciliation from a surviving per-run note, with `attempts` carried from the note so the stuck counter survives the loss; when several notes exist, the reconciliation picks deterministically (filename-sorted first) and leaves the others as the remaining queue; the residual window where neither field nor note was written before a child crash stays accepted and is detected by a human reading the branch list (the origin records the 2026-09-21 landing was completed hours later by explicit operator instruction). A child stranding while the field already holds another lane's record never overwrites it: it writes the per-run note only and reports the collision; the field is the drain cursor, the gate blocks on any surviving note, and the reconciliation plus the completion work drain the queue at one record per turn. Persistent occupancy of the primary checkout by a live peer is detected transitively (the occupying peer's own failure cap and the human check's decision_reason reading), not by the landing machinery. A stranded authoring child accrues a failure credit at the six-hour horizon where a stranded execution child is evidenced by archival (the failure-cap section is frozen; the asymmetry is accepted and the global gate blocks re-dispatch regardless). A record appearing between a child's landing-gated chaining and the successor's fire is the accepted TOCTOU mirror of the Invariants race bullet (the successor's own landing still verifies and it chains nothing after).

## Design Invariants (CR Guard)

- The landing and its completion never push to origin, and both ride the existing merge landing lock; `G3b` semantics are unchanged (a fresh hold defers, never stands the turn down). No new lock, script, or primitive is introduced.
- Additive state fields never bump the schema version (schema 4; additive-no-bump precedent: `park_proposals`, `rate_limited_events`, `quota_at_decision`); the Step 6 carry-forward list must name the new field (and the read-back's orphan `turn_error`) or the next whole-document rewrite drops them.
- Sanctioned-writer closedness: the `pending_landing` writes join the State file's writer-classes enumeration explicitly (the successor-dispatch class gains the execution-child landing-gate write; a new named class covers the completing authoring child's self-landing record, an in-session authoring run's stranding record joining the scheduler-turn class; the scheduler-turn class gains the reconciliation write, the clear-on-landed, the attempts-increment write, every landing-path `turn_error` write (the orphan, stuck, and stash-left escalations), and the note-delete bookkeeping on the memory-index surface, which is not a state-file write); the lead-in count sentence moves from five to six with the sweep. No unsanctioned writer class is created.
- SKILL.md stays runtime-agnostic: the landed-commit test is git mechanics and state mechanics, no automation primitive names enter SKILL.md.
- Blueprint bodies keep their pinned placeholder sets and exactly-once anchor literals; every blueprint change registers a dated deviation-list entry in prompt-templates.md (the file's protocol), and the entries paraphrase the note and record literals rather than quoting them, so the counts stay exact. The re-arm duty paragraphs are byte-identical between the blueprints and are not edited.
- Peer dirt is never committed by the loop. The landing-completion retry's sanctioned stash-and-restore is scoped to the retry: the stash is taken with `git stash push -m` labeling the record and the plan, never uses `-u` (so the untracked-overlap collision class deliberately exits through the stuck escalation rather than through a stash that would swallow untracked peer files), the stash entry id is captured, the restore is verified to consume the entry with `git stash pop --index` (a plain pop fallback when `--index` refuses, accepting the staged-to-unstaged downgrade as the sanctioned cycle's property), and a failed or conflicted restore leaves the stash in place (never dropped) and records `turn_error: pending-landing-stash-left` naming the entry, so the crash-window recovery artifact is always discoverable; the conditional writes (the occupied-field guard, the reconciliation's null-field precondition, the clear-on-landed, the orphan re-targeting, and the attempts increment) re-evaluate their precondition on the targeted-edit drift retry and yield to the fresh state instead of re-applying prepared bytes, each preconditioned on the record identity (plan path plus branch tip) matching the record being mutated.
- The landing gate is evaluated once per lane decision (D1 and D2) and re-checked once at the Step 5 final slot; no scheduler-turn site exists beyond the lane decisions, the Step 5 final slot, and the child duties' own chain-site conjuncts.
- The loop never blocks on questions (SKILL.md Invariants, unchanged): every landing outcome is decided and recorded, never asked about.
